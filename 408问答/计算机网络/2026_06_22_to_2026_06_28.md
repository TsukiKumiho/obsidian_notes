## Q13 · 路由的概念——路由器到底在做什么

> 路由到底是什么？

**答：路由就是路由器为数据包选择从源到目的地的路径的过程。核心动作只有两个——查路由表 + 转发到下一跳。**

### 一、路由 = 逐跳转发

```
你要从 A 发数据到 D，沿途经过路由器 R1、R2：

  A ──→ R1 ──→ R2 ──→ D

R1 收到包：
  ① 看目的 IP = D
  ② 查路由表：
      去哪       下一跳      出接口
      D          R2         eth1
  ③ 把包交给 R2（帧头重写为 R2 的 MAC）

R2 同样操作 → 直到 D 收到
```

**每个路由器只负责选择"下一跳"。** 它不需要知道整条路径——只需知道转交给谁离目标更近。

### 二、路由表长什么样

```
路由器 R1 的路由表：
┌────────────────┬────────────┬──────────┐
│  目的网络       │  下一跳     │  出接口   │
├────────────────┼────────────┼──────────┤
│ 192.168.1.0/24 │  直连       │  eth0    │  ← 自己就在这个网络里
│ 10.0.0.0/8     │  R2 的 IP   │  eth1    │  ← 转发给 R2
│ 0.0.0.0/0      │  网关 IP    │  eth1    │  ← 默认路由：不知道去哪就扔给网关
└────────────────┴────────────┴──────────┘
```

### 三、路由表怎么来的

| 方式 | 说明 | 场景 |
| :--- | :--- | :--- |
| **直连路由** | 路由器接口配置了 IP 和掩码后自动生成 | 自己直连的网络 |
| **静态路由** | 管理员手动配置 | 小网络或不常变的路径 |
| **动态路由** | 路由器之间跑协议（RIP/OSPF/BGP）互相学习 | 互联网 |

### 四、路由 ≠ 转发

| | 路由（Routing） | 转发（Forwarding） |
| :--- | :--- | :--- |
| **是什么** | 决定走哪条路——**建路由表** | 按表执行——**查表发出去** |
| **在何时** | 后台持续运行（路由协议交换信息） | 每个包到达时 |
| **类比** | 规划从北京到上海的路线 | 走到每个路口时按导航拐弯 |

> **省流：** 路由 = 路由器根据目的 IP 查路由表、找下一跳、转发出去。每个路由器只知道下一步交给谁，大家各管一段，最终把包送到目的地。路由是建表（控制面），转发是查表（数据面）。

## Q14 · 路由器转发时的"变与不变"——IP 和 MAC 各自改不改

> "转发不放：路由器只改MAC不改IP(NAT除外)" —— NAT 除外是什么意思？那一个局域网要联互联网不是必须得用 NAT 转化为公网 IP 吗？

**答：普通转发不改 IP，经 NAT 才改 IP。家用路由器两者同时做，但 408 考试会拆开考。**

### 一、普通转发：只改 MAC，不动 IP

```
包从 A 到 B，中间经过路由器 R1：

A(192.168.1.2) ──→ R1 ──→ B(10.0.0.5)

离开 A 时：
  源MAC = A的MAC    目的MAC = R1入接口的MAC
  源IP  = 192.168.1.2  目的IP  = 10.0.0.5

经过 R1 转发后：
  源MAC = R1出接口的MAC  目的MAC = B的MAC（或下一跳的MAC）
  源IP  = 192.168.1.2    目的IP  = 10.0.0.5    ← IP 没变！
```

> 每个路由器查路由表 → 找下一跳 → 改帧头（源MAC/目的MAC重写）→ 发出去。IP 头在整个转发链路上**端到端不变**——这是 IP 协议"无连接数据报服务"的核心特征。

### 二、经 NAT 时：IP 也要改

```
内网主机 A(192.168.1.2) 访问公网服务器 S(8.8.8.8)：

经过 NAT 路由器时：
  离开 A 时：源IP=192.168.1.2, 源端口=50000
  NAT 转换后：源IP=公网IP(1.2.3.4), 源端口=新端口(60000)
  → IP 也被改了！
  
NAT表记录：
  192.168.1.2:50000 ↔ 1.2.3.4:60000

回包时反向转换：
  目的IP=1.2.3.4:60000 → NAT查表 → 目的IP=192.168.1.2:50000
```

> NAT 改的是 IP 头中的源 IP（出去时）或目的 IP（回来时），这是因为**公网不认识私网地址**——不改 IP 的话回包找不到路。

### 三、家用路由器的实际情况

你说的完全对——家用路由器通常**转发 + NAT 绑在一起**：

```
你的电脑(192.168.1.x) 上百度：
  ① 包先到路由器
  ② 路由器查路由表 → 下一跳是运营商网关（这是"转发"）
  ③ 同时做 SNAT → 源 IP 从 192.168.1.x 变成公网 IP（这是"NAT"）
  ④ 包才出门
  
回来时反过来：
  ① 回包到路由器，目的 IP = 公网 IP
  ② 查 NAT 表 → DNAT → 目的 IP 变回 192.168.1.x
  ③ 查路由表 → 找到内网接口
  ④ 改 MAC 发给你
```

> 所以"路由器只改 MAC 不改 IP"是指**普通转发流程中的 IP 层行为**。NAT 是在转发之外**额外做了一次 IP 头改写**。家用场景下两者叠加，IP 确实被改了。

### 四、408 考试怎么区分

| 题目描述 | 是否改 IP | 关键判断依据 |
|:---|:---:|:---|
| "路由器 R 从接口 eth0 收到一个 IP 包，查路由表后从 eth1 发出" | **不改 IP** | 题干没说 NAT |
| "路由器启用了 NAT，内网主机访问外网" | **改 IP**（源 IP 改） | 题干明确说 NAT |
| "NAT 路由器收到外网回包" | **改 IP**（目的 IP 改） | NAT 反向转换 |
| "跨网段通信，主机 A 发 ARP 请求拿 B 的 MAC" | 不涉及 IP | ARP 只改帧头 |

> 核心原则：**题目不说 NAT 就当普通转发**——只改 MAC 不改 IP。说了 NAT 再考虑 IP 地址转换。

## Q15 · NAT 与路由表查找的先后顺序——实际场景中的完整链路

> 家用路由器收到内网发往互联网的包，是先查路由表还是先做 NAT？

**答：通常先查路由表确定"能出去"，再做 NAT 改写源地址，最后从对应接口发出。但两者的执行时机在不同实现中可能重叠——408 不考这个先后顺序，考的是两者的独立性和联动。**

### 一、逻辑流程

```
内网包(192.168.1.2 → 8.8.8.8) 到达路由器：

① 查路由表 → 匹配默认路由 0.0.0.0/0 → 下一跳=运营商网关, 出接口=WAN口
   （先确认"这个包能出去"）

② 查 NAT 表 → 192.168.1.2 有对应映射？没有→新建 SNAT 条目
   源 IP: 192.168.1.2 → 公网 IP(1.2.3.4)
   源端口: 50000 → 新端口(60000)

③ 修改 IP 头（源 IP 变为 1.2.3.4）→ 重算首部检验和
   修改帧头（源 MAC = WAN口MAC, 目的 MAC = 网关MAC）

④ 从 WAN 口发出
```

### 二、NAT 与路由表的配合——回包如何找到内网主机

```
回包(8.8.8.8 → 1.2.3.4) 到达路由器 WAN 口：

① 检查目的 IP(1.2.3.4) —— 是路由器的公网 IP（路由器自己就是终点）
   → 上交给 IP 层处理

② IP 层发现协议号是 TCP/UDP → 查 NAT 表
   1.2.3.4:60000 → 192.168.1.2:50000  ← 反向转换

③ 目的 IP 变为 192.168.1.2 → 查路由表
   192.168.1.0/24 → 直连网络 → 从 LAN 口出

④ 查 ARP 表 → 192.168.1.2 的 MAC → 封装帧 → 发出
```

> 回包时**先 NAT 转换再查路由表**——因为转换后的目的 IP 才是有意义的内网地址。

### 三、408 视角的总结

| 考点 | 考试问法 | 答案 |
|:---|:---|:---|
| 路由表+转发 | "路由器收到包后如何转发？" | 查表→最长前缀匹配→改MAC发下一跳 |
| NAT | "NAT 路由器如何实现内网访问外网？" | SNAT改源IP+端口，建表，回包时DNAT还原 |
| 联动 | "内网发出包经过NAT路由器的完整变化？" | MAC变(每跳) + IP变(NAT处) + 端口变(NAPT处) |
| 排错 | "NAT表项过期后外网回包会怎样？" | 找不到NAT映射→路由器丢弃回包 |

> **省流：** 普通路由转发只改 MAC 不改 IP。NAT 是一个独立功能——在 IP 层额外做源/目的地址转换，家用路由器两者叠加使用。408 选择题里，没有 NAT 关键字的题按"只改 MAC 不改 IP"处理，有 NAT 关键字的题才考虑 IP 地址被改。回包时先 NAT 转换再查路由表——因为转换后的内网地址才能用于查表转发。

## Q16 · IP 地址两层结构与三层结构——子网号如何被区分

> 关于 IP 地址的结构，最开始是两层结构 {网络号, 主机号}，加入子网后变成三层结构 {网络号, 子网号, 主机号}，位数仍为 32 位。那么如何分辨该 IP 地址是两层还是三层结构？两层结构的 IP 与子网掩码做与运算后也会产生一个"子网号"，但它根本就没有子网号——这如何解释？

**答：不存在"没有子网掩码"的 IP。不是"IP 地址先有两层或三层结构再配掩码"，而是"掩码是什么样，网络前缀就有多长"——掩码 = 默认掩码则子网号字段长度为零（退化为两层），掩码更长则多出来的位数就是子网号。**

### 一、核心逻辑：掩码定义一切

```
        无子网（C类 /24）:              有子网（C类 /26）:

  11000000.10101000.00000001.01100100      11000000.10101000.00000001.01100100
& 11111111.11111111.11111111.00000000    & 11111111.11111111.11111111.11000000
  ───────────────────────────────────      ───────────────────────────────────
  11000000.10101000.00000001.00000000      11000000.10101000.00000001.01000000
  └────── 网络号(24位) ──────┘└主机号┘     └──── 网络号(24位) ───┘└子网┘└主机┘
         ↑ 掩码1的位数=24                        ↑ 掩码1的位数=26
         与默认/24相同                              比默认/24多2位
         → 子网号长度=0                             → 子网号=2位
```

**掩码中 1 的数量就是网络前缀的总长度。** 无论有没有子网，路由器只做一件事：目的 IP & 掩码 → 网络前缀。掩码比默认多几位，子网号就有几位。

### 二、判定规则

| 场景 | 掩码 vs 默认 | 子网号字段 |
| :--- | :--- | :---: |
| A 类地址 /8 | = 默认（/8） | 长度为 0 → 两层 |
| A 类地址 /12 | 长 4 位 | 4 位子网号 → 三层 |
| B 类地址 /16 | = 默认（/16） | 长度为 0 → 两层 |
| B 类地址 /20 | 长 4 位 | 4 位子网号 → 三层 |
| C 类地址 /24 | = 默认（/24） | 长度为 0 → 两层 |
| C 类地址 /28 | 长 4 位 | 4 位子网号 → 三层 |

> **判定一句话：掩码长度 > 分类默认掩码长度 → 有子网。否则子网号为零长度，三层结构退化为两层。**

### 三、回答核心困惑："两层结构 IP 与运算后怎么会没有子网号"

C 类地址 `192.168.1.100`，无子网划分，掩码 `/24 = 255.255.255.0`：

```
与运算后得到 192.168.1.0
└──── 24位 ────┘└ 8位 ─┘
     网络号        主机号
```

**掩码的最后 8 位是 0，精确标记了主机号段。** 不存在一个隐藏的"子网号"字段——24 位全部是网络号，0 位是主机号。因为掩码长度 = 默认掩码长度，没从主机号中"借"走任何一位，所以子网号字段长度为零。

**对比：同一地址，掩码 /26：**

```
与运算后得到 192.168.1.64
└──── 24位 ────┘└2位┘└6位┘
     网络号      子网  主机
```

掩码比默认多了 2 位——这 2 位正是从主机号"借"来的，构成了子网号。

### 四、路由器的工作方式

```
路由器查表流程：
  目的 IP = D
  
  遍历路由表每条记录 (N, M, 下一跳):
    检查 D & M == N ?
    
    例：D = 192.168.1.100
    
    路由1: N=192.168.1.0,   M=/24 → D&M = 192.168.1.0    ✓ 匹配 (24位)
    路由2: N=192.168.1.64,  M=/26 → D&M = 192.168.1.64   ✓ 匹配 (26位)
    
    → 选最长前缀匹配：路由2（/26 > /24）
```

每条路由自带掩码，路由器只管逐条做与运算、选最长匹配。

### 五、CIDR 环境下——分割线不再在点号处

分类编址下，网络号和主机号的分割必定在字节边界（点号 `.` 处），即只有 /8、/16、/24 三种默认掩码。CIDR 彻底打破了这个约束——分割线可以在 32 位中的**任意位置**。

```
分类编址（classful）：                    CIDR（无分类编址）：

 192  .  168  .   1   .  100              192  .  168  .   1   .  100
└────网络号(24位)────┘└主机号┘           └────── 网络前缀(/26) ────┘└主机┘
       ↑                                         ↑
   分割线总在字节边界                      分割线可以在任意位置
   (/8, /16, /24 三种)                    (/0~/32 共33种)
```

| 对比维度 | 分类编址 | CIDR |
| :--- | :--- | :--- |
| **分割线位置** | 必定在字节边界（点号处） | 可以在 32 位中的**任意位置** |
| **掩码举例** | 只有 /8、/16、/24 三种默认掩码 | /9、/13、/19、/22、/27 ... 任意 |
| **网络号与点的关系** | 点 `.` 恰好是分割线 | 点 `.` 没有任何含义——`/19` 的边界在第三字节中间 |

```
地址: 192.168.1.100 / 19

二进制切分（19位前缀）：
  11000000 . 10101000 . 00000001 . 01100100
  └──────── 19 位网络前缀 ────────┘└─ 13位主机 ─┘

掩码: 255.255.224.0
  11111111 . 11111111 . 11100000 . 00000000
```

**分割线在第 19 位——第三个字节的内部。** 点 `.` 只是书写习惯，与分割线位置无关。

#### "子网号"概念在 CIDR 中消失

```
分类编址 + 子网划分：                   CIDR：
  网络号 . 子网号 . 主机号              网络前缀 / 主机号
  三个层次，内外视角不同                一个层级，N 位就是 N 位
```

CIDR 不再区分"哪几位是网络号、哪几位是子网号"——统一叫网络前缀。

### 六、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "A 类 / B 类 / C 类地址没有子网掩码" | 错——每条链路上都有掩码，分类地址默认掩码分别是 /8、/16、/24 |
| "子网号是 IP 地址里一个独立字段" | 错——子网号是网络前缀中超出默认掩码的那部分，不是独立字段 |
| "外部路由器需要知道内部子网划分" | 错——外部只看网络前缀，子网对外透明（路由聚合） |
| "掩码 255.255.255.0 意味着一定有子网" | 错——对 C 类这就是默认掩码，子网号长度为零 |
| "同一 IP 地址在无子网和有子网环境中与运算结果不同" | 对——但这是**同 IP 不同掩码**，掩码不同结果当然不同 |

> **省流：** 掩码的 1 的数量就是网络前缀的位数。掩码 = 默认掩码 → 子网号字段长度为零（两层）；掩码比默认长 → 多出的位数即子网号（三层）。路由器不关心"两层还是三层"——它只做 IP & 掩码 → 查最长前缀匹配。在 CIDR 中，分割线不再在点号 `.` 处——`/19` 的边界在第三字节中间，与那个 `.` 毫无关系。统一叫"网络前缀"即可。

## Q17 · IP 地址与 MAC 地址的本质区别——谁是主机的"固有属性"

> IP 地址和 MAC 地址，哪个是主机与生俱来的？

**答：MAC 地址是主机的固有属性（出厂烧录在网卡 ROM），IP 地址是临时分配的逻辑地址（DHCP 分配或手动配置）。主机启动时还没有 IP，靠 MAC 地址向 DHCP 服务器申请获得 IP。**

### 一、核心对比

| 对比维度      | IP 地址                     | MAC 地址               |
| :-------- | :------------------------ | :------------------- |
| **来源**    | DHCP 分配 / 手动配置，主机启动时获得    | 出厂烧录在网卡 ROM，**固有属性** |
| **层次**    | 网络层，逻辑地址                  | 数据链路层，物理地址           |
| **可变性**   | 换网络就变（移动主机 IP 随之变化）       | 不随网络变化（换网卡才变）        |
| **长度**    | 32 位（IPv4）/ 128 位（IPv6）   | 48 位                 |
| **唯一性范围** | 全球唯一（公网 IP）/ 私网内唯一（私网 IP） | 广播域内唯一（可跨网段重用）       |
| **类比**    | 收件地址——搬了家地址就变了            | 身份证号——跟一辈子           |

### 二、主机启动时只有 MAC，没有 IP

```
主机启动 → 还没有 IP
    │
    ▼
① 主机用自己的 MAC 地址广播 DHCP Discover
   （源MAC = 自己，目的MAC = FF-FF-FF-FF-FF-FF）
   
② DHCP 服务器收到 → 分配一个 IP → 用 DHCP Offer 回复
   （通过 MAC 地址定位该主机）

③ 主机接受 → IP 地址配置完成
   （此时主机才同时拥有 IP 和 MAC）
```

> **MAC 地址是主机在网络中的"身份证"——出厂就有，永不改变。IP 地址是"通信地址"——到了哪个网络就配置哪个网络的 IP。**

### 三、这解释了为什么 ARP 是必要的

```
A(192.168.1.2) 要发包给 B(192.168.1.5)：

A 知道 B 的 IP（逻辑地址），但不知道 B 的 MAC（物理地址）
    │
    ▼
① A 广播 ARP 请求："谁的 IP 是 192.168.1.5？请告诉我你的 MAC"
   目的MAC = FF-FF-FF-FF-FF-FF（广播）
   
② B 收到 → "我的 IP 是 192.168.1.5，MAC 是 xx:xx:xx:xx:xx:xx"
   单播回复给 A

③ A 拿到 B 的 MAC → 封装帧 → 发送
```

**IP 是临时的、逻辑的，真正在链路上发帧必须靠 MAC。** 每次通信前要发 ARP 请求把 IP 翻译成 MAC——这正是因为 IP 地址不像 MAC 那样烧死在硬件上。

### 四、与 Q14 的联动：转发过程中两者各司其职

```
跨网络通信（A → 服务器 S）：

离开 A 时：
  源IP=A的IP, 目的IP=S的IP         ← IP 端到端不变（普通转发）
  源MAC=A的MAC, 目的MAC=网关的MAC   ← MAC 逐跳变化

路由器为什么只改 MAC 不改 IP？
  → IP 是逻辑目标（地址），全程不变才能到达终点
  → MAC 是物理下一跳（身份证），每过一跳都要换新的下一跳
```

### 五、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "主机出厂就有 IP 地址" | 错——主机只有 MAC 是出厂烧录的，IP 通过 DHCP 或手动配置获得 |
| "MAC 地址全球唯一" | 错——MAC 地址只在同一广播域内唯一，跨网段可重用（见 Q10） |
| "IP 地址永远不会变" | 错——换个网络 IP 就变（除非是静态配置） |
| "ARP 协议用 IP 查 MAC 说明 IP 更底层" | 错——MAC 才是链路层的物理地址，IP 是网络层的逻辑地址 |
| "没有 IP 就不能通信" | 错——纯二层局域网内用 MAC 即可通信（但互联网通信必须有 IP） |

> **省流：** MAC 地址出厂烧录在网卡 ROM，是主机的固有属性（物理地址）；IP 地址由 DHCP 分配或手动配置，是临时的逻辑地址。主机启动时只有 MAC 没有 IP——用 MAC 广播 DHCP 请求获取 IP。ARP 之所以必要，正是因为 IP 不像 MAC 那样烧死在硬件上：每次通信前需要 ARP 把逻辑 IP 翻译成物理 MAC。

## Q18 · "公网不可路由"——私网地址为什么不能走公网

> 大家都说 192.168.x.x 这些私网地址在公网上不可路由，这是什么意思？

**答："公网不可路由" = 公网路由器不认识私网地址，路由表里没有去往这些地址的路由，包到了公网路由器就被丢弃。这是 RFC 1918 的刻意设计——私网地址只在局域网内有意义。**

### 一、私网地址范围

| 地址段 | CIDR | 可用 IP 数 | 典型场景 |
| :--- | :--- | :---: | :--- |
| 10.0.0.0 ~ 10.255.255.255 | 10.0.0.0/8 | ~1677 万 | 大型企业/数据中心 |
| 172.16.0.0 ~ 172.31.255.255 | 172.16.0.0/12 | ~104 万 | 中型网络 |
| 192.168.0.0 ~ 192.168.255.255 | 192.168.0.0/16 | ~6.5 万 | 家用路由器/小网络 |

### 二、"不可路由"的真正含义

```
公网路由器 R 收到一个包，目的 IP = 192.168.1.100：

R 查路由表：
  目的网络        下一跳
  1.2.3.0/24      R2
  8.8.8.0/24      R3
  0.0.0.0/0       网关      ← 默认路由
  
  192.168.x.x  →  查不到！没有这条路由 → 丢弃
```

**公网路由器的路由表中没有私网地址的路由。** 不是因为技术上天生的障碍，而是所有 ISP 都遵守约定——不在公网路由表中添加私网前缀。

### 三、如果强行让私网地址走公网会怎样

```
A(192.168.1.2) → 目的 IP = 192.168.1.3

站在 A 自己看来：192.168.1.3 就在本地局域网 → 直接 ARP 即可
站在公网路由器看来：全世界可能有几千万个 192.168.1.3 → 根本不知道找哪一个

问题：私网地址不具有全球唯一性。你的 192.168.1.3 和别人家的 192.168.1.3 在公网上无法区分。
```

> **根本原因不是"技术上做不到"，而是"私网地址不唯一，路由表无法区分"——同一个 192.168.1.x 全球可能有上亿个，路由器不知道该转发给谁。**

### 四、不可路由 ≠ 无法上网——NAT 是桥梁

```
内网 192.168.1.2 访问公网 8.8.8.8：

出去的包：
  源 IP = 192.168.1.2 → 经 NAT → 源 IP = 公网 IP(1.2.3.4)
  ↑ 私网地址被替换为公网地址后再上路

回来的包：
  目的 IP = 1.2.3.4 → 经 NAT 反向查表 → 目的 IP = 192.168.1.2
  ↑ 公网只看到了 1.2.3.4，不知道内网有 192.168.1.2
```

**NAT 充当了私网和公网之间的翻译。** 出去的包将私网源地址替换为公网地址，回来的包将公网目的地址替换回私网地址。公网从头到尾不知道私网的存在。

### 五、与 Q14、Q15 的联动——这就是 NAT 存在的根本原因

```
为什么需要 NAT（Q14）？
  → 因为私网地址公网不可路由（Q18），必须把 192.168.x.x 换成公网 IP 才能上路

为什么回包要先 NAT 再查路由表（Q15）？
  → 外网回包目的 IP 是公网 IP(1.2.3.4)，NAT 转换成 192.168.1.2
    之后查路由表 → 找到内网接口 → 转给你的电脑
    如果不先做 NAT，路由器看到目的 IP=1.2.3.4 就是自己，不会转发
```

```
                     Q18（本问）
                        │
               私网地址公网不可路由
                        │
              ┌─────────┴─────────┐
              ↓                   ↓
       Q14（为什么 NAT 改 IP）   Q15（NAT 与路由表的先后）
       把私网 IP 换成公网 IP      回包时先 NAT 还原再查路由表
```

### 六、408 常考

| 场景 | 结论 |
| :--- | :--- |
| ISP 路由器收到目的 IP = 192.168.1.x 的包 | 丢弃——公网无此路由 |
| 两个不同公司的内网都用 192.168.1.0/24 | 可以，互不影响——各自只在本地有效 |
| 内网 192.168.1.2 ping 公网服务器 8.8.8.8 成功 | 靠 NAT——出去的包源 IP 被换成了公网地址 |

> **省流：** "公网不可路由" = ISP 路由器不维护私网地址的路由，收到私网目的地址的包直接丢弃。根本原因不是技术做不到，而是私网地址不具全球唯一性（全球可能有几亿个 192.168.1.x），路由表无法区分该发给谁。NAT 通过在出口路由器把私网源 IP 替换为公网 IP 来解决——私网上网，全靠 NAT。

## Q19 · IP 地址的源/目的限制——谁能做源、谁能做目的

> 哪些 IP 地址可以做目的 IP 但不能做源 IP？哪些可以做源 IP 但不能做目的 IP？

**答：广播地址和组播地址只能做目的 IP（代表一群人），不能做源 IP（发送方必须是具体主机）。0.0.0.0 只能做源 IP（"我还没地址"的临时声明），不能做目的 IP（"发给那个没有地址的人"毫无意义）。网络地址（主机号全 0）两者都不能——它压根不是主机地址。**

### 一、总览——源/目的四象限

```
                可以做目的IP
                 │
    0.0.0.0      │    255.255.255.255
    (源√ 目×)    │    定向广播地址
                 │    组播地址(224-239)
                 │    (源× 目√)
                 │
    ─────────────┼────────────── → 可以做源IP
                 │
    网络地址      │    普通单播地址
    (主机号全0)   │    环回地址(127)
    (源× 目×)    │    (源√ 目√)
```

### 二、只能做目的 IP、不能做源 IP

| 地址                               | 类型             | 为什么不能做源 IP                                 |
| :------------------------------- | :------------- | :----------------------------------------- |
| **255.255.255.255**              | 有限广播地址         | 代表"本网络所有主机"——不是具体主机，发包的必须是具体主机，不可能说"我是所有人" |
| **定向广播地址**<br>如 192.168.1.255/24 | 定向广播地址（主机号全 1） | 同理——代表"这个网络中的所有主机"，是一个集合，不是某一台主机           |
| **224.0.0.0 ~ 239.255.255.255**  | D 类组播地址        | 组播地址标识一个"组"，不是一个发送者。组播源 IP 仍是单播地址          |

> **记法：广播和组播都是"喊一群人"——接收方可以是群体，但发送方必须是一个具体的主机。**

### 三、只能做源 IP、不能做目的 IP

| 地址          | 场景                    | 为什么不能做目的 IP                                                            |
| :---------- | :-------------------- | :--------------------------------------------------------------------- |
| **0.0.0.0** | DHCP Discover 中作为源 IP | 主机尚未获得 IP 时，源地址填 0.0.0.0 表示"我还没有地址"。作为目的地址毫无意义——"发给那个还没有 IP 的主机"，根本找不到 |

> **0.0.0.0 是"我现在没有身份"的临时声明——只有作为发送方说"我还不知道自己是谁"时才有意义。**

### 四、既能做源又能做目的

| 地址                  | 说明               |
| :------------------ | :--------------- |
| **普通单播地址**（公网/私网）   | 正常的通信双方          |
| **127.x.x.x**（环回地址） | 本机发给自己——源和目的都是自己 |

### 五、两者都不能

| 地址 | 类型 | 为什么 |
| :--- | :--- | :--- |
| **网络地址**（主机号全 0）<br>如 192.168.1.0/24 | 网络标识 | 它标识"这个网络"而不是任何一个主机——既不能作为发送者也不能作为接收者 |

### 六、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "广播地址可以做源 IP" | 错——广播/组播只能做目的，不能做源 |
| "0.0.0.0 可以作为目的 IP" | 错——0.0.0.0 只在 DHCP 请求中做源 IP，表示"本主机未获得 IP" |
| "组播地址可以做源 IP" | 错——组播源必须是单播地址（具体主机） |
| "网络地址可以分配给主机" | 错——主机号全 0 是网络标识，不可用于主机 |
| "127.0.0.1 不能做源 IP" | 错——环回地址源和目的都可以是 127.x.x.x |

> **省流：** 广播/组播→只目的不源（群体可收、个体才发）；0.0.0.0→只源不目的（还没名字、收不到信）；网络地址→都不行（那是路牌不是住户）；普通单播/环回→都可以。

## Q20 · 路由器如何找到下一跳——IP 不变，MAC 逐跳改变

> 在不考虑 NAT 的情况下，IP 数据报首部的源地址和目的地址都不会变化——目的地址帮助路由器进行路由选择。那么路由器怎么确定下一跳的地址？记忆中还有"目的地址改为下一跳地址、源地址改为当前路由器地址"的说法——这到底是怎么回事？

**答：下一跳的 IP 来自路由表（用目的 IP 做最长前缀匹配查到），下一跳的 MAC 来自 ARP（用下一跳 IP 查到）。你记忆中的"地址逐跳改变"发生在 MAC 帧头，不是 IP 首部——IP 全程不变、MAC 每跳重写。**

### 一、路由器找下一跳的全过程

```
路由器 R1 收到包，目的 IP = 10.0.0.5：

① 查路由表（用目的 IP 匹配）：
   ┌────────────────┬────────────┬──────────┐
   │  目的网络       │  下一跳 IP  │  出接口   │
   ├────────────────┼────────────┼──────────┤
   │ 10.0.0.0/8     │  R2 的 IP   │  eth1    │  ← 最长前缀匹配！
   └────────────────┴────────────┴──────────┘

   查到：下一跳 = R2 的 IP，出接口 = eth1

② 查 ARP 表（用下一跳 IP 查 MAC）：
   R2 的 IP → R2 的 MAC 地址
   （如果 ARP 表没有 → 发 ARP 请求广播获取）

③ 重写帧头，从 eth1 发出：
   源MAC = R1的eth1 MAC, 目的MAC = R2的MAC
   源IP  = A的IP（不变！）,  目的IP  = 10.0.0.5（不变！）
```

**路由表回答"走哪个 IP"，ARP 回答"那个 IP 的 MAC 是什么"。两层协作，各司其职。**

### 二、你记忆中的"地址逐跳改变"——那是 MAC 帧头

```
源主机 A ──→ R1 ──→ R2 ──→ 目的主机 B

离开 A 时的帧：
  ┌──────────────────────────────────┐
  │ 源MAC = A的MAC                    │  ← MAC头，到下一跳就换
  │ 目的MAC = R1的MAC                 │
  ├──────────────────────────────────┤
  │ 源IP = A的IP                     │  ← IP头，全程不变！
  │ 目的IP = B的IP                   │
  └──────────────────────────────────┘

离开 R1 时的帧：
  ┌──────────────────────────────────┐
  │ 源MAC = R1的MAC         ← 换了！  │
  │ 目的MAC = R2的MAC       ← 换了！  │
  ├──────────────────────────────────┤
  │ 源IP = A的IP           ← 不变！   │
  │ 目的IP = B的IP         ← 不变！   │
  └──────────────────────────────────┘

离开 R2 时的帧：
  ┌──────────────────────────────────┐
  │ 源MAC = R2的MAC         ← 又换了！│
  │ 目的MAC = B的MAC        ← 又换了！│
  ├──────────────────────────────────┤
  │ 源IP = A的IP           ← 不变！   │
  │ 目的IP = B的IP         ← 不变！   │
  └──────────────────────────────────┘
```

**你记忆中"目的地址改为下一个地点的地址，源地址改为当前路由器的地址"——完全正确，但它描述的是 MAC 帧头的源/目的 MAC，不是 IP 首部的源/目的 IP。**

### 三、为什么 IP 不变、MAC 必须变

```
IP 不变的原因：
  IP 是逻辑地址，提供端到端的全局标识。路由器需要原来的目的 IP
  来查路由表——如果把目的 IP 改成了下一跳的 IP，路由器就没法知道
  最终目标是谁了。IP 是整个转发链路的核心决策依据。

MAC 必变的原因：
  MAC 是物理地址，只在当前链路段有意义。A 的 MAC 出了 LAN1 就
  毫无意义——R2 在另一个网络里，根本不认识 A 的 MAC。每跳必须
  重写为当前链路的源 MAC（发送方）和下一跳的目的 MAC（接收方）。
```

### 四、与 Q13、Q14、Q17 的联动

```
Q13（路由概念）：路由表用目的IP匹配 → 输出下一跳IP
                   ↑
Q20（本问）：路由表给出下一跳IP → ARP查MAC → 帧头发送
                   ↑
Q14（转发规则）：IP不变、MAC变 ← 正是本问的结论
                   ↑
Q17（IP vs MAC）：ARP之所以必要，就是因为IP和MAC各自独立
```

### 五、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "路由器把目的 IP 改为下一跳 IP 后发出" | 错——目的 IP 全程不变，变的是帧头的目的 MAC |
| "路由器用源 IP 查路由表" | 错——路由表用 **目的 IP** 做最长前缀匹配 |
| "路由器只需要路由表，不需要 ARP" | 错——路由表给下一跳 IP，ARP 把 IP 翻译成 MAC，两者缺一不可 |
| "源 IP 每跳改成路由器出接口 IP" | 错（普通转发下）——源 IP 也不变，只有 NAT 才改源 IP |
| "下一跳 MAC 直接从路由表获取" | 错——路由表只有下一跳 IP，MAC 来自 ARP 表或 ARP 请求 |

> **省流：** 路由器查路由表（目的 IP 匹配 → 下一跳 IP），再查 ARP 表（下一跳 IP → 下一跳 MAC），然后重写帧头发出去。IP 首部的源/目的 IP 全程不变——路由器用目的 IP 选路，目的 IP 改了就没法选路了。你记忆中的"地址逐跳改变"是 MAC 帧头：源 MAC 和目的 MAC 每跳重写，描述的是当前链路段"谁发给谁"。IP 管全局，MAC 管局部。

## Q21 · 边界路由器看到私网地址——丢弃还是转换？

> LAN 内部都是私有地址，主机向外发送 IP 数据报经过边界路由器时，源 IP 是私网地址——边界路由器是直接丢弃不转发，还是怎么处理？

**答：边界路由器不会丢弃私网发出的包——它会在转发前做 SNAT，把源私网 IP 换成自己的公网 IP，然后才发出去。丢弃私网地址的包是公网核心路由器做的事（收到目的地址为私网的包就丢），不是边界路由器对内部主机做的事。**

### 一、两个路由器，两种处理

```
LAN 内部                         互联网
  │                                │
  ├─ 主机 A(192.168.1.5)           ├─ 服务器 S(8.8.8.8)
  ├─ 主机 B(192.168.1.6)           ├─ 公网路由器 R3
  │                                │
  └─ Router 2(边界路由器) ─────────┘
      内网口: 192.168.1.1
      公网口: 1.2.3.4
```

| 场景 | 哪个路由器 | 看到私网地址怎么做 |
| :--- | :--- | :--- |
| **内部主机发往外网** 包源 IP = 192.168.1.x | Router 2（边界） | **SNAT 替换源 IP → 1.2.3.4 → 转发** |
| **公网核心路由器收到** 包目的 IP = 192.168.1.x | 公网路由器 R3 | **查不到路由 → 丢弃**（Q18） |

**边界路由器是私网的"出口翻译官"，公网核心路由器是私网的"门卫"。角色不同，处理不同。**

### 二、为什么边界路由器不能直接丢弃

```
如果 Router 2 直接丢弃源 IP 为私网的包：
  → 内网所有主机永远无法访问互联网
  → 局域网变成一个孤岛
  → 这显然不是现实
```

你上网的每一步都是边界路由器在做 NAT，不是在做丢弃。

### 三、那"私有地址不可路由"到底说的是什么

说的是**公网上的路由器不转发目的地址为私网的包**——它在公网侧无路由可查：

```
公网路由器 R3 的视角：
  → 收到包，目的 IP = 192.168.1.x
  → 查路由表：没有去往 192.168.0.0/16 的路由
     （遵守 RFC 1918，ISP 不向公网通告私网路由）
  → 丢弃
```

**但 Router 2 是边界路由器，它在私网侧有直连路由，在公网侧有公网 IP——它做的是翻译（SNAT），不是路由。**

### 四、完整流程

```
内网主机 A(192.168.1.5) 访问服务器 S(8.8.8.8)：

A 发出包：
  源IP = 192.168.1.5, 目的IP = 8.8.8.8
       │
       ▼
Router 2 收到：
  ① 查路由表 → 目的IP 8.8.8.8 匹配默认路由 → 知道能出去
  ② 做 SNAT → 源IP 从 192.168.1.5 替换为 1.2.3.4（Router 2 的公网 IP）
  ③ 发出去
       │
       ▼
  此时包变为：
  源IP = 1.2.3.4, 目的IP = 8.8.8.8  ← 私网地址已消失！
       │
       ▼
公网路由器们 → 正常转发（全程看到的是 1.2.3.4，不知道 192.168.1.5 存在）
       │
       ▼
S 回复：
  源IP = 8.8.8.8, 目的IP = 1.2.3.4
       │
       ▼
Router 2 收到回包：
  ① 目的IP = 1.2.3.4 是自己的公网地址 → 上交给 IP 层
  ② 查 NAT 表 → 1.2.3.4 的映射 → 还原为 192.168.1.5
  ③ 查路由表 → 192.168.1.0/24 是直连网络 → 从 LAN 口发出
```

**公网从头到尾不知道 192.168.1.5 的存在——这正是 NAT 的设计目的。**

### 五、与 Q15、Q18 的联动

```
Q18（公网不可路由）          Q21（本问）
"公网路由器不认私网地址"     "边界路由器不丢私网包
 收到目的IP=私网→丢弃"       收到源IP=私网→NAT替换再发出"

              ↓                        ↓
           公网视角                  内网视角
              │                        │
              └────────┬───────────────┘
                       │
                  Q15（NAT 与路由表先后）
              出去：先查路由表→再 NAT
              回来：先 NAT→再查路由表
```

### 六、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "边界路由器收到私网源地址的包直接丢弃" | 错——边界路由器会做 SNAT 替换源地址后转发 |
| "私网地址在公网上完全不可路由 = 私网主机不能上网" | 错——私网上网靠 NAT 翻译，公网看不到私网地址 |
| "所有路由器看到私网地址都丢弃" | 错——边界路由器不丢（做 NAT），公网核心路由器才丢（无路由） |
| "NAT 路由器收到内网发出的包先检查源 IP 是否为私网" | 对——但检查后是做 SNAT，不是丢弃 |

> **省流：** 边界路由器 Router 2 不会丢弃内部主机的私网包——它做 SNAT 把私有源 IP 换成自己的公网 IP，然后再转发。公网核心路由器收到目的 IP 为私网的包才会丢弃（无路由）。私网不可路由 ≠ 不能上网，边界路由器充当翻译官——绝不让私有地址原样出门，但会让它换张公网"皮"再出门。

## Q22 · 路由器用什么地址——IP 还是 MAC？为什么 255.255.255.255 不转发？

> 路由器到底是用 MAC 地址还是 IP 地址？为什么受限广播 255.255.255.255 在路由器处不转发？路由器是网络层设备（用 IP），交换机和集线器是链路层/物理层设备（用 MAC 或不用地址）——这个理解对吗？

**答：路由器两层地址都使用——IP 做决策（查路由表选路），MAC 做执行（ARP 翻译后在链路上实际传帧）。255.255.255.255 不转发是刻意设计——路由器就是广播域的边界，把广播风暴锁在局域网内。集线器/交换机/路由器的层次理解完全正确。**

### 一、路由器两层地址都用

```
路由器收到一个包：

网络层（IP）：查路由表 ← 用 IP 地址选路
    │
    │  路由表找到下一跳 IP
    │
    ▼
链路层（MAC）：查 ARP 表 ← 用 MAC 地址传输
    │
    │  ARP 把下一跳 IP 翻译成 MAC
    │
    ▼
重写帧头（源MAC=自己, 目的MAC=下一跳）→ 从接口发出
```

| 层 | 做什么 | 用哪种地址 |
| :--- | :--- | :--- |
| **网络层** | 选路——决定走哪条路、下一跳是谁 | **IP 地址** |
| **链路层** | 实际发包——在当前链路上帧从谁到谁 | **MAC 地址** |

> **路由器 = 用 IP 做决策 + 用 MAC 做传输。缺一不可。**

### 二、集线器 vs 交换机 vs 路由器——层次对比

| 设备 | 工作层 | 看什么地址 | 转发依据 |
| :--- | :---: | :---: | :--- |
| **集线器 Hub** | 物理层 | 不看地址 | 信号复制到所有口（所有口共享一个冲突域） |
| **交换机 Switch** | 数据链路层 | **MAC 地址** | 查 MAC 地址表，精确转发到目标端口 |
| **路由器 Router** | **网络层** | **IP 地址**（选路）+ MAC 地址（实际发） | 查路由表找下一跳，ARP 翻译 MAC，逐跳转发 |

> **你的理解完全正确——路由器是网络层设备，骨干是 IP。交换机/集线器是链路层/物理层设备，只看 MAC 或根本不看地址。**

### 三、255.255.255.255 为什么路由器不转发

**路由器的一个核心职责就是隔离广播域。** 如果路由器转发受限广播包，一个局域网里的广播就会蔓延到所有网络——全世界的网络瞬间被广播风暴淹掉。

```
主机 A 发广播（255.255.255.255）：
  
  A ─→ 交换机（泛洪到本 LAN 所有端口）→ LAN 内所有主机收到 ✓
  │
  └─→ 路由器收到 → "这是受限广播，不转发" → 到此为止 ✗
                                              │
                                    广播域边界——路由器是墙
```

**路由器是广播域的分界线。** 交换机不隔离广播域（广播帧泛洪到所有端口），路由器隔离广播域（广播包到此被挡住）。

### 四、那"广播是怎么广播的"——广播只在本地 LAN 内

```
LAN1（广播域1）              LAN2（广播域2）
  192.168.1.0/24              10.0.0.0/24
      │                           │
  A 发 255.255.255.255            │
      │                           │
  交换机泛洪 → B,C,D 收到          │
      │                           │
  到路由器 → 挡住了，不转发 ──→ LAN2 里的 E,F 收不到
  
  LAN1 内广播 ✓ 完成
  LAN2 不受影响 ✓
```

**255.255.255.255 叫"受限广播"——被限制在当前网络内，路由器就是那道锁。** 广播只在本地广播域内有效。

### 五、受限广播 vs 定向广播

| | 255.255.255.255（受限广播） | 定向广播（如 10.0.0.255） |
| :--- | :--- | :--- |
| **范围** | 当前网络（本地广播域） | 指定网络 |
| **路由器是否转发** | **绝对不转发** | 默认不转发（可配置开启，但极危险） |
| **MAC 层对应** | FF-FF-FF-FF-FF-FF | FF-FF-FF-FF-FF-FF（到达目标网络后） |

### 六、408 常考陷阱

| 陷阱 | 正解 |
| :--- | :--- |
| "路由器只用 IP 地址不用 MAC" | 错——选路用 IP，链路上实际传帧用 MAC，两者都用 |
| "交换机隔离广播域" | 错——交换机不隔离广播域，广播帧泛洪到所有端口 |
| "255.255.255.255 路由器不转发是因为不认识这个地址" | 错——不是不认识，是刻意设计如此，路由器就是广播域边界 |
| "路由器可以转发 255.255.255.255" | 错——受限广播绝不转发 |
| "集线器用 MAC 地址转发" | 错——集线器工作在物理层，不看地址，信号复制到所有口 |

> **省流：** 路由器 = 网络层设备，用 IP 选路 + 用 MAC 传帧。交换机 = 链路层设备，只看 MAC。集线器 = 物理层设备，不看地址。255.255.255.255 不转发不是技术限制，是路由器作为广播域边界的设计职责——广播只在本地 LAN 有效，路由器就是挡住广播的那堵墙。

## Q23 · IP 数据报的两种交付方式——直接交付 vs 经由网关交付（ARP 全流程）

> 同一子网内如何直接交付（ARP 获取目的主机 MAC）？不同子网时，先发往默认网关——ARP 请求是否会被网关代替收到但不转发？整个流程中 ARP 与 IP 如何协作？

**答：交付方式由"目标 IP 是否在同一子网"决定。同一子网 → ARP 直接问目标主机 MAC → 帧发往目标主机。不同子网 → ARP 问默认网关的 MAC → 帧发往网关 → 网关拆帧后在下一跳链路上重新 ARP、重新封装帧头。ARP 广播只在当前链路有效，路由器绝不转发 ARP 请求到其他网络。**

### 一、前置判断：谁来决定走哪条路？

主机在发送 IP 数据报之前，IP 协议栈做一次纯软件判断（与 ARP、MAC 无关）：

```
目标 IP AND 本机子网掩码 == 本机 IP AND 本机子网掩码 ？
   |                                |
   是                               否
   ↓                                ↓
在同一子网                        不在同一子网
→ 直接交付                        → 间接交付（走默认网关）
```

这个判断确定的是：**我应该向谁发 ARP 请求？**

### 二、情况 1：同一子网内——直接交付

**场景**：主机 A（192.168.1.10/24）→ 主机 B（192.168.1.20/24），同一交换机下。

```
步骤 1: A 判断 B 在同一子网 → 决定"直接发"
步骤 2: A 查 ARP 缓存：IP=192.168.1.20 → MAC=?
        ├─ 缓存命中 → 跳到步骤 4
        └─ 缓存未命中 → 步骤 3
步骤 3: A 广播 ARP 请求：
        "谁是 192.168.1.20？请告诉 192.168.1.10 你的 MAC 地址"
        → B 收到（广播帧局域网内所有人都收）
        → B 单播回复："我是 192.168.1.20，MAC=BB:BB:BB:BB:BB:BB"
        → A 收到 ARP 响应，写入缓存
步骤 4: A 构造 MAC 帧：
        目的 MAC = B 的 MAC (BB:BB:...)
        源 MAC   = A 的 MAC (AA:AA:...)
        帧内封装 IP 数据报（源 IP=A，目的 IP=B）
步骤 5: A 通过网卡发出 → 交换机按目的 MAC 转发 → B 收到
```

```
  A                              B
  ↓                              ↑
  ARP请求(B的MAC?) ────────────→ (B收到,响应)
  ←─────────── ARP响应(我的MAC)
  MAC帧{目的MAC=B, 源MAC=A, IP: A→B} ──→ B收到
```

> **ARP 广播只在当前局域网内传播。B 直接单播回复给 A，整个过程完全在同一广播域内完成，无路由器参与。**

### 三、情况 2：不在同一子网——间接交付（走默认网关）

**场景**：A（192.168.1.10/24）→ 8.8.8.8（公网）。A 的默认网关 = 192.168.1.1。

#### 3.1 第一阶段：A → 默认网关（局域网内）

```
步骤 1: A 判断 8.8.8.8 不在同一子网 → 决定"走默认网关"
步骤 2: A 查 ARP 缓存：默认网关 IP=192.168.1.1 → MAC=?
        ├─ 缓存命中 → 跳到步骤 4
        └─ 缓存未命中 → 步骤 3
步骤 3: A 广播 ARP 请求：
        "谁是 192.168.1.1？请告诉 192.168.1.10 你的 MAC 地址"
        → 网关路由器收到（它的接口 IP 就是 192.168.1.1）
        → 网关单播回复："我是 192.168.1.1，MAC=GG:GG:GG:GG:GG:GG"
        → A 收到 ARP 响应，写入缓存
步骤 4: A 构造 MAC 帧：
```

```
┌───────────────────────────────────────────────────────┐
│ 目的 MAC = 网关的 MAC (GG:GG:...)  ← 链路层给网关       │
│ 源 MAC   = A 的 MAC (AA:AA:...)                        │
│ ┌───────────────────────────────────────────────────┐ │
│ │ IP 数据报：                                        │ │
│ │   源 IP   = 192.168.1.10  (A 的 IP，始终不变！)      │ │
│ │   目的 IP = 8.8.8.8       (最终目标，始终不变！)      │ │
│ └───────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

> **核心：A 发的帧，目的 MAC 是网关的 MAC，但帧内 IP 目的地址仍然是 8.8.8.8。IP 层始终不变，变的是每跳的链路层封装。**

#### 3.2 第二阶段：网关收到后的处理

```
步骤 5: 网关路由器收到帧
        → 目的 MAC = 自己 → 拆帧取出 IP 数据报
        → 目的 IP = 8.8.8.8，不是自己 → 需要转发
        → 查路由表，找到去往 8.8.8.8 的下一跳（假设是 10.0.0.2）
        → 在出接口上 ARP 问"谁是 10.0.0.2？"
        → 获取下一跳 MAC 后重新封装帧：
```

```
┌───────────────────────────────────────────────────────┐
│ 目的 MAC = 下一跳路由器的 MAC  (完全重写！)              │
│ 源 MAC   = 网关出接口的 MAC    (完全重写！)              │
│ ┌───────────────────────────────────────────────────┐ │
│ │ IP 数据报：                                        │ │
│ │   源 IP   = 192.168.1.10  ← 不变！                  │ │
│ │   目的 IP = 8.8.8.8       ← 不变！                  │ │
│ └───────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘

步骤 6: 网关发出新帧 → 下一跳路由器重复步骤 5 → ... → 最终到达 8.8.8.8
```

### 四、直接回答困惑——"ARP 是不是网关代替收到但不转发？"

#### Q1：A 发的 ARP 请求目标 IP 是 8.8.8.8 吗？

**不是。** A 发的 ARP 请求的目标 IP 是默认网关 192.168.1.1。

```
A 绝对不会 ARP 问"谁是 8.8.8.8？"
因为 8.8.8.8 不在同一子网，A 的网络层根本不会对它发 ARP。

A 做的事：
  → 发现 8.8.8.8 不在同一子网
  → 查路由表，下一跳 = 默认网关 192.168.1.1
  → ARP 问"谁是 192.168.1.1？" ← 问的是网关的 MAC，不是目标的 MAC
  → 网关自身直接响应
```

#### Q2：ARP 响应是网关"代替"目标返回的吗？

**不是"代替"。** 网关就是以自己的身份响应，因为 ARP 请求本来就是问它的 IP：

| 角色 | 动作 |
| :--- | :--- |
| A 发 ARP 请求 | "谁是 192.168.1.1？"（问的是网关自己的 IP） |
| 网关响应 | "我就是 192.168.1.1，我的 MAC 是 GG:GG..."（以自己身份回答） |

不存在"代替"——网关不是在替 8.8.8.8 回答，它就是在回答关于自己的问题。

#### Q3：网关会不会把 A 的 ARP 请求转发到公网？

**绝对不转发。** ARP 是链路层协议，ARP 请求包是广播帧（目的 MAC = FF-FF-FF-FF-FF-FF）。路由器核心职责之一就是隔离广播域——广播帧在路由器处被直接丢弃，不可能穿透到其他网络。

```
A 发的 ARP 广播 ──→ 网关收到 ──→ 到此为止
                          │
                   网关不在其他接口上转发这个广播帧
                          │
                   下一跳链路上的 ARP 是网关以自己的身份
                   重新发起的，与 A 的那次 ARP 完全独立
```

### 五、两张全链路图

#### 直接交付（同子网）：

```
  A                              B
  │                              │
  │ ARP请求(B的MAC?) ──────────→ (B收到,响应)
  │←──────── ARP响应 ──────────│
  │                              │
  │ 帧{MAC=B, IP: A→B} ────────→ B收到
  │                              │
  全程无路由器参与，ARP 一次搞定
```

#### 间接交付（跨子网）：

```
  A                    网关R1                 下一跳R2                目标B
  │                      │                      │                      │
  │ ARP:"R1的MAC?"      │                      │                      │
  │─────────────────────→│                      │                      │
  │←──ARP响应: GG:GG ──│                      │                      │
  │                      │                      │                      │
  │ 帧{MAC=R1, IP:A→B}  │                      │                      │
  │─────────────────────→│                      │                      │
  │                      │ 拆帧, 查路由表        │                      │
  │                      │ ARP:"R2的MAC?"       │                      │
  │                      │─────────────────────→│                      │
  │                      │←── ARP响应 ─────────│                      │
  │                      │                      │                      │
  │                      │ 帧{MAC=R2, IP:A→B}   │                      │
  │                      │─────────────────────→│                      │
  │                      │                      │ ...逐跳重复到B        │
  │                      │                      │                      │
  链路1的ARP ←→ 链路2的ARP ←→ 链路3的ARP ...
  每次ARP完全独立，只负责当前链路段
```

### 六、408 常考易错点

| 易错认知 | 正解 |
| :--- | :--- |
| "跨子网时，A 用 ARP 获取目标主机 B 的 MAC" | 错——A 只 ARP 获取默认网关的 MAC。B 的 MAC 对 A 完全不可见 |
| "路由器把 ARP 请求转发到下一跳网络" | 错——ARP 广播从不被路由器转发。每段链路的 ARP 是独立发起的 |
| "网关代替目标主机响应 ARP（代理 ARP）" | 两回事——普通转发中网关以自己的 IP 身份响应；代理 ARP 是网关故意冒充其他主机的 IP 回答，那是特殊场景 |
| "IP 数据报每跳会改变源/目的 IP" | 错——普通转发 IP 不变，只改 MAC。变 IP 仅 NAT 场景 |
| "A 需要知道目标 B 的 MAC 地址才能发数据" | 错——跨子网时 A 只需要默认网关的 MAC |

### 七、ARP 与 IP 的关系——一句话定位

> **IP 管"最终去哪"（端到端，始终不变），ARP 管"这一跳发给谁"（逐链路，每跳重新问）。同一子网时下一跳就是目标本身；跨子网时下一跳是网关——ARP 不关心最终目标是谁，它只负责把当前链路上下一跳的 IP 翻译成 MAC。**

> **省流：** 直接交付 = ARP 问目标 MAC → 帧直接发给目标。间接交付 = ARP 问网关 MAC → 帧发给网关 → 网关拆帧、查路由表、在新链路上重新 ARP、重写帧头发出（IP 不变，MAC 全变）。ARP 广播只在当前链路内有效，路由器不转发 ARP 请求。跨子网时，发送主机完全不知道目标主机的 MAC——它只需要知道默认网关的 MAC。

## Q24 · 子网划分的二叉树模型——聚合必须兄弟先行

> 子网划分的二叉树模型中，子网的合并（路由聚合）是否只能和兄弟节点聚合？例如 `111` 必须先和 `110` 聚合为 `11`，然后 `11` 和 `10` 聚合成 `1`，最后 `1` 与 `0` 聚合成 `/24` 网络——不能跳过中间步骤？

**答：正确。路由聚合必须沿二叉树自底向上，每次只能合并有同一父节点的兄弟节点。不能跨层级直接聚合。**

### 一、二叉树模型回顾

```
                    root (原始网络 /24)
                   /    \
          借1位   0      1
                / \    / \
  借2位       00  01 10  11
             /  \ /  \ /  \ /  \
  借3位    000 001 010 011 100 101 110 111
```

**每个非叶节点 = 其所有后代节点的地址空间之和。** 叶子节点的兄弟共享同一父节点，父节点的地址空间恰好等于两个子节点空间之和。

### 二、为什么 `111` 不能直接与 `10` 聚合？

```
尝试直接把 111 和 10 聚合：

  111 的前缀 = "111" (3位)
  10  的前缀 = "10"  (2位)

  "合并"后的地址空间 = 111xxxxx ∪ 10xxxxxx
```

这个并集**不连续**——中间缺了 `110xxxxx` 和 `0xxxxxxx` 表示的地址块：

```
地址空间（第4字节 0~255）：
├─ 0xxxxxxx  [0~127]    缺
├─ 10xxxxxx  [128~191]  有 (10)
├─ 110xxxxx  [192~223]  缺
└─ 111xxxxx  [224~255]  有 (111)

这不是一个可以用单一网络前缀表示的连续地址块
→ 无法聚合为一个路由条目
```

**聚合的本质是找公共前缀。** `111` 和 `10` 没有足够长的公共前缀（`111` 第一位是 1，`10` 第一位也是 1，但公共前缀只有 1 位——如果用 `1` 来做聚合，会把 `110` 也包含进来，而 `110` 不在集合中）。

### 三、唯一的聚合路径：兄弟先行

```
正确路径（自底向上）：

第1步：111 + 110 → 11    ← 兄弟，共享父节点 "11"
        (3位)   (3位)     (2位)

第2步：11  + 10  → 1     ← 兄弟，共享父节点 "1"
        (2位)   (2位)     (1位)

第3步：1   + 0   → root  ← 兄弟，共享父节点 root
        (1位)   (1位)     (/24)
```

```
root (/24)
  ├─ 0
  └─ 1 ─┬─ 10
         └─ 11 ─┬─ 110 ───┐
                 └─ 111 ─┘  ← 第1步：兄弟聚合

  第2步：10 + 11 → 1
                      ──┐
  第3步：0 + 1 → /24    ├── 自底向上逐层归并
                    ────┘
```

### 四、用 CIDR 术语表述：最长公共前缀

| 聚合对象 | 前缀1 | 前缀2 | 公共前缀 | 结果 | 是否合法 |
| :--- | :--- | :--- | :--- | :--- | :---: |
| `111` + `110` | `111` | `110` | `11`（2位相同） | `11` (/26) | 合法 |
| `11` + `10` | `11` | `10` | `1`（1位相同） | `1` (/25) | 合法 |
| `1` + `0` | `1` | `0` | （0位相同） | root (/24) | 合法 |
| `111` + `10` | `111` | `10` | `1`（1位相同） | `1` (/25) | **不合法**——`1` 会多包含 `110` |

> **核心：** 两个前缀聚合的前提是——除了最后一位不同，其余位完全相同。换句话说，两个待聚合的地址块，其前缀必须满足：一个以 `...0` 结尾，一个以 `...1` 结尾，且前面的所有位一致。这正是"兄弟节点"的二进制定义。

### 五、推广：任意 N 个子网的聚合

给定任意 N 个子网（不重叠、全覆盖），聚合回原网络的过程**始终是兄弟节点的归并**：

```
算法：
1. 从叶子节点开始，检查每对兄弟是否都在所选集合中
2. 若都在 → 用父节点替换这对兄弟（聚合一步）
3. 新父节点成为新的候选节点，继续与其兄弟检查
4. 重复直到归并为根节点
```

**兄弟关系是聚合的基本单位——路由聚合本质上就是二叉树的归并过程，不可跳步。**

### 六、回到原始问题：为什么 `011` 不能与 `10` 共存于 4 子网划分

用聚合逆向来理解"划分"：

```
假设选了 10、011、以及某两个其他节点作为 4 个子网。

从这些 4 个子网出发，反向聚合回 /24：
  - 011 的兄弟是谁？  → 010
  - 010 必须在集合中，011 才能向上聚合为 01
  - 但 010 不在 4 个子网中（配额已满）
  → 011 无法向上聚合
  → 这些节点永远聚不回 /24
  → 这个选择不满足"全覆盖"约束
  → 所以在 4 子网划分中，011 不可能与 10 共存
```

### 七、一句话总结

> **子网划分的二叉树中，聚合路径唯一——任何节点只能先与自己的亲兄弟归并为父节点，归并后父节点再与父节点的兄弟归并。这不是人为规定，而是 IP 地址的二进制前缀结构决定的：两个地址块能不引入空洞地合并，当且仅当它们除了最后一位不同外其余位全相同——这正是兄弟节点的数学定义。**

> **省流：** `111` 只能先和 `110` 聚合为 `11`，因为它们是兄弟（前缀仅最后一位不同）。`111` 和 `10` 无法直接聚合——它们的前缀公共部分只有 1 位，用 `1` 来覆盖会多出 `110` 的空间，导致不精确。路由聚合 = 二叉树的兄弟归并，不可跳过中间层级。

## Q25 · 同一子网内两台主机通信——用 IP 地址还是 MAC 地址？

> 同一子网内的两台主机通信，只用 MAC 还是只用 IP，还是都用？

**答：两层地址都用。IP 管"谁是谁"（逻辑标识），MAC 管"怎么送到"（物理传输）。以太网帧头必须填 MAC 地址（网卡只看 MAC），但 MAC 地址没有层次结构无法做路由——IP 给互联网提供可路由的逻辑地址，MAC 给以太网提供物理寻址。缺一不可。**

### 一、逐层分解——一次完整通信中每层做什么

场景：A（192.168.1.10，MAC=AA）发数据给 B（192.168.1.20，MAC=BB），同一交换机下。

```
应用层：A 想访问 B 的 Web 服务
   │  数据："GET /index.html"
   │
   ▼
传输层：封装 TCP 段
   │  源端口=随机, 目的端口=80
   │
   ▼
网络层：封装 IP 数据报
   │  源 IP=192.168.1.10, 目的 IP=192.168.1.20   ← IP 地址登场
   │
   │  A 判断：192.168.1.20 在同一子网吗？→ 是
   │  A 查 ARP 缓存/发 ARP 请求 → 获取 B 的 MAC=BB
   │
   ▼
链路层：封装 MAC 帧
   │  目的 MAC=BB, 源 MAC=AA                      ← MAC 地址登场
   │  帧内装的就是上面的 IP 数据报
   │
   ▼
物理层：网卡把帧变成电信号/光信号发出去
   │
   ▼
交换机：看目的 MAC=BB → 查 MAC 地址表 → 从端口 X 转发
   │
   ▼
B 的网卡：收到帧 → 目的 MAC 是自己 → 收下
B 的链路层：拆帧 → 取出 IP 数据报
B 的网络层：目的 IP=192.168.1.20 → 是自己 → 拆头 → 取出 TCP 段
B 的传输层：目的端口=80 → 交给 Web 服务进程
```

### 二、为什么不能只用一种地址？

#### 只有 IP 没有 MAC → 办不到

```
以太网交换机看不懂 IP 地址（交换机工作在链路层，只看帧头 MAC）。

如果帧头不写目的 MAC：
  → 交换机不知道往哪个端口转发
  → 以太网协议规定帧头必须有目的 MAC 字段
  → 没有 MAC，网卡没法发出帧——这是硬件的硬性要求
```

#### 只有 MAC 没有 IP → 不现实

```
MAC 地址是出厂烧录的 48 位编号，扁平结构，无层次。

如果只有 MAC：
  → 无法划分子网（MAC 没有网络号/主机号概念）
  → 无法做路由聚合（MAC 无层次前缀）
  → 全球几十亿设备，每台一条路由表项 → 不可能

IP 的核心贡献：给 MAC 加了一层有层次结构的逻辑地址。
路由表只存网络前缀，不存每台主机的 MAC。
```

### 三、对比：同子网 vs 跨子网

| | 同子网（直接交付） | 跨子网（经网关） |
| :--- | :--- | :--- |
| **IP 源** | A 的 IP | A 的 IP（始终不变） |
| **IP 目的** | B 的 IP | 最终目标 B 的 IP（始终不变） |
| **MAC 目的** | **B 的 MAC**（ARP 问 B） | **默认网关的 MAC**（ARP 问网关） |
| **ARP 问谁** | 目标主机 B | 默认网关 |
| **帧中 IP 目的地址** | = 帧中 MAC 目的地址对应的设备 | ≠（MAC 发网关，IP 写最终目标） |

### 四、总结

| 地址类型 | 作用 | 管什么 | 对应设备 |
| :--- | :--- | :--- | :--- |
| **IP 地址** | 逻辑标识，端到端 | 源是谁、最终目的地在哪 | 路由器用 IP 选路 |
| **MAC 地址** | 物理传输，逐链路 | 当前这一跳帧从哪张网卡发到哪张网卡 | 交换机用 MAC 转发 |

> **省流：** 同子网通信，IP 和 MAC 都用。应用层知道 B 的 IP → 网络层封装 B 的 IP → ARP 把 B 的 IP 翻译成 B 的 MAC → 链路层帧头填 B 的 MAC → 网卡发出。B 收到后先看 MAC（是不是给我的）→ 再看 IP（是不是给我的）→ 都对才收下。IP 提供可路由的逻辑结构，MAC 提供物理传输的寻址能力——两层地址各司其职，缺一不可。
