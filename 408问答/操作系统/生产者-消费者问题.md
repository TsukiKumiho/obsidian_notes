# 408 | 操作系统 - 生产者-消费者问题（完整梳理）

> 信号量同步的经典范式 | 408 高频考点 | PV 操作核心应用题

---

## 一、问题描述

多个生产者进程和多个消费者进程共享一个大小为 N 的有界缓冲区（bounded buffer）。生产者向缓冲区放入产品，消费者从缓冲区取出产品。约束：

1. **缓冲区满时**，生产者必须等待
2. **缓冲区空时**，消费者必须等待
3. **对缓冲区的访问必须互斥**——同一时刻最多一个进程操作缓冲区

---

## 二、信号量方案（标准教科书实现）

### 2.1 三个信号量

| 信号量 | 初值 | 含义 | 类型 |
| :--- | :---: | :--- | :--- |
| `mutex` | 1 | 互斥访问缓冲区数据结构 | 互斥信号量（二值） |
| `empty` | N | 空闲缓冲块数量 | 计数信号量 |
| `full` | 0 | 已占用缓冲块数量 | 计数信号量 |

### 2.2 伪代码

```c
semaphore mutex = 1;      // 互斥：保护缓冲区
semaphore empty = N;      // 同步：空闲槽位数
semaphore full  = 0;      // 同步：已填充槽位数
int buffer[N];            // 循环缓冲区
int in = 0, out = 0;     // 读写指针

// ============ 生产者 ============
void producer() {
    item next_produced;
    while (1) {
        next_produced = produce_item();  // 准备产品（在临界区外）

        wait(empty);        // ① 申请一个空位（无空位则阻塞）
        wait(mutex);        // ② 进入临界区

        buffer[in] = next_produced;      // ③ 放入产品
        in = (in + 1) % N;

        signal(mutex);      // ④ 退出临界区
        signal(full);       // ⑤ 增加已用计数（唤醒可能等待的消费者）
    }
}

// ============ 消费者 ============
void consumer() {
    item next_consumed;
    while (1) {
        wait(full);         // ① 申请一个产品（无产品则阻塞）
        wait(mutex);        // ② 进入临界区

        next_consumed = buffer[out];     // ③ 取出产品
        out = (out + 1) % N;

        signal(mutex);      // ④ 退出临界区
        signal(empty);      // ⑤ 增加空位计数（唤醒可能等待的生产者）

        consume_item(next_consumed);     // 消费产品（在临界区外）
    }
}
```

## 三、核心辨析：同步（empty/full）与互斥（mutex）的职责分离

```
生产者进入缓冲区的两个条件：
    ├── wait(empty) → "有没有空位可以放？"     ← 资源可用性（同步）
    └── wait(mutex) → "缓冲区现在有没有人动？"  ← 数据结构安全（互斥）

两个条件独立，缺一不可。
```

| 信号量 | 管什么 | 阻塞/唤醒逻辑 | 典型误解 |
| :--- | :--- | :--- | :--- |
| **empty** | 资源计数——有多少空槽 | 满 → 生产者阻塞；消费者取出 → 唤醒生产者 | "有空位就能立即放入"——错，mutex 可能还被占用 |
| **full** | 资源计数——有多少产品 | 空 → 消费者阻塞；生产者放入 → 唤醒消费者 | "有产品就能立即取出"——错，同上的互斥约束 |
| **mutex** | 互斥——缓冲区数据结构不被并发破坏 | 有人用 → 其他人排队等锁 | "只有互斥就够了"——错，还需要 empty/full 实现条件等待 |

## 四、死锁陷阱：P 操作顺序不可交换

### 4.1 正确顺序

```
生产者: wait(empty) → wait(mutex) → ... → signal(mutex) → signal(full)
消费者: wait(full)  → wait(mutex) → ... → signal(mutex) → signal(empty)
```

### 4.2 错误顺序一：先 mutex 后 empty（生产者）

```c
// 危险！缓冲区满时必死锁
void producer_wrong() {
    wait(mutex);      // 先拿到锁
    wait(empty);      // 满 → 生产者在此阻塞，持有锁不放！
    ...
}
```

```
死锁场景：
    缓冲区满（empty=0）
    P 先 wait(mutex) 成功 → mutex=0，P 持有锁
    P 再 wait(empty) → empty=-1，P 阻塞，但锁没释放！
    C 想取产品 → wait(mutex) 永远失败 → C 永远进不来
    → 死锁
```

### 4.3 错误顺序二：先 mutex 后 full（消费者）

```c
// 危险！缓冲区空时必死锁
void consumer_wrong() {
    wait(mutex);      // 先拿到锁
    wait(full);       // 空 → 消费者在此阻塞，持有锁不放！
    ...
}
```

### 4.4 死锁原因一句话

> 先拿互斥锁再申请资源，若资源不可用则持有锁阻塞——其他进程无法进入临界区释放资源，形成死循环等待。正确做法永远是：**先申请资源（empty/full），再抢锁（mutex）**。

### 4.5 signal 顺序有无影响

```c
// 两种写法都可，408 不扣分
// 写法 A：
signal(mutex); signal(full);

// 写法 B：
signal(full); signal(mutex);
```

| 写法 | 说明 |
| :--- | :--- |
| A（先 signal(mutex) 后 signal(full)） | 释放锁后立即通知消费者——消费者可能被唤醒但因锁刚释放通常能立即拿到 |
| B（先 signal(full) 后 signal(mutex)） | 先通知消费者，消费者被唤醒后仍需等待 mutex——多一次上下文切换 |

408 考试中两种写法均正确，关键在于 P 操作的顺序，signal 顺序影响性能但不影响正确性。

## 五、mutex 锁粒度：整缓冲区 vs 逐槽

| 维度 | 经典实现（整缓冲区锁） | 细粒度（逐槽锁） |
| :--- | :--- | :--- |
| **锁的对象** | 整个缓冲区 + in/out 指针 | 每个槽位独立 |
| **并发度** | 1 个进程/时刻 | 理论 N 个进程/时刻（不同槽位） |
| **实现复杂度** | 简单 | 极高——找空槽需要跨槽协调 |
| **408 考察** | 标准答案 | 不要求，作为理解题出现 |

> 经典实现中 mutex 保护的是**整个缓冲区数据结构**（数组 + in + out），不是每个槽位。即使 N 个空槽，同一时刻也只有 1 个进程能操作缓冲区。

## 六、变体与扩展

### 6.1 单生产者-单消费者

信号量方案直接适用。`mutex` 在某些实现中甚至可以省略（因为 in/out 指针不会同时被读写），但 408 考试中建议保留 mutex 以保证答案安全性。

### 6.2 多生产者-多消费者

必须保留 `mutex`——多个生产者可能同时修改 `in` 指针，多个消费者可能同时修改 `out` 指针。

### 6.3 管程实现

```c
monitor ProducerConsumer {
    condition not_full, not_empty;
    int count = 0;
    item buffer[N];
    int in = 0, out = 0;

    void insert(item x) {
        while (count == N) wait(not_full);   // while 不是 if！
        buffer[in] = x;
        in = (in + 1) % N;
        count++;
        signal(not_empty);
    }

    item remove() {
        while (count == 0) wait(not_empty);  // while 不是 if！
        item x = buffer[out];
        out = (out + 1) % N;
        count--;
        signal(not_full);
        return x;
    }
}
```

注意：管程中条件变量的 `wait` 必须是 `while` 而非 `if`——管程 signal 被唤醒后需重新检查条件（应对 Mesa 语义的虚假唤醒）。

### 6.4 与读者-写者问题的对比

| 对比维度 | 生产者-消费者 | 读者-写者 |
| :--- | :--- | :--- |
| **参与者角色** | 对称（读写各一个角色） | 不对称（读可共享，写互斥） |
| **核心矛盾** | 满/空时的条件等待 | 写者可能饥饿 |
| **信号量数量** | 3 个（mutex + empty + full） | 通常 2-3 个（mutex + wrt + readcount 保护） |
| **死锁风险** | P 操作顺序错 → 死锁 | 读者优先级不当 → 写者饥饿 |

## 七、408 常考辨析汇总

| 判断题 | 答案 | 原因 |
| :--- | :---: | :--- |
| "生产者-消费者问题需要 3 个信号量" | √ 正确 | mutex（互斥）、empty（空位计数）、full（产品计数），缺一不可 |
| "`empty` 和 `mutex` 可以合并为一个信号量" | × 错误 | empty 计数空槽（0~N），mutex 只取 0/1——语义和取值域完全不同，不可合并 |
| "生产者先 wait(mutex) 再 wait(empty) 是正确的" | × 错误 | 缓冲区满时持有锁阻塞 → 死锁 |
| "消费者先 signal(empty) 再 signal(mutex) 是正确的" | √ 正确 | signal 顺序不影响正确性，只影响调度效率 |
| "用管程实现时，条件判断用 `if` 即可" | × 错误 | 必须用 `while`——被唤醒后条件可能不再满足（Mesa 语义） |
| "单生产者单消费者时可以省略 mutex" | √ 理论正确 | in/out 指针不会并发修改，但 408 考试建议保留 |
| "mutex 保护的是每个缓冲槽" | × 错误 | mutex 保护的是整个缓冲区数据结构（数组 + 指针），不是逐槽保护 |

## 八、答题模板（408 大题速查）

遇到生产者-消费者问题时，按以下步骤写出答案：

```
步骤 1: 声明信号量（类型 + 初值 + 含义）
    semaphore mutex = 1;   // 互斥
    semaphore empty = N;   // 空位
    semaphore full = 0;    // 产品

步骤 2: 生产者流程
    produce item → wait(empty) → wait(mutex) →
    put item → signal(mutex) → signal(full)

步骤 3: 消费者流程
    wait(full) → wait(mutex) → take item →
    signal(mutex) → signal(empty) → consume item

步骤 4: 关键检查点
    - wait(empty) 在 wait(mutex) 之前 √
    - wait(full)  在 wait(mutex) 之前 √
    - produce_item() 在临界区外 √
    - consume_item() 在临界区外 √
```

## 九、一句话总结

> 生产者-消费者 = **2 个计数信号量（empty/full）管"条件等待"** + **1 个互斥信号量（mutex）管"并发安全"**。死锁的唯一风险在于 P 操作顺序——永远先申请资源（empty/full），再抢锁（mutex）。empty 和 mutex 职责不同不可互换：前者管"有没有空位"（资源计数），后者管"能不能动数据结构"（互斥）。

> **省流：** 三个信号量，两个维度——同步（empty/full 管资源可用性）+ 互斥（mutex 管数据结构安全）。P 操作顺序记死：先资源后锁（wait(empty) → wait(mutex)），反过来必死锁。mutex 锁整缓冲区而非逐槽。
