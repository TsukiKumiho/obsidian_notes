## Q1 · 系统调用 vs 系统命令

> 每个系统调用对应着内核中实现某个特定功能的子程序，那这么是不是就意味着，系统调用就和系统的命令一样？

**答：不是一回事。**

### 一、层次关系

```text
用户层     系统命令（cp, ls, mkdir, ...）  ← 可执行程序，运行在用户态
            │
            ▼
库函数层    C 库（fopen, printf, ...）      ← 封装系统调用，仍在用户态
            │
            ▼
───────  陷入/自陷指令（trap）───────        ← 从用户态切换到内核态
            │
            ▼
内核层     系统调用（open, read, write, ...）  ← 内核子程序，运行在核心态
```

### 二、核心区别

| 对比维度 | 系统调用 | 系统命令 |
| :--- | :--- | :--- |
| **运行态** | 核心态（内核态） | 用户态 |
| **本质** | 内核中实现特定功能的**子程序** | 操作系统提供给用户的**可执行程序** |
| **谁调用** | 用户程序/库函数通过陷入指令触发 | 用户通过终端/Shell 直接输入 |
| **入口方式** | 软中断 / trap / syscall 指令 | Shell 解析命令名 → 查找可执行文件 → fork+exec |
| **数量** | 固定，由 OS 内核决定（Linux 约 300+ 个） | 可任意添加（用户安装新程序即增加新命令） |
| **一对一？** | — | ❌ **一条命令通常调用多个系统调用** |

### 三、典型例子：`cp file1 file2` 内部

| 步骤 | 对应的系统调用 | 做什么 |
| :---: | :--- | :--- |
| ① | `open("file1", O_RDONLY)` | 打开源文件，获得 fd1 |
| ② | `open("file2", O_WRONLY \| O_CREAT)` | 打开/创建目标文件 |
| ③ | `read(fd1, buf, n)` | 从源文件读数据 |
| ④ | `write(fd2, buf, n)` | 写入目标文件 |
| ⑤ | 循环 ③④ 直到读完 | — |
| ⑥ | `close(fd1)` / `close(fd2)` | 关闭文件 |

> 一条 `cp` = 至少 4 种不同的系统调用，每种调用多次。**408 常考干扰项："一个系统命令对应一个系统调用"——❌ 错。**

### 四、一句话总结

> 系统调用是内核提供的"原语"（原子功能单元），系统命令是用户程序用这些原语"拼装"出来的完整工具。命令可被用户安装、删除、替换；系统调用是内核编译时就定死的，用户无法增减。

## Q2 · 系统调用的发生位置

> 系统调用的调用者运行在用户态中，而被调用者运行在内核态中，那么系统调用到底属于在哪里发生的事件？他是不是也可以称作，在用户态发生过的事件？

**答：✅ 可以。系统调用是跨越用户态和内核态的边界事件，它的"发起"在用户态发生，"处理"在内核态完成。2012 年真题原文："系统调用可以在用户态发生，随后通过中断或陷阱机制转入内核态。"**

### 一、2012 年真题原文（关键证据）

> "系统调用：用户程序在用户态执行时，如果想要请求操作系统提供服务（如读写文件、创建进程等），就会主动发起系统调用。因此，**系统调用可以在用户态发生**，随后通过中断或陷阱机制转入内核态。"

这是 408 真题对系统调用的**官方定性**——"在用户态发生"不是错误表述，而是被真题正面确认的正确说法。

### 二、"在用户态发生"指的是什么

| 阶段 | 发生位置 | 内容 |
| :--- | :---: | :--- |
| **发起阶段** | 用户态 ✅ | 用户程序执行陷入指令（`int 0x80` / `syscall`），主动请求内核服务。这是系统调用的**开始** |
| 切换阶段 | 硬件自动 | CPU 保存现场（PC、PSW）、切换栈指针、加载中断向量表入口 |
| **处理阶段** | 内核态 | 内核中的服务子程序执行（如 `sys_write`、`sys_open`），完成实际 I/O 操作 |
| 返回阶段 | 硬件自动 | 恢复现场，CPU 切回用户态，用户程序继续执行 |

**"系统调用在用户态发生"＝ 系统调用的发起动作（陷入指令）在用户态执行。**

### 三、完整理解：系统调用是跨边界事件

```text
用户态 ─────── 系统调用的"发起"（执行陷入指令）─────── 用户态发生
              │
              ▼  trap / syscall 指令
─────── 硬件切换 ────────────────────────────── 边界
              │
              ▼
内核态 ─────── 系统调用的"处理"（执行内核服务子程序）─── 内核态完成
```

| 表述 | 408 判定 | 真题依据 |
| :--- | :---: | :--- |
| "系统调用**在用户态发生**" | ✅ **正确** | 2012 真题原文 |
| "系统调用**最终在内核态执行**" | ✅ **正确** | 服务子程序运行于核心态 |
| "系统调用仅在用户态发生" | ❌ 错误 | 处理阶段在内核态 |
| "系统调用仅在核心态发生" | ❌ 错误 | 发起动作在用户态 |

### 四、易混淆概念辨析

| 事件 | 408 归入 | 辨析要点 |
| :--- | :--- | :--- |
| **系统调用** | 发起→用户态，处理→内核态 | 跨边界；真题确认"可在用户态发生" |
| **陷入指令（trap）的执行** | 用户态 | 该指令本身不含特权操作，在用户态执行 |
| **内核服务子程序执行** | 内核态 | 这才是特权操作的实际执行 |
| **C 库函数（如 printf）** | 用户态 | 全程用户态（内部再调用系统调用） |
| **缺页异常** | 内核态 | 非用户主动发起，CPU 检测到后直接转入内核态 |
| **外中断** | 内核态 | 硬件信号触发，CPU 响应后在内核态处理 |

### 五、一句话总结

> **408 真题的定调：系统调用"在用户态发生"是指用户程序在用户态主动执行陷入指令、发起服务请求这一动作；处理阶段转入内核态。因此"系统调用在用户态发生"和"系统调用在内核态执行"两句都对——前者指发起，后者指处理，不矛盾。**

### 六、我之前的错误

之前我回答"不能称为在用户态发生的事件"是**错误的**。这道真题明确说明："系统调用可以在用户态发生"。我混淆了"系统调用的服务逻辑执行于内核态"和"系统调用能否说在用户态发生"这两个命题——前者正确，后者也不假，因为"发生"可以指"发起"这个动作（这正是 408 真题使用的语义）。

## Q3 · 不能在用户态执行的指令/事件

### 一、特权指令（只能在核心态执行）

| 类别 | 具体指令/操作 | 为什么必须在内核态 |
| :--- | :--- | :--- |
| **I/O 指令** | `IN`, `OUT`, `INS`, `OUTS`（x86 端口读写） | 直接操作外设，用户程序绕过 OS 会破坏设备管理 |
| **停机指令** | `HLT`（处理器暂停） | 停止 CPU 是全局行为，不能由单个用户进程决定 |
| **中断控制** | `CLI`（关中断）、`STI`（开中断） | 中断标志位 IF 是全局资源，用户进程不能屏蔽外部中断 |
| **PSW 特权位修改** | 修改程序状态字中的特权级别、中断屏蔽位等 | 用户进程不能自行提权 |
| **控制寄存器** | 读/写 `CR0`–`CR4`（x86），修改 CPU 工作模式 | 涉及分页开关、保护模式开关等系统级配置 |
| **页表基址** | 修改 `CR3`（x86）/ 页目录基址寄存器 | 切换地址空间 = 切换进程，只能是内核的权限 |
| **中断向量表** | `LIDT`（加载中断描述符表寄存器） | 篡改中断向量 = 劫持整个系统的事件响应 |
| **段表/描述符表** | `LGDT`（加载全局描述符表）、`LLDT`、修改段描述符 | 涉及内存分段机制的安全隔离 |
| **TLB 刷新** | `INVLPG`、刷新整个 TLB | 虽在某些架构上用户态可触发，但通常与页表切换绑定，属内核操作 |
| **设置系统时钟** | 修改硬件定时器/时钟芯片 | 系统时间对多任务至关重要，单进程不能改动 |
| **直接访问磁盘** | 读写磁盘控制器的寄存器端口 | 绕过文件系统的所有保护 |

### 二、在用户态发生、在内核态处理的事件

| 事件 | 发起位置 | 处理位置 | 说明 |
| :--- | :---: | :---: | :--- |
| **系统调用** | 用户态（陷入指令） | 内核态（服务子程序） | 2012 真题："可在用户态发生" |
| **缺页异常** | 用户态（访存指令触发） | 内核态（缺页处理程序） | 用户不可能自己调页 |
| **除零异常** | 用户态（除法指令触发） | 内核态（异常处理程序） | CPU 检测后自动转入内核 |
| **外中断响应** | —（硬件信号触发） | 内核态（中断服务程序） | 全程在内核态处理 |
| **DMA 操作** | —（DMA 控制器完成） | 不经过 CPU | DMA 控制器与内存直接交互 |

### 三、用户态可执行但常被误认为特权的指令

| 指令/操作 | 能否在用户态执行 | 说明 |
| :--- | :---: | :--- |
| 普通访存（`MOV`、`LOAD`、`STORE`） | ✅ | 但地址不能超出进程自己的地址空间 |
| 算术逻辑运算（`ADD`、`AND` 等） | ✅ | 普通数据处理 |
| `PUSHF` / `POPF` | ✅（受限） | 可读/写标志寄存器，但 **IF 位在用户态不能被修改**（写入无效） |
| `CPUID` | ✅ | 读取 CPU 信息，不涉及系统状态变更 |
| `RDTSC`（读时间戳计数器） | ✅ | 仅读取，不修改系统状态 |
| 修改段寄存器（`MOV DS, AX`） | ✅ | 但段选择子必须指向合法的、属于该进程的段描述符 |
| `trap` / `syscall` / `int` | ✅ | **唯一可以在用户态执行并主动进入内核态的指令类别** |

### 四、408 考题常见干扰项

| 干扰项 | 判定 | 原因 |
| :--- | :---: | :--- |
| "用户程序可以执行 I/O 指令" | ❌ | I/O 是特权指令 |
| "用户程序可以开/关中断" | ❌ | CLI/STI 是特权指令 |
| "用户程序可以直接修改页表" | ❌ | 页表在内核空间，用户不可写 |
| "系统调用完全在内核态发生" | ❌ | 发起在用户态（2012 真题） |
| "系统调用完全在用户态发生" | ❌ | 处理在内核态 |
| "trap 指令不能由用户程序执行" | ❌ | 恰恰相反——陷入指令**就是**给用户程序用的入口 |
| "用户态程序可以直接访问 I/O 端口" | ❌ | 端口读写 = 特权指令 |

### 五、一句话记忆口诀

> **用户态做计算、访自己内存、发系统调用；其余一切——I/O、关中断、改页表、改控制寄存器——全是内核态的事。**

## Q4 · I/O 软件层次与 I/O 生命周期

> 一次完整的 I/O 操作是不是包含 I/O 请求、I/O 进行、I/O 完成三个阶段？从操作系统的视角看，各阶段发生了什么？

**答：是。一次完整的 I/O 操作从 OS 视角看确实包含这三个阶段，但 OS 教科书将其展开为更细的"I/O 软件层次"——三个阶段的背后是四个软件层的分工协作。**

### 一、I/O 软件的四层结构

```text
用户进程        read(file, buf, n)                    ← I/O 请求的发起点
    │
    ▼  系统调用
──────────────────────────────────────────  用户态 / 内核态 边界
    │
    ▼
① 用户层 I/O 软件     库函数（如 fopen/fread/fclose）      ← 封装系统调用
    │                  提供用户友好的接口
    ▼
② 设备无关软件层      统一接口、缓冲区管理、设备保护、       ← OS 内核核心
    │                  逻辑块→物理块映射、错误处理
    ▼
③ 设备驱动程序        将通用请求翻译为设备特有命令序列       ← 与设备类型一对一
    │                  （写哪些寄存器、按什么时序）
    ▼
④ 中断处理程序        处理设备完成通知，唤醒等待进程         ← 与硬件直接交互
    │
    ▼
硬件（设备控制器）      执行物理 I/O 操作
```

### 二、三阶段与四层软件的对应

```text
┌─────────────────────────────────────────────────────────┐
│ I/O 请求阶段                                              │
│                                                         │
│ 用户进程调用 read() → 库函数 → 系统调用（trap）            │
│ → 设备无关软件：检查参数合法性、查设备状态、分配缓冲区       │
│ → 若设备忙 → 进程进入阻塞队列（blocked）                   │
│ → 设备驱动程序：将请求写入设备控制器的命令寄存器             │
│   此时请求已"提交"，CPU 可调度其他进程运行                  │
├─────────────────────────────────────────────────────────┤
│ I/O 进行阶段                                              │
│                                                         │
│ 设备控制器独立工作（不占用 CPU）：                          │
│   - 磁盘：磁头寻道 → 旋转延迟 → 扇区读取                   │
│   - 键盘：等待用户按键                                    │
│   - 网卡：接收/发送数据帧                                 │
│ CPU 在此期间执行其他进程（I/O 与计算重叠，提高系统吞吐）      │
├─────────────────────────────────────────────────────────┤
│ I/O 完成阶段                                              │
│                                                         │
│ 设备完成任务 → 发中断信号给 CPU                            │
│ → 中断处理程序：保存现场 → 读取设备状态 →                   │
│   将数据从设备缓冲拷入内核缓冲区                            │
│ → 唤醒被阻塞的用户进程（移入就绪队列）                      │
│ → 进程被调度 → 返回 read() → 用户得到数据                  │
└─────────────────────────────────────────────────────────┘
```

### 三、各层职责速查

| 层次 | 主要职责 | 举例（以读磁盘为例） |
| :--- | :--- | :--- |
| **用户层 I/O** | 提供库函数接口 | `fread(buf, 1, 512, fp)` |
| **设备无关软件** | 统一命名、保护、缓冲、分配 | 将文件名→inode→逻辑块号；检查权限；分配内核 buffer |
| **设备驱动程序** | 将通用命令翻译为设备操作 | 计算物理柱面/磁头/扇区；写磁盘控制器命令寄存器 |
| **中断处理程序** | 响应完成信号、唤醒进程 | 磁盘中断→读状态→拷贝数据→`wakeup(process)` |

### 四、与 408 计组 I/O 章节的对应关系

| OS 层    | 计组对应内容              | 差异                            |
| :------ | :------------------ | :---------------------------- |
| 设备驱动程序  | I/O 接口（数据/状态/控制寄存器） | OS 讲软件如何操作寄存器，计组讲寄存器硬件结构      |
| 中断处理程序  | 中断隐指令 + ISR         | OS 讲 ISR 唤醒进程的逻辑，计组讲 CPU 硬件动作 |
| 设备无关软件  | —（计组不涉及）            | 文件系统、缓冲区、设备保护是 OS 独有的         |
| 用户层 I/O | —（计组不涉及）            | 库函数是 OS 独有                    |

### 五、贯穿始终的四个重要概念

| 概念                   | 含义                             | 在哪个阶段体现                 |
| :------------------- | :----------------------------- | :---------------------- |
| **阻塞（Blocking）**     | 进程发起 I/O 请求后进入阻塞态，CPU 转去执行其他进程 | 请求→进行 的过渡阶段             |
| **缓冲（Buffering）**    | 在内核中开辟缓冲区，解决 CPU 与外设速度不匹配      | 请求阶段（分配缓冲）和完成阶段（数据拷入缓冲） |
| **异步（Asynchrony）**   | I/O 操作与 CPU 计算并行执行             | 进行阶段（设备独立工作）            |
| **通知（Notification）** | 设备完成 I/O 后通过中断告知 CPU           | 完成阶段                    |

### 六、一句话总结

> **I/O 请求 = 用户发起系统调用 + OS 层层下传至设备驱动；I/O 进行 = 设备独立工作 + CPU 执行其他进程（异步并行）；I/O 完成 = 设备发中断 + ISR 唤醒被阻塞的进程。三阶段的背后是 OS 四层 I/O 软件（用户库 → 设备无关层 → 驱动 → 中断处理）的接力协作。**

## Q5 · 系统调用/中断/异常中 硬件与 OS 的分工

> 在执行系统调用、中断、异常等事件时，哪些由硬件完成，哪些由操作系统完成？

**答：硬件管三件事——检测、保存（PC+PSW）、跳转；OS 管剩下所有事。**

### 一、系统调用（自陷 / trap）

```text
用户程序执行 trap/syscall 指令
    │
    ▼  ┌─────────────────────────────────────────┐
       │ 硬件完成：                                │
       │ (1) 保存 PC → 特定寄存器/内核栈             │
       │ (2) 保存 PSW → 内核栈                      │
       │ (3) 切换到内核态（修改 PSW 特权级别位）       │
       │ (4) 从中断向量表加载系统调用入口 → PC         │
       │ (5) 切换到内核栈                           │
       └─────────────────────────────────────────┘
    │
    ▼  ┌─────────────────────────────────────────┐
       │ OS 完成：                                 │
       │ (1) 保存通用寄存器（上下文保护）              │
       │ (2) 根据系统调用号查系统调用表                │
       │ (3) 执行对应内核服务子程序                   │
       │ (4) 恢复通用寄存器                          │
       │ (5) 执行 return-from-trap 返回             │
       └─────────────────────────────────────────┘
```

### 二、外部中断（I/O 完成等）

```text
外设发出 INTR 信号
    │
    ▼  ┌─────────────────────────────────────────┐
       │ 硬件完成：                                │
       │ (1) CPU 执行完当前指令后检测 INTR 线         │
       │ (2) 若 IF=1 → 进入中断响应周期              │
       │ (3) 关中断（IF 自动清零）                   │
       │ (4) 保存断点 PC + PSW → 内核栈             │
       │ (5) 从外设获取中断类型号                    │
       │ (6) 查中断向量表 → 加载 ISR 入口 → PC       │
       │ (7) 切换到内核态                           │
       └─────────────────────────────────────────┘
    │
    ▼  ┌─────────────────────────────────────────┐
       │ OS 完成：                                 │
       │ (1) 保存所有寄存器（上下文保护）              │
       │ (2) 开中断（STI，允许嵌套）                  │
       │ (3) 执行 ISR 核心处理                      │
       │ (4) 关中断（CLI）                          │
       │ (5) 发 EOI（中断结束信号）                  │
       │ (6) 恢复寄存器                             │
       │ (7) IRET 返回被中断的程序                   │
       └─────────────────────────────────────────┘
```

### 三、异常（缺页/除零/非法指令）

```text
CPU 在指令执行过程中检测到异常条件
    │
    ▼  ┌─────────────────────────────────────────┐
       │ 硬件完成：                                │
       │ (1) CPU 检测到异常（除零/缺页/保护违例）      │
       │ (2) 保存断点 PC + PSW → 内核栈             │
       │ (3) 根据异常类型查向量表 → 加载处理入口       │
       │ (4) 切换到内核态                           │
       └─────────────────────────────────────────┘
    │
    ▼  ┌─────────────────────────────────────────┐
       │ OS 完成：                                 │
       │ (1) 保存寄存器上下文                        │
       │ (2) 判异常类型并处理：                      │
       │    · 缺页 → 查地址合法性 → 调页 → 更新页表    │
       │    · 除零 → 发 SIGFPE 信号                │
       │    · 保护违例 → 发 SIGSEGV 信号            │
       │ (3) 能修复 → 恢复寄存器 → IRET 重试         │
       │    不能修复 → 终止进程                     │
       └─────────────────────────────────────────┘
```

### 四、三类事件分工速查

| 做什么 | 系统调用 | 外部中断 | 异常 |
| :--- | :--- | :--- | :--- |
| **谁触发** | 用户程序主动（trap 指令） | 外设（INTR 信号） | CPU 内部检测到问题 |
| **检测者** | —（程序主动触发） | 硬件：指令结束时查 INTR 线 | 硬件：指令执行中检测 |
| **保存 PC/PSW** | 硬件 | 硬件 | 硬件 |
| **切内核态** | 硬件 | 硬件 | 硬件 |
| **加载入口地址** | 硬件（查向量表） | 硬件（查向量表） | 硬件（查向量表） |
| **保存通用寄存器** | OS | OS | OS |
| **核心处理** | OS（内核服务子程序） | OS（ISR） | OS（异常处理程序） |
| **恢复通用寄存器** | OS | OS | OS |
| **返回** | OS 执行 return-from-trap | OS 执行 IRET | OS 执行 IRET |

### 五、一句话总结

> **硬件管三件事：检测信号、保存 PC+PSW、查向量表跳转。OS 管剩下所有：保存通用寄存器、核心处理逻辑、开/关中断、唤醒进程、恢复寄存器、返回。口诀：硬件切进来，OS 做出来。**

## Q6 · 中断 vs 子程序调用 + 系统调用 vs 库函数

### 一、中断处理 vs 子程序调用

两者都改变程序执行流程、跳转到别处执行后返回，但本质完全不同：

| 对比维度         | 中断处理               | 子程序调用                 |
| :----------- | :----------------- | :-------------------- |
| **触发者**      | 硬件/外设（异步，不可预测）     | 程序指令 CALL（同步，程序员写死的）  |
| **发生时机**     | 可在任意指令执行后          | 仅在 CALL 指令处           |
| **运行态**      | 内核态                | 用户态（通常）               |
| **返回地址保存于**  | 内核栈（硬件自动压入 PC+PSW） | 用户栈或寄存器（CALL 指令压入 PC） |
| **PSW 是否保存** | 是（硬件自动保存并切换模式）     | 否（PSW 不变）             |
| **通用寄存器保存**  | ISR 开头软件保存全部       | 调用者/被调用者按约定保存部分       |
| **与主程序关系**   | 无直接关系（打断随机指令）      | 明确主-子关系（传参、返回值）       |
| **开销**       | 大（全上下文、切换栈、查向量表）   | 小（仅保存返回地址、跳转）         |

> 一句话：子程序调用是主动的、同步的、可预期的代码复用；中断是被动的、异步的、外设强加的事件响应。

### 二、系统调用 vs 库函数

```text
用户程序
    │
    ├── printf()           ← 库函数（用户态）
    │       └── write()    ← 系统调用（内核态）
    │
    └── strlen()           ← 库函数（用户态），纯计算，不涉及系统调用
```

| 对比维度          | 系统调用                | 库函数                      |
| :------------ | :------------------ | :----------------------- |
| **运行态**       | 内核态                 | 用户态                      |
| **本质**        | 内核提供的服务入口           | 用户空间的函数封装                |
| **入口方式**      | trap/syscall → 查向量表 | CALL → 函数地址              |
| **由谁提供**      | OS 内核               | C 标准库 / 第三方库             |
| **栈切换**       | 切换（用户栈 → 内核栈）       | 不切换（同一用户栈）               |
| **可移植性**      | 不同 OS 不同            | 同标准下可移植                  |
| **开销**        | 大（陷阱+态切换+上下文保存）     | 小（普通函数调用）                |
| **一定涉及系统调用？** | 本身即系统调用             | 不一定——strlen/abs 纯计算，不碰内核 |
| **一对一？**      | —                   | 一个库函数可能调零个、一个或多个系统调用     |

### 三、408 常见干扰项

| 表述                     | 判定  | 原因                               |
| :--------------------- | :-: | :------------------------------- |
| "库函数 = 系统调用的封装"        | 部分对 | 有的库函数无系统调用（strlen），有的封装多个（fopen） |
| "系统调用必须通过库函数调用"        |  错  | 可直接汇编 trap 进入                    |
| "调用库函数不会进入内核态"         |  错  | 取决于内部是否调系统调用                     |
| "库函数执行在用户态，系统调用执行在内核态" |  对  | 本质区别                             |
| "中断和子程序调用没有本质区别"       |  错  | 同步 vs 异步、用户态 vs 内核态              |

## Q7 · 时钟中断服务程序需要更新哪些内容

> 每次时钟中断发生时，ISR 需要更新哪些关键数据？

**答：三类核心更新——全局时钟变量、进程 CPU 时间记账、进程剩余时间片，分别对应系统计时、进程统计、进程调度。**

### 一、三项核心更新

| 更新内容 | 对应变量/字段 | 操作 | 用途 |
| :--- | :--- | :--- | :--- |
| **I. 内核时钟变量** | `jiffies` / `ticks` 等全局计数器 | 每次中断 +1 | 维持全局系统时间，是所有定时操作（sleep、timeout）的基础 |
| **II. 当前进程占用 CPU 时间** | PCB 中 `utime`（用户态时间）、`stime`（内核态时间） | 累加本次 tick | 进程调度记账；`top`/`ps` 显示 CPU 占用率；为 CPU 时间记账机制提供数据 |
| **III. 当前进程剩余时间片** | PCB 中 `timeslice` / `counter` 等字段 | 减 1 | 若减到 0 → 置 `need_resched` 标志，触发调度器在下一次调度点抢占当前进程 |

### 二、三者的关系

```text
时钟中断到达
    │
    ├─→ (I)   jiffies++                  ← 系统全局计时，无条件执行
    │
    ├─→ (II)  current->utime++ 或 stime++ ← 进程 CPU 记账
    │         （取决于中断发生时 CPU 处于用户态还是内核态）
    │
    └─→ (III) current->timeslice--        ← 时间片轮转的核心
              │
              ├─ timeslice > 0 → 继续运行
              └─ timeslice == 0 → need_resched = 1
                                    │
                                    └─ 中断返回前检查 → 若 need_resched=1
                                       → 调用 schedule() 切换进程
```

### 三、408 考点关联

| 考法 | 涉及项 | 典型问题 |
| :--- | :---: | :--- |
| 时间片轮转调度 | III | "RR 调度算法中，时间片用完时由谁触发进程切换？" — 时钟中断 |
| 进程 CPU 时间统计 | II | "ps 命令显示的进程 CPU 时间从哪里来？" — PCB 中的 utime/stime |
| 系统定时精度 | I | "sleep(1) 的精度取决于什么？" — 时钟中断的频率（HZ） |
| 抢占式调度触发 | III | "用户进程在什么时机被剥夺 CPU？" — 时钟中断发现 timeslice=0，返回前调度 |

### 四、补充：第四项常见误区

| 是否属于时钟 ISR | 内容 | 说明 |
| :---: | :--- | :--- |
| 是 | 处理软定时器（soft timer） | 扫描内核定时器链表，检查是否有到期 timer，将其回调函数加入待执行队列 |
| 否 | 实际执行 timer 回调 | 回调函数通常在**下半部**（bottom half / 软中断）执行，不在 ISR 中直接调用——ISR 只负责检查并标记 |
