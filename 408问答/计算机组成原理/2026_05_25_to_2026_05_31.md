### Q57 | 2026-05-28

**问题**：在输入输出系统中的程序中断用于异步通信，外设是否仅需提供数据即可，对于数据的后继处理有中断程序完成即可？

**回答**：

**基本正确，但外设除了"提供数据"之外，还必须做两件事：① 发出中断请求信号通知 CPU；② 在中断响应周期提供中断类型号/向量，让 CPU 能找到正确的中断服务程序。**

#### 一、外设与 CPU 在程序中断 I/O 中的分工

| 谁做 | 做什么 | 所在阶段 |
| :--- | :--- | :--- |
| **外设** | 准备数据（如键盘扫描码、网卡帧、磁盘扇区） | 数据准备阶段 |
| **外设** | 将数据放入数据缓冲寄存器（DBR） | 数据就绪 |
| **外设** | **发出中断请求信号（INTR）** | 通知 CPU |
| **外设** | 在中断响应周期，将**中断类型号**送到数据总线 | CPU 响应后 |
| **CPU（ISR）** | 保存现场 → 从 DBR 读数据 → 写入主存 → 处理数据 → 恢复现场 → 中断返回 | 中断服务阶段 |

#### 二、完整交互时序

```text
外设                                      CPU
  │                                        │
  │  数据准备完成，放入 DBR                   │  正在执行用户程序
  │                                        │
  │  ── INTR（中断请求）────────────────→     │  ← 没有这根信号线，CPU 永远不知道数据好了
  │                                        │
  │                                        │  当前指令执行完，检测到 INTR
  │                                        │  若 IF=1（开中断），进入中断周期
  │                                        │
  │  ←── INTA（中断响应）─────────────────   │  CPU 发出中断响应信号
  │                                        │
  │  ── 中断类型号 → 数据总线 ──────────→    │  ← 没有类型号，CPU 调不到正确的 ISR
  │                                        │
  │                                        │  从 IVT 取 ISR 入口地址 → PC
  │                                        │
  │  ←── IOR（读端口指令）───────────────   │  ISR 从外设端口读取数据
  │                                        │
  │  ── DBR 中数据 → 数据总线 ─────────→    │  CPU 读入数据
  │                                        │
  │                                        │  ISR 处理、写入主存、清中断、返回
  │                                        │  继续执行原程序
```

#### 三、"只提供数据"为什么不够？

| 缺少的步骤 | 后果 |
| :--- | :--- |
| 没有 **INTR 信号** | CPU 永远不知道外设何时准备好了数据，只能轮询——那就退化成**程序查询方式**了 |
| 没有 **中断类型号** | CPU 不知道是哪个设备发出的中断，无法定位 ISR 入口地址（除非只有唯一设备 + 固定入口） |

#### 四、程序中断 vs. DMA vs. 程序查询

| 维度 | 程序查询 | 程序中断 | DMA |
| :--- | :--- | :--- | :--- |
| **CPU 如何知道数据就绪** | 反复读状态字（轮询） | 外设主动发 INTR | 外设主动发 DMA 请求 |
| **数据传送路径** | CPU：外设 DBR → CPU → 主存 | CPU：外设 DBR → CPU → 主存 | **直接**：外设 → 主存（不经过 CPU） |
| **后续数据处理** | 程序继续处理 | ISR 处理 | CPU 仅收"传输完成"中断 |
| **CPU 负担** | 全程占用（忙等） | 仅在 ISR 中逐字传送 | 仅在启动和结束时介入 |
| **适用场景** | 低速、简单系统 | 中低速、实时响应 | 高速大批量数据传送 |

> ⚠️ **核心区别**：程序中断方式中，CPU 仍**逐字**从外设数据寄存器读取数据并写入主存（搬运工仍是 CPU）。DMA 方式中，数据传送由 DMA 控制器独立完成，CPU 只负责启动和收尾。

#### 五、一句话总结

**外设要提供三样东西：数据 + 中断请求信号 + 中断类型号。数据的存储、加工、后继处理全部由 ISR 完成——外设不需要知道数据最终去哪里、怎么用。**

### Q58 | 2026-05-28

**问题**：在多重中断的处理过程中，中断隐指令完成时间段是否就是中断响应时间段？中断服务程序执行时间段是否是中断处理时间段？而能够抢断中断的时间段是不是在 ISR 中 STI 开中断之后的某一点？

**回答**：

#### 一、中断隐指令时间段 = 中断响应时间段？

**是的，两者等价。** 中断隐指令是 CPU 响应中断后由**硬件自动完成**的操作序列，不属于任何用户程序指令（故称"隐"）。这个硬件操作阶段就是**中断响应周期**。

```text
当前指令执行完毕
      │
      ▼
┌─────────────────────────┐
│  中断响应周期 = 中断隐指令  │  ← 硬件自动完成，非软件指令
│                         │
│  ① SP-1 → SP, SP → MAR  │
│  ② PC → MDR → 主存[SP]  │  压栈保存断点
│  ③ PSW → 堆栈（部分 CPU）│  保存程序状态字
│  ④ 中断向量 → PC         │  跳转到 ISR 入口
│                         │
│  ▲ 全程关中断，不可被抢断  │
└─────────────────────────┘
      │
      ▼
  进入 ISR 第一条指令
```

| 两个名称 | 指代对象 | 侧重点 |
| :--- | :--- | :--- |
| **中断响应周期** | 指令周期五阶段之一（取指→间址→执行→**中断**） | 时序位置——"哪一 CPU 周期阶段" |
| **中断隐指令** | 该阶段中硬件执行的操作序列（关中断 + 保存断点 + 取 ISR 入口） | 功能内容——"做了哪些事" |

---

#### 二、中断服务程序执行时间段 = 中断处理时间段？

**基本等价，但"中断处理"有广狭两义：**

| 含义 | 覆盖范围 | 对应 408 术语 |
| :--- | :--- | :--- |
| **狭义** | 仅指 ISR 软件执行期间（入口 → IRET 前） | "中断服务程序" |
| **广义** | 从 CPU 响应中断到返回原程序的**全过程**（含中断隐指令 + ISR） | "中断处理全过程" |

408 中通常把 ISR 执行阶段称为"中断处理"，中断响应阶段已独立命名，所以这个对应关系是对的。

---

#### 三、能抢断的时间段在 ISR 中什么位置？

**在 ISR 中，但不是在"某一点"——是一段连续窗口：STI（开中断指令）之后 → CLI（关中断指令）之前。** 不是任意位置都能被抢断。

ISR 执行的各阶段按时间顺序如下：

|      阶段       |    谁做的     | 做什么                                   | 关中断？ |     可被抢断？      |
| :-----------: | :--------: | :------------------------------------ | :--: | :------------: |
|  **① 中断响应**   |  硬件（隐指令）   | 关中断 → 保存断点(PC+PSW 压栈) → 取 ISR 入口 → PC | ✅ 已关 |      ❌ 不可      |
|  **② 保存现场**   | 软件（ISR 开头） | PUSH 各通用寄存器到堆栈                        | ✅ 仍关 |      ❌ 不可      |
| **③ STI 开中断** |     软件     | 执行 STI 指令，IF ← 1                      | ❌ 已开 | ✅ **从此起可被抢断**  |
|  **④ 核心处理**   |     软件     | 执行 ISR 真正任务（读外设数据、处理、写主存等）            | ❌ 开着 |  ✅ 可被更高级中断抢断   |
| **⑤ CLI 关中断** |     软件     | 执行 CLI 指令，IF ← 0                      | ✅ 重关 | ❌ **从此起不可再抢断** |
|  **⑥ 恢复现场**   | 软件（ISR 末尾） | POP 各通用寄存器                            | ✅ 关着 |      ❌ 不可      |
| **⑦ IRET 返回** |     硬件     | 恢复 PC、PSW → 返回原程序断点                   | ✅ 关着 |      ❌ 不可      |
|               |            |                                       |      |                |

> ⚠️ 可抢断窗口 = 阶段 ③ → ④（STI 之后、CLI 之前的一**段连续时间**），不是某一个时间点。

**嵌套打断的完整时序：**

假设：ISR_1 对应 2 级中断，ISR_2 对应 1 级中断（更高级，可抢断 2 级）。

| 步骤 | 谁在执行 | 发生了什么 |
| :---: | :--- | :--- |
| 1 | 主程序 | 正常运行中…… |
| 2 | — | **1 级中断源发出请求** |
| 3 | 硬件 | 中断响应（隐指令）：关中断 → 保存主程序断点 → 加载 ISR_1 入口 |
| 4 | ISR_1 | 保存现场（PUSH 寄存器） |
| 5 | ISR_1 | **执行 STI，开中断** ← 抢断窗口打开 |
| 6 | — | **0 级中断源（更高级）发出请求** |
| 7 | 硬件 | 中断响应：关中断 → 在 ISR_1 的堆栈帧上保存 ISR_1 的断点 → 加载 ISR_2 入口 |
| 8 | ISR_2 | 保存现场 → STI 开中断 → 核心处理 → CLI 关中断 → 恢复现场 |
| 9 | ISR_2 | **执行 IRET**，返回 ISR_1 |
| 10 | ISR_1 | 继续核心处理（从被抢断处恢复）→ CLI 关中断 → 恢复现场 |
| 11 | ISR_1 | **执行 IRET**，返回主程序 |
| 12 | 主程序 | 继续执行 |

> 核心逻辑：步骤 5（STI 开中断后）到步骤 10（CLI 关中断前）是 ISR_1 的**可抢断窗口**。如果更高级中断请求恰好在窗口期内到达（步骤 6），CPU 就会暂停 ISR_1、嵌套执行 ISR_2，等 ISR_2 返回后再继续 ISR_1。

---

#### 四、三个时间段的抢断能力对比

| 时间段                     | 是否可被抢断 | 原因                               |
| :---------------------- | :----: | :------------------------------- |
| 中断隐指令（中断响应）             |  ❌ 不可  | 硬件自动关中断，PC/PSW 正在压栈，此时打断会破坏堆栈一致性 |
| ISR：**现场保存阶段**（STI 之前）  |  ❌ 不可  | IF=0，中断被屏蔽                       |
| ISR：**STI 之后 → CLI 之前** |  ✅ 可以  | IF=1，更高级中断请求可被响应                 |
| ISR：**现场恢复阶段**（CLI 之后）  |  ❌ 不可  | 即将 IRET，若此时被抢断，返回地址链会混乱          |

---

#### 五、一句话总结

> **中断隐指令 = 中断响应**（同一阶段，硬件关中断完成）；**ISR 执行 = 中断处理**（软件完成）；**可抢断的窗口是 STI → CLI 之间的一段连续时间**——没开中断的 ISR 段落同样不可被抢断。多重中断的关键不是"ISR 中间某一点"，而是软件**主动在保存现场后 STI 开了一个窗口**，让更高级中断有机会进来。

### Q59 | 2026-05-28

**问题**：在 CPU 的程序执行轨迹图中，多个中断源同时到达时，是否先响应硬件优先级高的 A？如果又有处理优先级更高的 B，轨迹图上是否出现 A 一小截 → B 完整的进程？什么时候轨迹才会先跳回主程序再跳去另一个中断源？

**回答**：

#### 一、多中断同时到达，先响应谁？

**硬件排队优先级最高的那个（设为 A）。** CPU 不认识"处理优先级"——排队仲裁由硬件排队器/优先编码器硬连线决定，不可软件更改。

```text
多个中断请求同时到达
        │
        ▼
  硬件排队器仲裁（硬连线固定）
        │
        ▼
  选出硬件优先级最高的 → CPU 响应它（A）
  其余中断源保持请求信号（pending），等待下次被响应
```

#### 二、A 一小截 → B 完整的轨迹

**是的，这正是嵌套抢断的执行轨迹。**

```text
时间 →

主程序  ████████                                    ████████
A_ISR           ████░░░░░░░░░░░░░░░░░░░░░░░░████████
B_ISR                ████████████████████████
                         ↑
                    B 完整跑完，IRET 回到 A 的断点
```

A 上那一小截的内容：

| A 执行了什么 | 阶段 | 可被抢断？ |
| :--- | :--- | :---: |
| 进入 A 的中断隐指令（关中断、保存断点、加载入口） | 硬件 | ❌ |
| A 的保存现场（PUSH 寄存器） | 软件 | ❌ |
| **A 执行 STI，开中断** | 软件 | ✅ 从此可被抢断 |
| ← B 在此刻到达，抢断发生 | — | — |

B 完整跑完后，IRET 回到 A 的断点，A 继续剩余部分（核心处理 → CLI → 恢复现场 → IRET → 主程序）。

#### 三、什么时候轨迹会先跳回主程序？

**当 B 无法抢断 A 时**——即 B 的处理优先级 ≤ A 的处理优先级。此时 A 必须完整跑完，CPU 回到主程序执行至少 1 条指令，然后才响应 B。

```text
时间 →

主程序  ████████                        ██          ████████
                             ← 回到主程序至少 1 条指令 →
A_ISR           ████████████████████████
B_ISR                                   ████████████████████████
```

**为什么中间有主程序那一小截？**

IRET 指令本身执行结束时**不会立即**再次响应中断。中断请求的采样发生在**每条指令执行结束后**：

1. A 执行 IRET → PC、PSW 恢复为主程序上下文（IF=1，开中断）
2. CPU 进入取指周期，取主程序的下一条指令并执行
3. **该指令执行结束时**，CPU 采样 INTR 线 → 发现 B 仍在 pending
4. 进入新的中断响应 → 跳去执行 B 的 ISR

> ⚠️ 所以主程序至少执行 1 条指令后才跳到 B，不可能是 0 条。IRET 返回后立即再次响应中断的说法是错误选项的常见写法。

#### 四、两张轨迹图的对比

| 场景 | 条件 | 轨迹顺序 | 主程序夹在 A 和 B 之间？ |
| :--- | :--- | :--- | :---: |
| **B 抢断 A**（嵌套） | B 的处理优先级 > A 的处理优先级 | 主程序 → A(头) → B(完整) → A(尾) → 主程序 | ❌ 没有 |
| **B 排队等 A**（顺序） | B 的处理优先级 ≤ A 的处理优先级 | 主程序 → A(完整) → **主程序(≥1条)** → B(完整) → 主程序 | ✅ 有 |

#### 五、硬件排队优先级 vs. 中断处理优先级

| | 硬件排队优先级 | 中断处理优先级 |
| :--- | :--- | :--- |
| **谁定的** | 硬件（排队器电路，固定） | 软件（中断屏蔽寄存器 IMR，可编程） |
| **决定什么** | 多个请求**同时到达**时，先响应谁 | 正在执行的 ISR **能否被抢断** |
| **生效时机** | 中断响应周期之前（排队仲裁） | ISR 执行期间（STI 之后的窗口期） |
| **能改吗** | ❌ 不可（硬连线） | ✅ 可（软件写屏蔽字） |
| **408 关键词** | "同时到达"、"排队"、"优先编码器" | "多重中断"、"嵌套"、"抢断"、"屏蔽字" |

#### 六、一句话总结

> **硬件优先级管"谁先上场"，处理优先级管"上场后会不会被踢下去"。** B 能抢断 A → 轨迹是 A(头)→B(完整)→A(尾)，中间不经过主程序；B 不能抢断 A → 轨迹是 A(完整)→主程序(至少1条)→B(完整)，中间必有主程序的一小截。

### Q60 | 2026-05-28

**问题**：当两个中断源 A、B 之间是嵌套关系（A 响应优先级 > B，B 处理优先级 > A），中间就不出现主程序；而顺序关系（A 响应优先级 > B 且处理优先级也 > B；或者 B 处理优先级 > A 但 A 后到达、被 B 屏蔽），就会出现主程序。这样理解对吗？

**回答**：

**完全正确。** 是否出现主程序，只取决于一件事：**先进 ISR 的那个能不能被另一个抢断。**

#### 一、嵌套（无主程序）— 一种情况

| 条件 | |
| :--- | :--- |
| 到达时序 | A 和 B **同时到达** |
| 硬件仲裁 | A 响应优先级 > B → CPU 先响应 A |
| 处理优先级 | **B 处理优先级 > A 处理优先级** |
| 结果 | A 执行到 STI 后被 B 抢断 |

```text
主程序  ████████                                    ████████
A_ISR           ████░░░░░░░░░░░░░░░░░░░░░░░░████████
B_ISR                ████████████████████████
                     ↑ 无主程序
```

#### 二、顺序（有主程序）— 两种情况

**情况 1：同时到达，但抢不动**

| 条件 | |
| :--- | :--- |
| 到达时序 | A 和 B **同时到达** |
| 硬件仲裁 | A 响应优先级 > B → CPU 先响应 A |
| 处理优先级 | **A 处理优先级 > B 处理优先级** |
| 结果 | A 开着中断跑完，B 抢不动，排队 |

**情况 2：先来后到，后来者被屏蔽**

| 条件 | |
| :--- | :--- |
| 到达时序 | B **先到**，CPU 已在执行 B 的 ISR；A **后到** |
| 处理优先级 | **B 处理优先级 > A 处理优先级** |
| 结果 | A 被 B 的屏蔽字挡住，CPU 不响应，等 B 跑完 |

两种情况的轨迹相同：

```text
主程序  ████████                        ██          ████████
                             ← 至少 1 条指令 →
先跑者      ████████████████████████████
后跑者                                    ████████████████
```

#### 三、完整判断流程

```text
A 和 B 的请求到达
        │
        ▼
   同时到达？
    │         │
   是         否（B 先到，已在执行）
    │         │
    ▼         ▼
 CPU 先响应   B 的处理优先级 > A？
 响应优先级    │         │
 高的那个     是         否
    │         │         │
    ▼         ▼         ▼
 它开中断后  A 被屏蔽    A 可以抢断 B
 另一个能    B 先跑完   （嵌套，A 抢 B）
 抢断它？
  │    │
 是    否
  │    │
  ▼    ▼
嵌套       排队
无主程序    有主程序
```

#### 四、一句话总结

> **是否出现主程序，取决于"先进 ISR 的那个能不能被抢断"。能抢 → 嵌套，无主程序；不能抢（处理优先级不够 → 抢不动 + 后到被屏蔽 → 没资格抢，两种情况）→ 排队，必有主程序至少一条指令。**

### Q61 | 2026-05-28

**问题①**：进入中断响应周期"时"，CPU 一定处于中断允许状态（IF=1）吗？

**问题②**：进入中断响应周期"后"，CPU 一定处于关中断状态（IF=0）吗？

**回答**：

> ⚠️ **408 选择题高频文字陷阱**："时"和"后"一字之差，答案完全相反。

#### 一、进入中断响应周期"时"——不一定

| 中断类型 | 进入响应周期"时"IF 必须为 1？ | 原因 |
| :--- | :---: | :--- |
| **INTR（可屏蔽中断）** | ✅ 必须 | IF=1 是进入门槛，IF=0 则 CPU 直接跳过，不进入响应周期 |
| **NMI（非屏蔽中断）** | ❌ 不要求 | IF 拦不住 NMI，IF=0 照样进入响应周期 |

```text
INTR 的流程：
当前指令结束 → 检测 INTR 且 IF=1？
                    │
                    ├─ 否 → 不响应，继续取下一条指令
                    │
                    └─ 是 → 进入中断响应周期（门槛跨过）
                            │
                            ▼ 第一步
                        硬件关中断 IF ← 0
```

> 所以题目如果写"进入中断响应周期时，CPU 一定处于开中断状态"——**错**，NMI 是反例。

#### 二、进入中断响应周期"后"——一定关中断

| 中断类型 | 进入响应周期"后"IF 一定为 0？ | 原因 |
| :--- | :---: | :--- |
| **INTR** | ✅ 一定 | 响应周期第一步就是硬件自动 IF ← 0 |
| **NMI** | ✅ 一定 | 同样关中断——保存断点是原子操作，不允许嵌套打断 |

没有反例。无论什么中断，保存断点（PC + PSW 压栈）绝不能被中断，所以进入后 IF 必为 0。

#### 三、"时" vs. "后"——一张表说死

| 问法 | 答案 | 反例 |
| :--- | :---: | :--- |
| 进入中断响应周期**时**，IF 一定为 1？ | ❌ **错** | NMI 不需要 IF=1 |
| 进入中断响应周期**时**（仅限 INTR），IF 一定为 1？ | ✅ **对** | 无 |
| 进入中断响应周期**后**，IF 一定为 0？ | ✅ **对** | 无（INTR 和 NMI 都关） |
| 进入中断响应周期**后**，IF 可能仍为 1？ | ❌ **错** | 不存在 |

> 💡 **记忆技巧**："时"看门槛（INTR 要跨，NMI 不用跨）；"后"看动作（进门第一件事就是锁门，谁进去都得锁）。

#### 四、一句话总结

> **"时"不一定——NMI 可以破门而入；"后"一定关——进门就锁，没有例外。408 选择题把"时"偷换成"后"（或反过来）是最常见的干扰项设计。**

### Q62 | 2026-05-28

**问题**：异常、中断、DMA 请求三者的检测时机有何不同？

**回答**：

**三者对应三个不同的检测时间点，408 选择题常混在一起考。**

#### 一、检测时机对比

| 事件类型 | 检测时机 | 为什么在这个时刻 |
| :--- | :--- | :--- |
| **异常（内中断）** | 指令执行**过程中** | 异常是当前指令自身引发的（除零、缺页、非法指令、断点），不等指令结束就得处理 |
| **中断（外中断 / INTR）** | 指令执行**结束时** | 中断来自 CPU 外部（外设），必须等当前指令完整执行完毕再采样 INTR 线 |
| **DMA 请求** | **总线周期结束时** | DMA 控制器只借总线使用权，不打断 CPU 指令执行。当前总线周期一结束就让出总线 |

#### 二、时间点示意

```text
                        指令执行中
                    ┌───────────────┐
                    │               │
    异常检测点 ──────┤  取指→译码→执行→访存→写回  ├───── 中断检测点
                    │               │              （指令结束）
                    └──┬──┬──┬──┬──┘
                       │  │  │  │
                       ▼  ▼  ▼  ▼
                   每个总线周期结束 ──→ DMA 检测点
```

#### 三、深度辨析

| 对比维度 | 异常 | 中断 | DMA 请求 |
| :--- | :--- | :--- | :--- |
| 谁触发的 | CPU 内部（指令执行） | CPU 外部（外设） | DMA 控制器（外设） |
| 检测粒度 | 指令内任意时刻 | 指令边界 | 总线周期边界 |
| 是否打断指令 | ✅ 可能打断并重跑 | ❌ 等指令执行完 | ❌ 不涉及指令流，只借总线 |
| 处理方式 | 跳转异常处理程序 | 跳转 ISR | CPU 暂停总线使用，交给 DMA |

#### 四、一句话总结

> **异常：指令中途发现就处理（可能重跑当前指令）；中断：指令完整跑完才看一眼 INT 线；DMA：总线周期结束就交枪。三个检测点——指令中、指令末、总线末。**

> ⚠️ **高频错误项**："中断是异常的一种"或"异常在指令结束时检测"——都是错的。408 中异常和中断是并列概念，检测时机完全不同。

### Q63 | 2026-05-28

**问题**：下列关于 DMA 方式的叙述中，错误的是（ ）

A. DMA 方式在主存和外设之间建立了直接的数据通路，数据传输无需 CPU 干预
B. DMA 控制器的初始化工作（如设置主存地址、传送字数）由 CPU 执行
C. 在 DMA 传送过程中，CPU 不能访问主存，必须等待 DMA 传送结束
D. DMA 请求的检测时机是在每个总线周期结束时

**回答**：

**正确答案：C。DMA 与 CPU 之间采用周期挪用或交替访存方式共享总线，CPU 不需要等 DMA 整块传送完成。**

#### 一、逐项分析

| 选项 | 对/错 | 理由 |
| :--- | :---: | :--- |
| A | ✅ 对 | DMA 的本质：外设 ↔ 主存直接交换数据，传送过程由 DMA 控制器接管，CPU 不参与数据搬运 |
| B | ✅ 对 | DMA 传送**前**，CPU 对 DMA 控制器做初始化：写入主存起始地址、传送字数、读写方向。属于预处理阶段 |
| C | ❌ **错** | DMA 只占用一个或几个总线周期（周期挪用），传完一个字就让出总线；CPU 可在 DMA 不占总线时继续执行 |
| D | ✅ 对 | 参见 Q62：DMA 请求在每个总线周期结束时检测 |

#### 二、三种总线使用策略

| 策略 | CPU 反应 | DMA 效率 | 说明 |
| :--- | :--- | :--- | :--- |
| **周期挪用** | DMA 占用一个总线周期，下一周期 CPU 继续 | 高 | 最常用，CPU 最多等一个总线周期 |
| **交替访存** | CPU 和 DMA 分时使用总线 | 中 | 需 C1/C2 双周期交替 |
| **停止 CPU 访存** | CPU 完全停摆等 DMA 传完 | 低 | 极少使用 |

#### 三、一句话总结

> **DMA 是借总线，不是霸占总线。CPU 最多等一个总线周期，不需要等 DMA 整个数据块传送完成。408 常把"周期挪用"偷换成"DMA 传送期间 CPU 不能访存"。**

### Q64 | 2026-05-28

**问题**：DMA 与 Cache 的一致性问题——为什么会产生，如何解决？

**回答**：

DMA 绕过 CPU 直接读写主存，而 CPU 通过 Cache 访问主存。两者看到的是同一块主存区域，但 Cache 中可能有该区域的副本，导致数据不一致。

#### 一、两种不一致场景

| 场景 | 方向 | 发生了什么 | 谁读到脏数据 |
| :--- | :--- | :--- | :--- |
| **场景①** | DMA 写主存 | DMA 把外设数据写入主存区域 X | CPU 读 Cache 中的旧副本 |
| **场景②** | CPU 写 Cache | CPU 修改了 Cache 中区域 X 的数据（write-back 未写回） | DMA 从主存读到旧数据 |

```text
场景①：                             场景②：
  CPU (Cache)  ───旧数据───            CPU  ──写──→ Cache(新) ──未回写──→ 主存(旧)
                                                                    ↑
  DMA ──新数据──→ 主存(新)              DMA ────────读─────────────→ 读到旧的
```

#### 二、三种解决方案

| 方案 | 做法 | 硬件/软件 | 适用场景 |
| :--- | :--- | :---: | :--- |
| **总线监视（硬件监听）** | Cache 控制器监听总线，发现 DMA 写了某地址 → 使对应 Cache 行失效或更新 | 纯硬件 | 有总线侦听能力的系统 |
| **页不可缓存（OS 标记）** | OS 把 DMA 缓冲区所在页标记为不可缓存（uncacheable），CPU 访问时绕过 Cache 直读主存 | 软件（页表属性位） | 最通用，无需特殊硬件 |
| **Cache 刷新** | CPU 在 DMA 操作前后主动执行失效/写回操作 | 软件 + 少量硬件 | 传统 DMA（无总线监听） |

#### 三、Cache 刷新方案详细时序

| 时机 | DMA 写主存（外设→内存） | DMA 读主存（内存→外设） |
| :--- | :--- | :--- |
| **DMA 前** | CPU 把 Cache 脏行**写回**主存 | CPU 把 Cache 脏行**写回**主存，再**失效**对应行 |
| **DMA 中** | 禁止 CPU 访问该区域 | 禁止 CPU 访问该区域 |
| **DMA 后** | CPU 首次访问 Cache miss，从主存取新数据（DMA 刚写入的） | 无需额外操作 |

#### 四、写回 vs 失效

| 操作 | 英文 | 做什么 | 用于哪一侧 |
| :--- | :--- | :--- | :--- |
| **写回** | Write-back / Flush | 把 Cache 脏行写回主存 | CPU 写了但还没到主存 → 先写回，DMA 才能读到新的 |
| **失效** | Invalidate | 标记 Cache 行无效 | DMA 写了主存 → 失效，CPU 下次 miss 取新数据 |

> 💡 口诀：**"DMA 写主存 → CPU 侧失效；CPU 写 Cache → DMA 侧先回。"**

#### 五、避坑警示

> ⚠️ "DMA 和 Cache 不存在一致性问题，因为 DMA 只和外设打交道"——**错**。DMA 的另一端是主存，主存是 CPU-Cache-DMA 三方共享的。
>
> ⚠️ 写直达（write-through）Cache **只解决场景②**（CPU 写同时更新主存），场景①（DMA 写主存后 CPU 读 Cache 旧副本）仍需失效处理。

#### 六、一句话总结

> **DMA 绕过 CPU 直接碰主存，Cache 里可能有陈年旧账。三种解法：硬件偷听总线（总线监视）、软件标记不走 Cache（页不可缓存）、手动打扫（Cache 刷新——写回脏数据 + 失效旧行）。**
