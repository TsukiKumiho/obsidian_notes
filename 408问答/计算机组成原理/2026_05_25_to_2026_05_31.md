### Q57 | 2026-05-28

**问题**：在输入输出系统中的程序中断用于异步通信，外设是否仅需提供数据即可，对于数据的后继处理有中断程序完成即可？

**回答**：

**基本正确，但外设除了"提供数据"之外，还必须做两件事：① 发出中断请求信号通知 CPU；② 在中断响应周期提供中断类型号/向量，让 CPU 能找到正确的中断服务程序。**

#### 一、外设与 CPU 在程序中断 I/O 中的分工

| 谁做 | 做什么 | 所在阶段 |
| :--- | :--- | :--- |
| **外设** | 准备数据（如键盘扫描码、网卡帧、磁盘扇区） | 数据准备阶段 |
| **外设** | 将数据放入数据缓冲寄存器（DBR） | 数据就绪 |
| **外设** | **发出中断请求信号（INTR）** | 通知 CPU |
| **外设** | 在中断响应周期，将**中断类型号**送到数据总线 | CPU 响应后 |
| **CPU（ISR）** | 保存现场 → 从 DBR 读数据 → 写入主存 → 处理数据 → 恢复现场 → 中断返回 | 中断服务阶段 |

#### 二、完整交互时序

```text
外设                                      CPU
  │                                        │
  │  数据准备完成，放入 DBR                   │  正在执行用户程序
  │                                        │
  │  ── INTR（中断请求）────────────────→     │  ← 没有这根信号线，CPU 永远不知道数据好了
  │                                        │
  │                                        │  当前指令执行完，检测到 INTR
  │                                        │  若 IF=1（开中断），进入中断周期
  │                                        │
  │  ←── INTA（中断响应）─────────────────   │  CPU 发出中断响应信号
  │                                        │
  │  ── 中断类型号 → 数据总线 ──────────→    │  ← 没有类型号，CPU 调不到正确的 ISR
  │                                        │
  │                                        │  从 IVT 取 ISR 入口地址 → PC
  │                                        │
  │  ←── IOR（读端口指令）───────────────   │  ISR 从外设端口读取数据
  │                                        │
  │  ── DBR 中数据 → 数据总线 ─────────→    │  CPU 读入数据
  │                                        │
  │                                        │  ISR 处理、写入主存、清中断、返回
  │                                        │  继续执行原程序
```

#### 三、"只提供数据"为什么不够？

| 缺少的步骤 | 后果 |
| :--- | :--- |
| 没有 **INTR 信号** | CPU 永远不知道外设何时准备好了数据，只能轮询——那就退化成**程序查询方式**了 |
| 没有 **中断类型号** | CPU 不知道是哪个设备发出的中断，无法定位 ISR 入口地址（除非只有唯一设备 + 固定入口） |

#### 四、程序中断 vs. DMA vs. 程序查询

| 维度 | 程序查询 | 程序中断 | DMA |
| :--- | :--- | :--- | :--- |
| **CPU 如何知道数据就绪** | 反复读状态字（轮询） | 外设主动发 INTR | 外设主动发 DMA 请求 |
| **数据传送路径** | CPU：外设 DBR → CPU → 主存 | CPU：外设 DBR → CPU → 主存 | **直接**：外设 → 主存（不经过 CPU） |
| **后续数据处理** | 程序继续处理 | ISR 处理 | CPU 仅收"传输完成"中断 |
| **CPU 负担** | 全程占用（忙等） | 仅在 ISR 中逐字传送 | 仅在启动和结束时介入 |
| **适用场景** | 低速、简单系统 | 中低速、实时响应 | 高速大批量数据传送 |

> ⚠️ **核心区别**：程序中断方式中，CPU 仍**逐字**从外设数据寄存器读取数据并写入主存（搬运工仍是 CPU）。DMA 方式中，数据传送由 DMA 控制器独立完成，CPU 只负责启动和收尾。

#### 五、一句话总结

**外设要提供三样东西：数据 + 中断请求信号 + 中断类型号。数据的存储、加工、后继处理全部由 ISR 完成——外设不需要知道数据最终去哪里、怎么用。**

### Q58 | 2026-05-28

**问题**：在多重中断的处理过程中，中断隐指令完成时间段是否就是中断响应时间段？中断服务程序执行时间段是否是中断处理时间段？而能够抢断中断的时间段是不是在 ISR 中 STI 开中断之后的某一点？

**回答**：

#### 一、中断隐指令时间段 = 中断响应时间段？

**是的，两者等价。** 中断隐指令是 CPU 响应中断后由**硬件自动完成**的操作序列，不属于任何用户程序指令（故称"隐"）。这个硬件操作阶段就是**中断响应周期**。

```text
当前指令执行完毕
      │
      ▼
┌─────────────────────────┐
│  中断响应周期 = 中断隐指令  │  ← 硬件自动完成，非软件指令
│                         │
│  ① SP-1 → SP, SP → MAR  │
│  ② PC → MDR → 主存[SP]  │  压栈保存断点
│  ③ PSW → 堆栈（部分 CPU）│  保存程序状态字
│  ④ 中断向量 → PC         │  跳转到 ISR 入口
│                         │
│  ▲ 全程关中断，不可被抢断  │
└─────────────────────────┘
      │
      ▼
  进入 ISR 第一条指令
```

| 两个名称 | 指代对象 | 侧重点 |
| :--- | :--- | :--- |
| **中断响应周期** | 指令周期五阶段之一（取指→间址→执行→**中断**） | 时序位置——"哪一 CPU 周期阶段" |
| **中断隐指令** | 该阶段中硬件执行的操作序列（关中断 + 保存断点 + 取 ISR 入口） | 功能内容——"做了哪些事" |

---

#### 二、中断服务程序执行时间段 = 中断处理时间段？

**基本等价，但"中断处理"有广狭两义：**

| 含义 | 覆盖范围 | 对应 408 术语 |
| :--- | :--- | :--- |
| **狭义** | 仅指 ISR 软件执行期间（入口 → IRET 前） | "中断服务程序" |
| **广义** | 从 CPU 响应中断到返回原程序的**全过程**（含中断隐指令 + ISR） | "中断处理全过程" |

408 中通常把 ISR 执行阶段称为"中断处理"，中断响应阶段已独立命名，所以这个对应关系是对的。

---

#### 三、能抢断的时间段在 ISR 中什么位置？

**在 ISR 中，但不是在"某一点"——是一段连续窗口：STI（开中断指令）之后 → CLI（关中断指令）之前。** 不是任意位置都能被抢断。

```text
中断响应（硬件隐指令）          中断服务程序执行（软件）
┌──────────────┐    ┌─────────┬──────────────┬─────────┬──────┐
│ 关中断        │    │ 保存现场  │  STI 开中断   │  核心处理 │ CLI  │
│ 保存断点(PC)  │──→ │ (PUSH各  │              │  (可被   │ 关中断 │ IRET
│ 取ISR入口→PC  │    │  寄存器)  │              │   抢断)  │ 恢复  │ 返回
│              │    │          │              │          │  现场  │
└──────────────┘    └─────────┴──────────────┴─────────┴──────┘
     ↑                  ↑           ↑            ↑         ↑
  全程关中断          仍关中断    从此处起      在此处止    从此恢复
  不可抢断           不可抢断    可被更高级    不可再抢断   关中断状态
                                 中断抢断

可抢断窗口：STI ─────► CLI（一段连续时间，不是"一个点"）
```

**嵌套打断的完整时序：**

```text
主程序          ISR_1（2级）         ISR_2（1级·更高级）
  │               │                    │
  │  1级中断请求   │                    │
  ├──────→│        │                    │
  │       │ 关中断  │                    │
  │       │ 现场保存 │                    │
  │       │ STI ───│──→ 开中断          │
  │       │        │   1级请求到达       │
  │       │        ├─────────────────→ │
  │       │        │                    │ 关中断
  │       │        │                    │ 保存现场
  │       │        │                    │ STI（开中断）
  │       │        │                    │ ... 核心处理 ...
  │       │        │                    │ CLI（关中断）
  │       │        │                    │ 恢复现场
  │       │        │                    │ IRET
  │       │        │←───────────────── │
  │       │ ... 继续ISR_1核心处理 ...   │
  │       │ CLI（关中断）               │
  │       │ 恢复现场                    │
  │       │ IRET                       │
  │←──────┤        │                    │
  │ 继续  │        │                    │
```

---

#### 四、三个时间段的抢断能力对比

| 时间段 | 是否可被抢断 | 原因 |
| :--- | :---: | :--- |
| 中断隐指令（中断响应） | ❌ 不可 | 硬件自动关中断，PC/PSW 正在压栈，此时打断会破坏堆栈一致性 |
| ISR：**现场保存阶段**（STI 之前） | ❌ 不可 | IF=0，中断被屏蔽 |
| ISR：**STI 之后 → CLI 之前** | ✅ 可以 | IF=1，更高级中断请求可被响应 |
| ISR：**现场恢复阶段**（CLI 之后） | ❌ 不可 | 即将 IRET，若此时被抢断，返回地址链会混乱 |

---

#### 五、一句话总结

> **中断隐指令 = 中断响应**（同一阶段，硬件关中断完成）；**ISR 执行 = 中断处理**（软件完成）；**可抢断的窗口是 STI → CLI 之间的一段连续时间**——没开中断的 ISR 段落同样不可被抢断。多重中断的关键不是"ISR 中间某一点"，而是软件**主动在保存现场后 STI 开了一个窗口**，让更高级中断有机会进来。
