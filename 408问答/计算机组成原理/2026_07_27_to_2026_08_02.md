### Q65 | 2026-07-28

**问题**：DMA 请求到底指什么？是不是外设不直接向 CPU 发 DMA 请求，而是外设发信号给 DMA 控制器，然后 DMA 控制器置位后向 CPU 发请求？

**回答**：

用户的理解是正确的。DMA 传送涉及**两级请求信号**，需要严格区分：

#### 一、完整信号链路

```
外设 ──DREQ──→ DMA控制器 ──HRQ──→ CPU
              (内部锁存)    (总线请求)
```

| 信号 | 全称 | 方向 | 含义 |
| :--- | :--- | :--- | :--- |
| **DREQ** | DMA Request | 外设 → DMA 控制器 | 外设通知 DMA 控制器："数据就绪，请求 DMA 服务" |
| **HRQ**（或 BUSRQ） | Hold Request / Bus Request | DMA 控制器 → CPU | DMA 控制器向 CPU 申请总线使用权 |
| **HLDA**（或 BUSAK） | Hold Acknowledge / Bus Acknowledge | CPU → DMA 控制器 | CPU 让出总线，授权 DMA 控制器接管 |
| **DACK** | DMA Acknowledge | DMA 控制器 → 外设 | DMA 控制器回应外设："总线已拿到，开始传送" |

#### 二、"DMA 请求"一词的歧义

"**DMA 请求**"在中文教材中存在语境歧义，需根据上下文区分：

| 语境 | 实际信号 | 说明 |
| :--- | :--- | :--- |
| "外设发出 DMA 请求" | **DREQ** | 外设 → DMA 控制器。这是外设唯一主动发出的信号 |
| "DMA 控制器发 DMA 请求给 CPU" | **HRQ**（总线请求） | DMA 控制器 → CPU。更精确应称"总线请求" |
| "DMA 请求检测时机在总线周期结束时" | **HRQ**（总线请求） | 从 CPU 视角看：在每个总线周期结束时采样 HRQ 线 |
| "DMA 请求信号置 1" | **DMA 控制器内部状态位** | 控制器收到 DREQ 后，内部锁存请求，再向 CPU 发 HRQ |

#### 三、全过程时间线

```text
时间 ──────────────────────────────────→

① 外设数据准备好
   │
   ├→ DREQ 有效（外设 → DMA 控制器）
   │
   ├→ DMA 控制器内部锁存请求
   │
   ├→ 当前总线周期结束时
   │    DMA 控制器发出 HRQ（→ CPU）
   │    └── 即"在总线周期结束时检测 DMA 请求"
   │
   ├→ CPU 完成当前总线周期
   │    响应 HRQ → 发出 HLDA（→ DMA 控制器）
   │    总线使用权从 CPU 移交给 DMA 控制器
   │
   ├→ DMA 控制器收到 HLDA
   │    发 DACK（→ 外设）：通知"可以开始了"
   │    发地址/控制信号到总线，开始数据传送
   │    每次传一个字（一个总线周期）
   │
   └→ 传送完毕（字计数器归零）
        DMA 控制器撤销 HRQ
        CPU 收回总线控制权
        DMA 控制器向 CPU 发中断请求（通知整块传输完成）
```

#### 四、与已有 Q62/Q63 的关联

| 已有 Q | 涉及内容 | 本 Q 补充的精度 |
| :--- | :--- | :--- |
| Q62 | DMA 请求检测时机 = 总线周期结束时 | 明确这个"DMA 请求"指的是 **HRQ**（控制器→CPU），而非 DREQ |
| Q63 | DMA 与 CPU 的周期挪用关系 | 补充了 DREQ→HRQ→HLDA→DACK 的完整握手时序 |

#### 五、一句话总结

> **"DMA 请求"分两级——外设发 DREQ 给 DMA 控制器，DMA 控制器锁存后再发 HRQ（总线请求）给 CPU。408 真题中"在总线周期结束时检测 DMA 请求"指的是 HRQ 这一级，是从 CPU 视角说的。不要混淆 DREQ（外设→控制器）和 HRQ（控制器→CPU）。**

> **省流：** 外设只发 DREQ（给 DMA 控制器），DMA 控制器才发 HRQ（给 CPU 要总线）。408 真题问"DMA 请求检测时机"指的是 HRQ — CPU 在每个总线周期结束时看一眼有没有控制器在要总线，有就给，没有就继续跑。

### Q66 | 2026-07-28

**问题**：在 DMA 停止 CPU 访存模式下，DMA 传送过程中是否也会出现间断——例如外设的数据缓冲寄存器（DBR）存满了，外设停止工作，等待主存取走数据后再继续？

**回答**：

用户的直觉方向正确。停止 CPU 访存模式下，总线一直被 DMA 占据，但数据传输本身确实可能有不连续的空拍（等待周期）。

#### 一、先分清两个概念

| 概念 | 停止 CPU 访存模式下 |
| :--- | :--- |
| **总线是否一直被 DMA 占据？** | 是。从块传输开始到结束，CPU 完全不能访存 |
| **数据传输是否每个总线周期都在发生？** | 不一定。外设未就绪时，DMA 插入**等待周期**（wait state） |

核心洞察：**总线被占着 ≠ 每拍都在传数据**。DMA 控制器占有总线但外设没准备好时，当前总线周期空转。

#### 二、DBR 满导致暂停的具体场景

需区分数据方向：

**外设 → 主存（DMA 写，即 I/O 读）**：

```
外设产生数据 → 填入 DBR → DBR 满 → DREQ 有效
    → DMA 读 DBR → 写主存（一个总线周期）
    → DBR 空 → 外设填下一个字
```

- DBR 通常只有 **1 个字宽**，外设和 DMA 之间是逐字乒乓
- 外设填满 DBR 后，如果 DMA 还没来取（比如 DMA 正在处理上一个字的写内存操作），外设确实要等
- 但对于磁盘/网卡等设备，数据是**持续到达**的，DBR 不快腾空就会数据覆盖/丢失（overrun），而不是设备主动停
- 只有支持**流控**的设备才能主动暂停数据产生

**主存 → 外设（DMA 读，即 I/O 写）**：

```
DMA 读主存 → 写入 DBR → DBR 满
    → 外设从 DBR 消费数据
    → DBR 空 → DMA 写下一个字
```

- 此方向更可能出现用户描述的场景：外设消费数据慢，DBR 长期满，DMA 插入等待周期
- 例如：打印机打印速度远低于内存读取速度，DMA 每次写完 DBR 后就等着打印机取走数据

#### 三、三种总线策略下的"间断"对比

| 策略 | 总线持有 | 数据传输连续性 | 间断原因 |
| :--- | :--- | :--- | :--- |
| **停止 CPU 访存** | 全程占据 | 可能有空拍 | 外设未就绪 → DMA 插入等待周期（**总线仍被占，CPU 仍阻塞**） |
| **周期挪用** | 逐字申请 | 必然不连续 | DMA 传一个字就主动释放总线还给 CPU |
| **交替访存** | C1/C2 分时 | 必然不连续 | DMA 只在 C1 周期传，C2 空闲 |

> 提示： 停止 CPU 访存的"间断"和周期挪用的"间断"本质不同：
> - 周期挪用：DMA **主动释放**总线 → CPU 可在此期间访存
> - 停止 CPU 访存的等待周期：DMA **不释放**总线 → CPU 仍被阻塞，只是当前拍没传数据。"占着总线不干活"

#### 四、为什么停止 CPU 访存很少用

正因为存在"占着总线等外设"的浪费，停止 CPU 访存模式极少使用：

| 外设速度 | 合理策略 | 原因 |
| :--- | :--- | :--- |
| 中低速（磁盘、网卡） | **周期挪用** | 外设准备数据需要时间，DMA 趁此间隙释放总线给 CPU |
| 极高速（接近内存带宽） | **停止 CPU 访存** | 外设几乎不需要等待，空拍极少，占据总线的浪费可接受 |

#### 五、与已有 Q63 的关联

Q63 指出的"C 选项错误：DMA 传送期间 CPU 不能访存"是从周期挪用角度说的——DMA 传一个字就还总线，CPU 不需要等整块传完。本 Q 补充的是：即使在停止 CPU 访存模式下（CPU 确实全程不能访存），数据传输本身也不是每个周期都在发生——外设跟不上时 DMA 空等，进一步说明这种模式的低效。

> **省流：** 停止 CPU 访存模式下，总线全程被 DMA 占着、CPU 全程阻塞，但数据传输可以有间断——外设没准备好时 DMA 插入等待周期（占着总线不传数据）。DBR 通常只有 1 字宽，外设和 DMA 逐字乒乓。这种"占着茅坑等茅坑"的浪费正是该模式几乎不用的原因。周期挪用才是主流：传一个字就还总线，外设准备下一个字时 CPU 照常跑。
