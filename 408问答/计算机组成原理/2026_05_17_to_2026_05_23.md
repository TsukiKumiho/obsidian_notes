### Q28 | 2026-05-16 | Cache 行的位数

**问题**：Cache行的位数是指多少，若为按字节编址，主存块大小为32B，那么计算cache行位数就需将32B+tag（bit）+修改位（bit）+有效位（bit）吗，如果是按字编址呢？

---

#### 一、Cache 行位数的组成

「Cache 行的位数」指 Cache 中**每一行（Entry）的总存储比特数**：

$$ \text{Cache 行位数} = \underbrace{\text{数据位}}_{\text{块大小} \times 8} + \underbrace{\text{Tag 位}}_{\text{取决于地址格式}} + \underbrace{\text{有效位}}_{1\text{ bit}} + \underbrace{\text{脏位}}_{1\text{ bit（回写策略）}} $$

| 组成部分 | 说明 |
|:---|:---|
| 数据（Data） | 块大小 × 8 bit，存储从主存搬来的实际数据 |
| 标记（Tag） | 用于判断 Cache 行中的数据是否来自目标主存块 |
| 有效位（Valid） | 1 bit，标记该行数据是否有效（启动时全 0） |
| 脏位（Dirty） | 1 bit，回写策略下标记数据是否被修改；写直达法则不需要 |

---

#### 二、按字节编址（块大小 32B）

| 组成部分 | 位数 | 说明 |
|:---|:---:|:---|
| 数据 | 32×8 = **256 bit** | 块大小 32B |
| Tag | 取决于题目参数 | Tag = 地址总位数 − Index 位 − 块内偏移位 |
| 有效位 | **1 bit** | 固定 |
| 脏位 | **1 bit** | 回写策略需要；写直达法可省略 |

块内偏移位数 = $\log_2 32 = 5$ 位。

---

#### 三、按字编址（设 1 字 = 4B，块大小仍 32B）

**关键区别**：按字编址时，每个地址指向一个「字」而非一个「字节」。编址方式只影响**地址划分**，不影响物理存储量。

| 项目 | 按字节编址 | 按字编址（1字=4B） |
|:---|:---:|:---:|
| 块大小（物理） | 32B | 32B（不变） |
| 块内包含单位数 | 32 个字节 | 32÷4 = 8 个字 |
| 块内偏移位数 | $\log_2 32 = 5$ 位 | $\log_2 8 = 3$ 位 |
| **数据位** | 256 bit | 256 bit（不变） |
| **有效位** | 1 bit | 1 bit（不变） |
| **脏位** | 1 bit | 1 bit（不变） |
| **Tag 位** | = 总地址 − Index − 5 | = 总地址 − Index − 3 |

偏移位少的那部分会跑到 Tag 里，Tag 位数增加。

---

#### 四、对比示例

> 假设：主存地址 32 位，Cache 共 64 行，块大小 32B，回写策略。

| 字段 | 按字节编址 | 按字编址（1字=4B） |
|:---|:---:|:---:|
| 块内偏移 | $\log_2 32 =$ **5 bit** | $\log_2 8 =$ **3 bit** |
| Cache 行索引 | $\log_2 64 =$ **6 bit** | **6 bit**（不变） |
| Tag | $32 - 6 - 5 =$ **21 bit** | $32 - 6 - 3 =$ **23 bit** |
| 数据 | **256 bit** | **256 bit** |
| 有效位 | 1 bit | 1 bit |
| 脏位 | 1 bit | 1 bit |
| **一行总位数** | 256+21+1+1 = **279 bit** | 256+23+1+1 = **281 bit** |

按字编址时一行多出 2 bit，全加在 Tag 上。

---

#### 五、核心结论

1. **数据位不变**：编址方式不影响块的实际物理大小（32B 始终是 256 bit）。
2. **有效位、脏位不变**：始终各 1 bit（脏位仅在回写策略下需要）。
3. **仅 Tag 位变化**：按字编址时偏移位数减少 → 多出的位归入 Tag → Tag 变长。
4. **Cache 行位数 = 数据 + Tag + 1（有效位）+ 1（脏位，回写）**，无论按字节还是按字编址，公式相同，只是 Tag 值不同。

### Q29 | 2026-05-16 | Cache 的局部性前提与容量关系

**问题**：「Cache 的设计是基于程序访问的局限性原理。」这句话的意思是不是就是说，有的程序只是没体现出来局限性，但是就算有的程序没体现出局限性，由于局限性，增加cache的大小也会提高命中率？

---

#### 一、正确理解与常见误读

**前半句**「Cache 基于局部性原理」—— 完全正确。这是 Cache 能以小容量达到高命中率的理论前提。

**后半句推论**有问题：把因果关系搞反了。不是「因为局部性，增大 Cache 才提高命中率」，而是：
- 增大 Cache → 能装更多数据 → 减少冲突覆盖与被换出的概率 → 命中率上升
- 这与「局限性」是两条独立机制

---

#### 二、无局部性时，增大 Cache 的效果

极端情况：程序以**真随机**方式访问 1GB 地址空间，每次访问与上一次毫无关联。

| Cache 大小 | 命中率 | 原因 |
|:---|:---:|:---|
| 16KB | ≈ 0% | 工作集 1GB $\gg$ Cache |
| 1MB | ≈ 0% | $\frac{1\text{MB}}{1\text{GB}} \approx 0.1\%$ |
| 1GB | ≈ 100% | Cache 大到了覆盖整个工作集 |

Cache 容量 < 工作集时，没有局部性的程序命中率趋近于零，再增大也几乎没用——因为每次访问都会跳到 Cache 没装的那部分。

---

#### 三、局部性与容量的真实关系

Cache 之所以能用**很小的容量**（几 KB~几 MB）达到 **90%+** 命中率，靠的正是局部性。

> 没有局部性，要达到同样的命中率，Cache 必须做得和主存一样大——那就不叫 Cache 了。

正确的逻辑链：

```
程序有局部性 → 小 Cache 就能高命中率 → 增大 Cache 可进一步提高
程序无局部性 → 增大 Cache 也几乎没用 → 除非大到覆盖整个工作集
```

---

#### 四、核心结论

**「增大 Cache 能提高命中率」的前提是程序本身有局部性可供利用。**

- 有局部性：增大容量减少冲突缺失和容量缺失，效果显著
- 无局部性：Cache 装不下工作集时命中率始终接近 0%，增大容量只是杯水车薪，除非大到能装下全部数据

---

### Q30 | 2026-05-17 | 分页映射与 Cache 映射的差异

**问题**：分页虚拟存储器中的映射关系与 Cache 的映射关系有何不同？主存到 Cache 中，可以直接由主存的地址推得数据所在 Cache 的行号，但是在分页虚拟存储器中则不能，为什么？

---

#### 一、总览对照

| 维度 | 分页虚拟存储器 | Cache |
|:---|:---|:---|
| 映射对象 | 虚页号 → 物理页框号 | 主存块号 → Cache 行号 |
| 管理方 | **OS（软件）** + MMU（硬件） | **纯硬件**（Cache 控制器） |
| 映射表存放处 | **主存**中的页表（每进程一份，MB 级） | Cache 内部 **Tag 阵列**（与行一一对应） |
| 映射表大小 | 虚页数可达百万项 | Cache 行数（几十~几千） |
| 粒度 | 页（典型 4KB） | 块（典型 16B~64B） |
| 缺失代价 | 缺页中断 → **磁盘 I/O**（毫秒级） | 硬件自动 → **访问主存**（纳秒级） |
| 缺失处理者 | OS 缺页中断处理程序 | 硬件 Cache 控制器 |
| 关联度 | 全相联（任一虚页→任一物理页） | 直接/组相联/全相联，硬件固定 |
| 替换算法 | OS 实现（LRU / Clock） | 硬件实现（LRU / 伪 LRU / 随机） |
| 写策略 | 回写为主（脏位在页表项） | 写直达 / 写回 |
| 加速结构 | **TLB**（快表），缓存页表项 | Cache 本身就是加速层 |

---

#### 二、核心差异：能不能「算」出行号

##### Cache：地址自带行号信息

以直接映射为例，主存块号 mod Cache 行数 = 该块在 Cache 中的**唯一位置**。硬件拿到主存地址后，Index 字段直接译码选出 Cache 行，无需查表。

```
主存地址 = [  Tag  |  Index  |  Offset  ]
                 ↓         ↓
             比 Tag ← 直接译码选中一行
```

即使组相联，Index 也能将范围缩小到一组（组内 Tag 并行比较）。公式 `块号 mod 组数 = 组号` 始终成立，因为这是**硬件连线决定的**。

##### 分页：虚页号与物理页框号无公式关系

虚页 → 物理页的映射是**任意**的，由 OS 动态分配，不存在 `phys = f(virt) mod N` 这样的公式。

| | Cache 映射 | 分页映射 |
|:---|:---|:---|
| 映射决定因素 | **硬件设计固定**（几路组相联，行数确定） | **OS 运行时的空闲页框分布**（动态） |
| 行号/页框号获取 | **算出来**（mod 运算或译码） | **查表**（页表 + TLB） |
| 能否用公式推得 | ✅ | ❌ |

---

#### 三、为什么分页不能像 Cache 一样「算」

Cache 映射规则是**硬件写死的**——从地址总线看到那一刻，块号 → 行号的信号通路就已由连线决定了。这是电路级的确定关系。

分页中，物理页框分配由 **OS 软件动态管理**：

- 进程的虚页 0 这一秒可能映射到物理页 5
- 换出再换入后，下一秒可能变成物理页 12
- 物理页的分配取决于系统当时的空闲页框情况，完全不可预测

所以只能**查页表**，不能算。

---

#### 四、TLB 与 Cache 的层次关系

```
虚地址 ──→ TLB（硬件快查，缓存页表项）
              │ miss → 查主存中的页表 → 得物理地址
              │ hit  → 直接得物理地址
                         │
                         ▼
              物理地址 ──→ Cache（硬件，Index 选组 → Tag 比较）
                              │ hit  → 数据送 CPU
                              │ miss → 从主存搬一块进 Cache
```

| 对比 | TLB | Cache |
|:---|:---|:---|
| 缓存对象 | **页表项**（虚→物理映射） | **主存数据** |
| 命中后得 | 物理页框号 | 实际指令/数据 |
| Tag 内容 | 虚页号的一部分 | 主存块号高位 |
| 缺失后 | 查页表（可能再缺页） | 访问主存 |

---

#### 五、一句话总结

> **Cache 的行号是「算」出来的——地址字段的 Index 直接译码选中行，这是硬件电路的确定性映射。分页的物理页框号是「查」出来的——虚页到物理页的映射由 OS 动态决定，没有公式，只能查页表。**

### Q31 | 2026-05-17 | 基本分页存储 vs 分页虚拟存储

**问题**：分页存储和分页虚拟存储的差别？

---

#### 一、核心区别：是否允许「缺页」

两者都用了「分页」机制做地址转换，但所处层次和解决的核心问题不同。

| | 基本分页存储 | 分页虚拟存储 |
|:---|:---|:---|
| **进程运行前提** | 所有页**必须先全部装入主存** | 只需装入部分页，其余留在磁盘 |
| **程序能否大于物理内存** | ❌ 不能 | ✅ 可以（按需调入） |
| **页表项内容** | 页框号 + 基本保护位 | 页框号 + **存在位** + 修改位 + 引用位 + 外存地址 |
| **缺页中断** | ❌ 不存在 | ✅ 核心机制——访问不在内存的页时触发 |
| **所属范畴** | 内存管理（存储管理） | 虚拟存储器 |

---

#### 二、页表项的差异

**基本分页**的页表项：

| 字段 | 说明 |
|:---|:---|
| 页框号（物理块号） | 该虚页对应的物理页框编号 |
| 保护位 | 读/写/执行权限 |

**分页虚拟存储**的页表项额外增加：

| 字段 | 说明 |
|:---|:---|
| **存在位（P）** | 1 = 在主存中；0 = 在磁盘上 → 缺页中断 |
| 修改位（M） | 该页写入过？决定换出时是否写回磁盘 |
| 引用位（A） | 用于 Clock / LRU 页面置换算法 |
| 外存地址 | 该页在磁盘上的位置 |
| 访问权限位 | 基本分页也有 |

---

#### 三、一句话总结

> **基本分页存储**：分页只是地址映射手段，进程全部装入主存才能运行。**分页虚拟存储** = 基本分页 + 请求调页 + 页面置换，进程只需部分驻留，缺页时从磁盘调入——这是「虚拟」二字的来源。

### Q32 | 2026-05-17 | 存储空间与地址空间的区别

**问题**：虚拟存储器是主存与辅存之间构建的一个**地址空间**，Cache 是主存与 CPU 之间的**辅助存储空间**。存储空间与地址空间有何不同？

---

#### 一、核心定义

|                | 地址空间              | 存储空间               |
| :------------- | :---------------- | :----------------- |
| **本质**         | 逻辑概念——「能访问多大的范围」  | 物理概念——「实际有多少地方放数据」 |
| **决定因素**       | 地址线位数 / 指令寻址能力    | 实际安装的硬件容量          |
| **是否必须全部物理存在** | ❌ 不必——可以部分地址映射到磁盘 | ✅ 必须——存储空间一定对应物理介质 |
| **程序员视角**      | 程序中使用的地址          | 无直接感知              |

**一句话**：地址空间是「你能叫出多少号」，存储空间是「你实际有多少个房间」。

---

#### 二、虚拟存储器为何是「地址空间」

虚拟存储器解决的核心问题是**让程序以为自己拥有比实际主存更大的空间**：

```
程序看到的：  虚地址空间 0 ~ 4GB-1  （地址空间——大）
                  ↓ 页表映射
实际存放的：  主存 512MB + 磁盘上的交换区  （存储空间——小）
```

- 程序用 32 位虚地址，认为自己在 4GB 的地址空间中运行
- 实际上主存只有 512MB，其余页面在磁盘上
- **「虚拟」二字修饰的是地址**——程序使用的地址是虚拟的（不是真实的物理地址），需要页表翻译

> 关键：虚拟存储器为每个进程创造了一个**独立的、连续的虚拟地址空间**，并将这个地址空间映射到主存+辅存构成的存储层次上。

---

#### 三、Cache 为何不创建新地址空间

Cache 只做一件事：**暂存主存中某些块的副本**，加速访问。CPU 发出的始终是主存地址（或虚地址），该地址经过译码后：

```
CPU 发出主存地址
       │
       ├─→ Index 字段直接选中 Cache 中的一行
       ├─→ 比较该行 Tag 与地址高位
       └─→ 命中则取数据，不命中则访问主存
```

关键：
- CPU **不知道 Cache 的存在**——它发出的就是主存地址，没有引入新的地址概念
- Cache 不改变地址空间的大小——主存地址空间多大，CPU 看到的就是多大
- Cache 只是**物理上多了一块存储介质**（SRAM），所以是「辅助存储空间」

---

#### 四、对比总结

| | 虚拟存储器 | Cache |
|:---|:---|:---|
| **创建了什么** | 新的**虚拟地址空间**（大于物理内存） | 不创建地址空间，只增加**物理存储容量** |
| CPU 发出的地址 | 虚地址（需翻译成物理地址） | 主存地址（不用翻译） |
| 程序员感知 | 能感知到更大地址空间 | **完全透明**，感知不到 Cache |
| 核心机制 | 地址映射（虚→物理）+ 缺页调入 | 数据暂存 + Tag 匹配 |
| 本质分类 | **地址空间** | **存储空间** |

---

#### 五、一句话总结

> **虚拟存储器创造了一个比物理内存更大的「地址空间」，让程序能使用超过实际主存容量的地址范围——程序用的是「虚拟地址」。Cache 只是增加了一块 SRAM「存储空间」，CPU 永远发的是主存地址，不知道 Cache 存在。虚拟存储器改变的是"能访问多少地址"，Cache 改变的是"数据放在哪更快"。**

---

### Q33 | 2026-05-17 | 该说法的正误辨析

**问题**：「虚拟存储器是主存与辅存之间构建的一个地址空间，Cache 是主存与 CPU 之间的辅助存储空间。」这个说法是正确的吗？

---

#### 一、结论

**该说法基本正确，但需补充关键信息，否则容易引起误解。**

---

#### 二、逐句辨析

##### 前半句「虚拟存储器是主存与辅存之间构建的一个地址空间」

✅ **正确**，但不够完整。

虚拟存储器确实是在主存（DRAM）和辅存（磁盘）之间构建的存储层次，其核心产物是一个**虚拟地址空间**。但严格来说：

- 虚拟存储器 = 虚拟地址空间 + 页表映射机制 + 缺页中断 + 页面置换
- 「地址空间」是虚拟存储器最核心的对外表现，但实现上依赖一整套软硬件协同机制
- 这个地址空间不是凭空虚构的——它**对应着辅存中的数据**，只是通过主存作为缓存来加速访问

##### 后半句「Cache 是主存与 CPU 之间的辅助存储空间」

✅ **正确**。

Cache 是主存与 CPU 之间的高速缓冲存储器，用 SRAM 实现：
- 不创建新地址空间——CPU 始终发出主存地址
- 仅提供物理存储——暂存主存块的副本以加速访问
- 「辅助存储空间」的定位准确——它是主存的补充，加速数据访问

---

#### 三、该说法容易引发的误解

| 可能误解 | 澄清 |
|:---|:---|
| 以为虚拟存储器**只是**一个地址空间，里面没有数据 | 虚地址空间中的每一页都对应磁盘上的数据；主存是磁盘的"Cache"，数据实际存在磁盘上，热数据调入主存 |
| 以为虚拟存储器与 Cache 互斥——一个管地址，一个管数据 | 两者是**串联**关系：虚地址 → TLB/页表 → 物理地址 → Cache，各管一段 |
| 以为「地址空间」比「存储空间」低级 | 恰恰相反——地址空间是更上层的抽象（给程序员用的），存储空间是底层实现 |

---

#### 四、更精确的表述

> **虚拟存储器**以主存为缓存、磁盘为后备，为每个进程构造了一个独立、连续的**虚拟地址空间**，并通过页表将该地址空间映射到物理存储层次上。**Cache** 则位于主存与 CPU 之间，不创建新地址空间，仅以 SRAM 提供高速**存储空间**来暂存主存块的副本。

---

#### 五、一句话总结

> **这个说法正确地抓住了两者在存储层次中的位置差异——虚拟存储器创造地址空间（逻辑层），Cache 提供存储空间（物理层）。但需注意：虚拟存储器不止是地址空间，它还依赖一整套机制将地址映射到实际数据。**

### Q34 | 2026-05-17 | 虚拟存储器综合辨析

**问题**：虚拟存储器是如何形成的，为什么虚地址空间远大于实地址空间，为什么引入了虚拟存储器就能够使得 CPU 访问的速度加快？虚拟存储器不只是一个地址空间吗，没包含任何数据，那么数据不还是从辅存里边访问的吗？它又不像是 Cache 直接将主存中的数据副本放在自己的存储空间中，而是只是一个利用主存和辅存构建的一个逻辑上连续的地址空间而已。还有，书上说虚拟存储器借鉴了 Cache 的思想，将辅存中频繁访问的数据缓存在主存中。为什么是缓存？他不是只是一个地址空间吗？

---

#### 一、虚拟存储器 ≠ 仅地址空间

这是最核心的澄清：虚拟存储器不是「仅一个地址空间」，而是以下组件构成的**完整存储层次**：

```
虚拟存储器 = 虚拟地址空间 + 主存（DRAM）+ 磁盘（辅存）+ 页表 + 缺页中断机制
```

地址空间只是对程序员的「接口」，背后的主存、磁盘、页表才是真正干活的东西。

---

#### 二、为什么虚地址空间远大于物理内存

虚地址空间的大小取决于 CPU **地址线的位数**（如 32 位 → 4GB），物理内存大小取决于**实际安装了多大的 DRAM**。

虚空间 > 物理内存之所以可行，靠的是**程序局部性原理**：

- 程序在任何时刻真正活跃的只是少部分页面（工作集）
- 只需将工作集驻留在主存中，其余虚页留在磁盘
- 访问不在主存的页时，触发缺页中断，从磁盘调入

> 类比：你的书架（主存）只能放 50 本书，但你的书目编号系统（地址空间）可以编号到 5000 本——其余 4950 本在仓库（磁盘）。当你需要编号 237 的书时，如果不在书架上，就去仓库取。

---

#### 三、为什么能加速 CPU 访问

虚拟存储器**不是让单次访存变快**，而是提升了**系统整体吞吐量**：

1. **程序无需全量装入内存即可运行**——过去程序必须全部装入内存才能执行，程序大小受物理内存严格限制
2. **多道程序度提高**——每个程序只需工作集驻留，内存可同时容纳更多进程，CPU 利用率上升
3. **绝大多数访问命中主存**——缺页率通常低于 0.01%，平均访问时间 ≈ 主存延迟

加速的不是「一次访问」而是「系统吞吐」。如果缺页率高，虚拟存储器反而会严重拖慢系统（颠簸现象）。

---

#### 四、数据到底在哪里？「只是地址空间」的误区

**误区**：虚拟存储器只是地址空间，不包含数据，数据在辅存里，所以每次访问都得从辅存读。

**真相**：虚地址空间的每一页**确实对应辅存中的数据**，但：

- 经常访问的页面（工作集）已被**调入主存**
- CPU 访问时，绝大多数情况下数据已经在主存里了
- 只有缺页时才需要从磁盘调入

```
虚页 0  ──→ 物理页框 5（在主存中）← 命中！
虚页 1  ──→ 物理页框 2（在主存中）← 命中！
虚页 2  ──→ 磁盘地址 X（不在主存）← 缺页！调入主存
虚页 3  ──→ 物理页框 7（在主存中）← 命中！
```

地址空间定义了「能访问哪些页」，但**数据通过主存中的物理页框来访问**。

---

#### 五、「借鉴了 Cache 思想」——为什么说主存是磁盘的「Cache」

这一点是理解虚拟存储器的关键。看存储层次：

```
CPU 寄存器  ←  最快、最小
     ↕
   Cache（SRAM）  ← 主存的"Cache"
     ↕
   主存（DRAM）   ← 磁盘的"Cache" ← 这里！
     ↕
   磁盘/SSD
```

在虚拟存储器中，**主存本身就是磁盘的 "Cache"**：

| 对应关系 | Cache | 虚拟存储器（主存作为磁盘Cache） |
|:---|:---|:---|
| 上层（快而小） | Cache（SRAM） | 主存（DRAM） |
| 下层（慢而大） | 主存（DRAM） | 磁盘 |
| 传输单位 | Block（块） | Page（页） |
| 命中 | Cache 命中 → 直接返回 | 页在内存中 → 直接访问 |
| 缺失 | Cache miss → 从主存取一块 | 缺页 → 从磁盘调入一页 |
| 映射方式 | 直接/组相联 | 全相联（任一虚页→任一物理页框） |
| 替换策略 | 硬件 LRU/随机 | OS 软件 LRU/Clock |

**所以「借鉴了 Cache 思想」的意思是**：主存缓存磁盘中被频繁访问的页，就像 Cache 缓存主存中被频繁访问的块。虚拟地址空间中的每一页数据**确实在磁盘上**，但它的活跃副本在**主存**中——主存就是磁盘页面的 Cache。

---

#### 六、一句话总结

> **虚拟存储器不只是「地址空间」——它是「虚拟地址空间 + 以主存为 Cache 缓存磁盘数据 + 页表映射 + 缺页中断」的完整存储层次。地址空间是给程序员的接口，主存里的物理页框才是数据的实际载体。数据确实存在磁盘上，但热数据已被调入主存，绝大多数访问直接命中主存——这正是借鉴 Cache 思想的地方。**

### Q35 | 2026-05-17 | 进程与页表关系 + 页表项与虚页对应

**问题**：每个进程是否对应一个页表？所有进程都可以访问页表吗？页表中的每个表项是否与一个虚页对应？

---

#### 一、每个进程是否对应一个页表？

**是的。** 每个进程拥有独立的页表。

原因：每个进程拥有独立的虚拟地址空间，页表负责将该进程的虚拟页号映射到物理页框号。不同进程的同一虚拟地址（如 `0x00400000`）映射到的物理地址不同，因此必须有各自的页表。

| 对象 | 页表数量 | 原因 |
|:---|:---:|:---|
| **进程** | 1 张 | 独立地址空间，必须独立映射 |
| **同进程线程** | 共享 1 张 | 共享地址空间 |
| **内核** | 共享内核部分 | 所有进程页表的内核空间部分映射相同 |

进程切换时，OS 更新 **页表基址寄存器**（如 x86 的 CR3）指向新进程的页表，同时刷新 TLB（切换地址空间）。这也解释了进程切换比线程切换开销更大——线程切换不换页表，也不需要刷 TLB。

---

#### 二、所有进程都可以访问页表吗？

**不能。** 页表是内核数据结构，用户进程无法直接读写。

| 角色 | 能否访问 | 说明 |
|:---|:---:|:---|
| **用户进程** | 否 | 每条访存指令都会**经过**页表（MMU 硬件自动查表翻译），但进程无法读写页表项 |
| **操作系统内核** | 是 | 内核在特权态下可修改页表内容、切换 CR3 指向不同进程页表 |
| **MMU 硬件** | 是 | 每次地址翻译时硬件自动走查页表（TLB 命中则跳过） |

原因：
- 页表基址寄存器（CR3）是**特权寄存器**，只能在内核态修改
- 页表本身存放在**内核地址空间**中，用户态无法访问
- 如果进程可以直接改页表，就能把自己的虚页映射到任意物理页框，破坏所有进程隔离

---

#### 三、页表中每个表项是否与一个虚页对应？

**末级页表：是。非末级页表：否。** 需区分页表层级。

| 页表类型 | 每个表项对应什么 |
|:---|:---|
| **单级页表** | 每个 PTE 对应一个虚页（虚页号 = 数组下标） |
| **多级页表 — 末级** | 每个 PTE 对应一个虚页，存物理页框号 + 标志位 |
| **多级页表 — 上级** | 存的是**下一级页表的物理地址**，不对应虚页本身 |
| **倒排页表** | 反过来，每个表项对应一个**物理页框**，而非虚页 |

上级页表条目本质是「目录项」——告诉你下级页表在哪，不直接描述虚页到物理页框的映射。

---

#### 四、一句话总结

> **每个进程一张页表，页表是内核数据结构，用户进程只能「经过」不能「访问」。多级页表中只有末级条目对应虚页，上级条目是目录指针。倒排页表反过来，按物理页框组织。**

### Q36 | 2026-05-18 | 按字节/字编址 vs 按字节/字寻址

**问题**：按字节编址和按字节寻址分别用于什么地方？有什么不同？按字编址和按字寻址呢？

---

#### 一、先区分两组概念的本质

|          | **编址**（Addressing）    | **寻址**（Access）        |
| :------- | :-------------------- | :-------------------- |
| **定义**   | 存储器中**每个地址单元**对应多大的数据 | CPU **一次访存**能精确到多大的粒度 |
| **关注点**  | 存储器的**组织方式**          | 指令集/CPU 的**访存能力**     |
| **决定因素** | 地址线与存储体的连接方式          | 指令集设计 + 数据通路宽度        |
| **问的是**  | "一个地址编号代表多少数据？"       | "一条访存指令操作几字节？"        |

> 类比：编址 = 每个信箱的门牌号规则；寻址 = 你能以多细的粒度去投递/取件。

---

#### 二、按字节编址

**定义**：存储器的每一个字节被分配一个独立的地址编号。

| 项目 | 说明 |
|:---|:---|
| 地址 N | 指向第 N 个字节 |
| 地址 N+1 | 指向第 N+1 个字节 |
| 寻址范围 | $2^n$ 个地址 → 共 $2^n$ 字节 |

**使用场景**：几乎所有现代通用计算机（x86, ARM, RISC-V）都采用按字节编址——每个字节一个地址。

**原因**：`char` 类型占 1 字节，必须能直接寻址到单字节。字符串处理也依赖逐字节寻址。

---

#### 三、按字编址

**定义**：存储器中每一个**字**（如 4 字节）被分配一个独立的地址编号。

| 项目 | 说明 |
|:---|:---|
| 地址 N | 指向第 N 个字（如 4 字节） |
| 地址 N+1 | 指向第 N+1 个字 |
| 寻址范围 | $2^n$ 个地址 → 共 $2^n \times \text{字长}$ 字节 |

**使用场景**：
- **老式大型机 / 某些 DSP** — 只处理固定字长的数据，不需要字节粒度
- **408 考题**中常见对比出现——用来让考生在两种编址方式下分别计算 Cache 容量、地址位数等

**优缺点**：
- ✅ 地址空间需求更小（同样地址位数，覆盖的存储空间更大）
- ❌ 无法直接访问单个字节，需配合字节使能信号

---

#### 四、按字节寻址 vs 按字寻址

**按字节寻址**：CPU 的访存指令能以**1 字节**为最小单位访问内存。

**按字寻址**：CPU 的访存指令最小只能访问**一个字**（如 4 字节）。

| | 按字节寻址 | 按字寻址 |
|:---|:---|:---|
| 最小访问粒度 | 1 字节 | 1 个字 |
| `char` 访问 | 直接 `load byte` | 需 load word + 移位 + 掩码 |
| 地址总线 | 发出字节地址 | 发出字地址（地址总线的低两位可省略） |
| 非对齐访问 | 可能支持 | 通常要求对齐，否则异常 |
| 典型架构 | x86, ARM | 早期 SPARC, 某些 DSP |

---

#### 五、四种组合及其存在性

| 编址方式 | 寻址方式 | 存在？ | 典型场景 |
|:---|:---|:---:|:---|
| 按字节编址 | 按字节寻址 | ✅ 最常见 | x86, ARM — 每个字节有地址，可访问单字节 |
| 按字节编址 | 仅按字寻址 | ⚠️ 少见 | 某些 RISC（存储器按字节编址以保证兼容，但 CPU 只发字地址） |
| 按字编址 | 按字寻址 | ✅ | 早期大型机、某些 DSP |
| 按字编址 | 按字节寻址 | ❌ 无意义 | 存储器都不按字节编号了，无法按字节寻址 |

**现代通用计算机**的操作模式：**按字节编址 + 多粒度寻址**（load byte / half-word / word 均有对应的机器指令）。

---

#### 六、在 408 考题中的影响

**场景 1：计算寻址范围**

> 某机字长 32 位，地址总线 32 根，按字节编址。求 CPU 的寻址范围。

解：$2^{32}$ 个地址 × 1 字节/地址 = $2^{32}$ 字节 = 4GB。

若改为**按字编址**（字长 32 位 = 4 字节），则：$2^{32}$ 个地址 × 4 字节/地址 = $2^{34}$ 字节 = 16GB。

**场景 2：Cache 行大小与位数计算**

> 主存按字节编址，Cache 行大小 64B。块内偏移需几位？

解：64B = $2^6$B → 块内偏移 = 6 位（每个字节一个地址，64 个字节需 6 位区分）。

若改为**按字编址**（1 字 = 4 字节），块内偏移 = $\log_2(64/4) = \log_2 16 = 4$ 位。

**场景 3：地址空间利用率**

> 存储容量 1GB，分别按字节编址和按 32 位字编址，各需多少位地址？

- 按字节编址：$\log_2(2^{30}) = 30$ 位
- 按 32 位字编址：$\log_2(2^{30}/4) = \log_2(2^{28}) = 28$ 位

---

#### 七、一句话总结

> **"编址"管存储器怎么编号（每个地址指多大），"寻址"管 CPU 怎么访问（一次访存多大粒度）。现代通用计算机 = 按字节编址 + 多粒度寻址（byte/half/word）。按字编址存于考题和特定 DSP 中，用于对比计算。408 考题看到"按 X 编址"先确认一个地址对应多少字节，全部计算基于此展开。**

### Q36 补充 | 2026-05-18 | "字"在按字编址/寻址中到底指什么

**问题**：按字编址中的"字"是指什么？与机器字长（32位/64位）是什么关系？

---

#### 一、结论

**在 408 考研语境中，按字编址/按字寻址的「字」通常 = 机器字长（存储字长）。**

---

#### 二、"字"在 408 中的三种出现场景

| 场景 | 含义 | 具体值 | 谁决定 |
|:---|:---|:---|:---|
| **按字编址** | 存储字长 — 一个存储地址对应的数据宽度 | 通常 = 机器字长 | 存储器设计 |
| **机器字长** | CPU 一次能处理的数据位数（寄存器/数据通路宽度） | 32 位/64 位 | CPU 设计 |
| **指令字长** | 一条机器指令的位宽 | 可能 = / > / < 机器字长 | ISA 设计 |

三者关系：存储字长一般等于机器字长（数据总线一拍传完一个机器字），指令字长则不一定。

---

#### 三、为什么「存储字长 = 机器字长」？

计算机设计上的自然匹配：

- 数据总线宽度 = 机器字长（CPU 一个周期正好传输一个机器字）
- 存储器一个存储单元 = 数据总线宽度（一拍读完一个单元，不浪费带宽）
- 所以存储字长 = 机器字长

因此 408 题干写「某机字长 32 位，按字编址」→ 一个字 = 32 bit = 4 字节，每个地址对应 4 字节。

---

#### 四、一个高频坑：「字长 ≠ 编址单位」

> 某机**字长 32 位**，**按字节编址**。

这里的两个信息是**独立**的：

| 信息 | 含义 | 对计算的影响 |
|:---|:---|:---|
| 字长 32 位 | CPU 以 4 字节为单位处理数据 | 一个 32 位整数占 4 个地址（地址 N, N+1, N+2, N+3） |
| 按字节编址 | 每个地址对应 1 字节 | 每个地址 = 1B；地址位宽直接对应字节容量 |

**常见错误**：看到「字长 32 位」就按「每个地址 4 字节」来计算块内偏移、Cache 行大小。实际上编址方式由题干单独给出，**字长不等于编址单位**。

> 实例：字长 32 位，按字节编址，Cache 行 64B → 块内偏移 = $\log_2 64 = 6$ 位（而非 $\log_2(64/4) = 4$ 位）。

---

#### 五、对比总结

| 题干表述 | 每个地址对应 | 计算规则 |
|:---|:---:|:---|
| 字长 32 位，**按字节编址** | 1 字节 | 容量 = 地址数 × 1B |
| 字长 32 位，**按字编址** | 4 字节（= 字长） | 容量 = 地址数 × 4B |
| 字长 64 位，**按字节编址** | 1 字节 | 容量 = 地址数 × 1B |
| 字长 64 位，**按字编址** | 8 字节（= 字长） | 容量 = 地址数 × 8B |

**核心原则**：编址单位看题干「按 X 编址」，不看样子长。字长只在「按字编址」时告诉你一个字有多大。

---

#### 六、一句话总结

> **408 中的"字"默认 = 机器字长（= 存储字长）。但编址单位和字长是两个独立信息——「按字节编址」就是每个地址 1 字节，跟字长 32 位还是 64 位无关。看题先找「按 X 编址」，再对照字长确定一个地址对应的字节数。**

### Q36 补充② | 2026-05-18 | 按字寻址时"首个地址代表整个字"的含义

**问题**：按字寻址是否就是指：字的最前面那个字节的地址就代表了那个字本身？

---

#### 一、结论

**在按字节编址的机器上：是的。在按字编址的机器上：不存在字节地址，地址直接就是字地址。**

---

#### 二、情况 A：按字节编址 + 按字访问（现代通用场景）

每个字节有独立地址，访问一个字（如 4 字节）时，CPU 发出**首字节地址**，硬件自动连续取出 4 个字节拼成一个字：

```
地址:  0    1    2    3    4    5    6    7
       ├────── 字0 ──────┤├────── 字1 ──────┤
       ↑                  ↑
    字0 的地址 = 0       字1 的地址 = 4
```

CPU 执行 `load word [0]` → 硬件取地址 0, 1, 2, 3 四个字节 → 拼接成 32 位字。地址线实际发出的是 0，**用首字节地址代表了整个字**。

> 这就是你直觉中的场景——这里的「字」作为一个整体来访问，但编址依然按字节。所以一个 32 位字占用 4 个地址编号。

---

#### 三、情况 B：按字编址 + 按字寻址

每个地址编号直接指向一个完整的字。**根本不存在字节地址**：

```
地址:   0        1        2
       ├─字0 ──┤├─字1 ──┤├─字2 ──┤
       (32bit)  (32bit)  (32bit)
```

CPU 发出地址 **1** → 直接取回完整的第 1 个字（32 bit）。

这里不能说"用首地址代表字"——因为字节地址这个概念在此根本不存在。地址 1 就是字地址，不是某个字节的地址。

---

#### 四、两种情况的直观对比

| | 按字节编址 + 按字访问 | 按字编址 + 按字寻址 |
|:---|:---|:---|
| 一个地址编号代表什么？ | 1 个字节 | 1 个字（如 4 字节） |
| 一个 32 位字占几个地址？ | 4 个（N, N+1, N+2, N+3） | 1 个 |
| "字地址"是什么？ | 字的首字节地址 | 地址本身 |
| 有字节地址吗？ | 有 | **无** |
| `load word [4]` 取什么？ | 取地址 4,5,6,7 四个字节拼一字 | 取第 4 个完整的字 |

---

#### 五、一句话总结

> **按字节编址时，字的地址 = 首字节地址，"一个地址代表一个字"这种说法成立（但严格来说是指向字的起始位置）。按字编址时，地址直接就是字地址，字节地址不存在，谈不上"代表"。408 考题 99% 是按字节编址，所以你的理解在实践中完全正确——按字访问就是用首地址指向整个字。**

### Q37 | 2026-05-18 | 指令字长与字节编址

**问题**：当计算机按字节编址时，指令字长是否必须要是 8 的整数倍？

**回答**：

**是的，必须是 8 的整数倍。**

核心原因：按字节编址（byte addressing）意味着每个内存地址指向 1 个字节 = 8 bits，这是存储器的最小可寻址单元（minimum addressable unit）。指令存储在内存中，占据从某个起始地址开始的一段连续地址空间，因此指令占用的物理存储必然是整数字节 → 指令字长必为 8 bits 的整数倍。

反例说明：假如某指令字长为 10 bits，它需要 1.25 字节的存储空间。但地址只能指向整字节边界（0, 1, 2, ...），不存在「0.25 字节」对应的地址，10-bit 指令在字节编址的机器上无法有效存取——要么浪费 6 bits 凑成 2 字节（16 bits），要么与其他数据混合存放（会极大增加取指复杂度，现实中无处理器采用）。

**实际处理器印证**：

| 处理器/架构 | 指令长度 | 对应字节数 |
| :--- | :--- | :---: |
| x86（变长） | 8 ~ 120 bits | 1 ~ 15 字节 |
| ARM Thumb | 16 bits | 2 字节 |
| MIPS | 32 bits | 4 字节 |
| ARM（标准） | 32 bits | 4 字节 |
| RISC-V（标准） | 32 bits | 4 字节 |
| RISC-V 压缩指令 | 16 bits | 2 字节 |

无一例外，全是 8 的整数倍。

**补充说明**：

1. 指令字长是 8 的整数倍，但**不一定是 2 的幂次**。例如理论上可以存在 24-bit（3 字节）或 48-bit（6 字节）的定长指令集，只是现实中出于硬件对齐和译码简化的考虑而极少被采用。

2. **概念区分**（三者无必然倍数关系）：
   - **指令字长**（Instruction Word Length）：一条指令占用的位数
   - **存储字长**（Memory Word Length）：一个存储字包含的位数（可能与机器字长相同或不同）
   - **机器字长**（Machine Word Length）：CPU 通用寄存器的位数，体现处理器一次能处理的数据宽度

3. **按字编址的情况**：如果计算机是按字编址（word addressing），则指令字长必须是该「字」的整数倍。例如某机器按 16-bit 字编址，指令长度必为 16 bits 的整数倍。

### Q38 | 2026-05-19 | 指令执行中的访存操作分析

**问题**：指令执行过程中，哪些操作会访存？各访存多少次？操作流程是怎样的？哪些操作不会访存？

**回答**：

### 指令周期四阶段

```
取指周期 → 间址周期 → 执行周期 → 中断周期
  (必有)    (可能无)    (必有)    (可能无)
```

### 一、各周期访存分析

**取指周期（必有）**

| 操作 | 访存 | 次数 |
| :--- | :---: | :---: |
| 按 PC 取指令 | 是 | 1 次读 |
| PC + 1 | 否 | 0 |

流程：`PC → MAR → 地址总线 → 存储器 → 数据总线 → MDR → IR`

**间址周期（仅间接寻址时有）**

| 寻址方式 | 访存 | 次数 |
| :--- | :---: | :---: |
| 立即/寄存器/直接寻址 | 否 | 0 |
| 一次间接寻址 | 是 | 1 次读 |
| 多次间接寻址 | 是 | 多次读 |
| 变址/基址/相对寻址 | 否 | 0（CPU 内部加法得 EA） |

**执行周期（按指令分）**

| 指令类型 | 访存 | 次数 |
| :--- | :---: | :---: |
| RR 型运算（ADD R1,R2） | 否 | 0 |
| 立即数运算 | 否 | 0 |
| 移位/逻辑（寄存器型） | 否 | 0 |
| LOAD | 是 | 1 次读 |
| STORE | 是 | 1 次写 |
| PUSH | 是 | 1 次写（SP 先减再写） |
| POP | 是 | 1 次读（先读 SP 再加） |
| CALL | 是 | ≥2 次写（返回地址 + 可能压栈保护） |
| RET | 是 | ≥1 次读（取返回地址 → PC） |
| 跳转（JMP/JZ） | 否 | 0（仅改 PC） |
| NOP | 否 | 0 |

LOAD 流程：`MAR←EA → M[MAR]→MDR → MDR→目标寄存器`  
STORE 流程：`MAR←EA, MDR←源寄存器 → MDR→M[MAR]`

**中断周期（响应中断时）**

| 操作 | 访存 | 次数 |
| :--- | :---: | :---: |
| 保存断点（PC → 栈） | 是 | 1 次写 |
| 保存 PSW | 是 | 1 次写（部分机器） |
| 取中断向量 | 是 | 1 次读 |
| 关中断 | 否 | 0 |

最少 2 次（保存断点 + 取向量），最多 3 次。

### 二、完整指令访存次数示例

`ADD R1, R2`（寄存器-寄存器型）：

| 周期 | 访存 |
| :--- | :---: |
| 取指 | 1 读 |
| 间址 | 0 |
| 执行 | 0 |
| 中断 | 0 |
| **合计** | **1 次** |

`LOAD R1, addr`（直接寻址）：

| 周期 | 访存 |
| :--- | :---: |
| 取指 | 1 读 |
| 间址 | 0 |
| 执行 | 1 读 |
| **合计** | **2 次** |

`STORE R1, @addr`（间接寻址 + 写）：

| 周期 | 访存 |
| :--- | :---: |
| 取指 | 1 读 |
| 间址 | 1 读 |
| 执行 | 1 写 |
| **合计** | **3 次** |

### 三、总结

**一定访存**：取指令（1 次）、LOAD/POP、STORE/PUSH、间接寻址、CALL（压返回地址）、中断响应（保存断点 + 取向量）

**绝不访存**（纯 CPU 内部）：寄存器间运算、移位、逻辑、MOV 寄存器间、标志位操作、跳转（JMP/JZ 等）、NOP、PC 自增

### Q39 | 2026-05-19 | 相对寻址中"下一条指令地址"的理解

**问题**：在相对寻址中，使用的是"当前指令的下一条指令的地址"作为基准——这个不太理解，为什么不是当前指令的地址？

---

#### 一、结论

**因为取指阶段结束后 PC 已经自动递增，指向了下一条指令。相对寻址在"执行阶段"计算地址时，PC 的值已经更新过了。**

这是硬件执行顺序导致的自然结果，不是人为规定的特殊设计。

---

#### 二、指令执行的两个阶段

```
┌─────────────────────────────────────────────────────┐
│ ① 取指阶段                                          │
│    PC → MAR → 地址总线 → 存储器 → 数据总线 → MDR → IR │
│    PC ← PC + 1（或 + 指令长度）                      │
│                                                     │
│ ② 执行阶段（相对寻址的 EA 在这里计算）                │
│    EA = (PC) + A                                    │
│    ↑ 此时的 PC 已经是下一条指令的地址                  │
└─────────────────────────────────────────────────────┘
```

**关键时间线**：PC 递增发生在取指阶段末尾、执行阶段之前。所以当 CPU 开始计算操作数地址时，PC 已经指向下一条指令了。

---

#### 三、具体数值示例

假设内存布局如下（按字节编址，当前指令占 2 字节，偏移量 A = +8）：

```
地址    内容
─────   ─────────
1000    相对寻址指令（占 2B，偏移量字段 A = +8）
1002    下一条指令
1004    ...
 ...
1010    要访问的操作数  ← 目标地址
─────   ─────────
```

执行过程分步：

| 步骤 | 发生的事 | PC 的值 |
| :---: | :--- | :---: |
| 1 | 取指：从地址 1000 取出指令 → IR | 1000 |
| 2 | PC 递增：PC ← 1000 + 2 | **1002** |
| 3 | 执行：EA = (PC) + A = 1002 + 8 = **1010** | 1002 |

EA = 1010 正是操作数所在地址。

**如果错误地用"当前指令地址"**（1000），EA = 1000 + 8 = 1008，就取错了——偏了两个字节。

---

#### 四、为什么偏移量 A 要相对于"下一条"而非"当前"？

**原因一：硬件实现最自然**

取指完成后 PC 已经指向下一条，直接用当前 PC 值加偏移量，无需额外硬件保存"当前指令地址"。

**原因二：转移指令（JMP）的统一性**

相对寻址最常用于**转移指令**。考虑 `JMP +20`：

```
① 取指：取出 JMP +20 指令，PC 指向下一条
② 执行：PC ← (PC) + 20  ← 跳转到"下一条往后 20"
```

如果相对于"当前指令"计算，程序员/编译器在写跳转距离时必须额外减去指令自身长度，极不直观。而相对于下一条，跳转距离就是「从这个位置往后/往前数多少条指令」，语义清晰。

**原因三：代码浮动（relocatability）**

无论程序加载到内存的哪个位置，只要跳转的相对距离不变，转移指令的偏移字段就不需要修改。如果相对于"当前指令"计算，程序搬家后指令的绝对地址变了，但下一条的绝对地址也同步变了，相对距离依然正确——两者效果等价，但用"下一条"在硬件上更直接。

---

#### 五、一句话总结

> **相对寻址用"下一条指令地址"作为基准，不是因为特殊设计，而是因为取指阶段 PC 已经自动递增。CPU 在计算 EA 时，PC 自然指向下一条，直接用即可——这是硬件执行时序的必然结果。**

---

### Q40 | 2026-05-19 | 大端方式 vs 小端方式的直观理解

**问题**：大端方式是不是就是人类所习惯的顺序（高位在低位之前），而小端方式则为反人类的顺序？

---

#### 一、结论

**是的。大端 = 人类书写习惯（高位→低位，从左到右），小端 = 反人类直觉但硬件有好处。**

---

#### 二、两种方式的直观对比

以 32 位数据 `0x12345678` 存入内存地址 `0x00` 为例：

```
大端 (Big-Endian) — 符合人类阅读习惯
地址:  0x00    0x01    0x02    0x03
      ┌──────┬──────┬──────┬──────┐
      │ 0x12 │ 0x34 │ 0x56 │ 0x78 │
      └──────┴──────┴──────┴──────┘
       高位字节          低位字节
       (MSB)             (LSB)

小端 (Little-Endian) — "反着存"
地址:  0x00    0x01    0x02    0x03
      ┌──────┬──────┬──────┬──────┐
      │ 0x78 │ 0x56 │ 0x34 │ 0x12 │
      └──────┴──────┴──────┴──────┘
       低位字节          高位字节
       (LSB)             (MSB)
```

**大端模式**：最高字节 `0x12` 存在最低地址 `0x00`。看内存 dump 时，`12 34 56 78` 读起来就是原数字——和人类从左到右写数字完全一致。

**小端模式**：最低字节 `0x78` 存在最低地址 `0x00`。看内存 dump 是 `78 56 34 12`，一眼看不出来原数字是什么。

---

#### 三、为什么小端"反直觉"却被广泛使用？

**核心原因：不同字长数据的起始地址可以保持不变。**

```
整数 0x00000042 (= 十进制 66) 分别以 int32 / int16 / int8 访问：

小端存储（地址从低到高）：
  地址:  0x00    0x01    0x02    0x03
       ┌──────┬──────┬──────┬──────┐
       │ 0x42 │ 0x00 │ 0x00 │ 0x00 │
       └──────┴──────┴──────┴──────┘
         ↑                  ↑
    取 int8：读 0x00 → 0x42 ✓（同一地址直接读）
    取 int16：读 0x00-0x01 → 0x0042 ✓（同一地址读 2 字节）
    取 int32：读 0x00-0x03 → 0x00000042 ✓

大端存储（地址从低到高）：
  地址:  0x00    0x01    0x02    0x03
       ┌──────┬──────┬──────┬──────┐
       │ 0x00 │ 0x00 │ 0x00 │ 0x42 │
       └──────┴──────┴──────┴──────┘
                               ↑
    取 int8：读 0x03 → 0x42（地址变了！）
    取 int16：读 0x02-0x03 → 0x0042（地址也变了！）
    取 int32：读 0x00-0x03 → 0x00000042
```

在小端模式下，同一个内存地址 `0x00`，无论按 int8、int16 还是 int32 去读，得到的**数值相同**。大端则不行——截取不同宽度时起始地址需要变。

这对于硬件做**加法进位**也友好：从最低位开始加，恰好是地址 0x00 的位置，进位向高地址方向自然传播。

---

#### 四、实际应用中的阵营

| 阵营 | 采用方 | 备注 |
| :--- | :--- | :--- |
| **大端** | 网络协议（TCP/IP）、PowerPC、SPARC、MIPS（可配） | "网络字节序" = 大端 |
| **小端** | x86、ARM（可配，默认小端）、RISC-V（小端） | 桌面/移动/嵌入式主流 |

408 考试中，题干通常**不会默认某种字节序**——需要从题目描述或内存 dump 数据反推。

---

#### 五、一句话总结

> **大端 = 高位存低地址，看内存 dump 和人类读数一致，网络传输用。小端 = 低位存低地址，看 dump 是反的，但不同字长取同一地址的数值不变，x86/ARM 用。两种方式没有"对错"，只是取舍不同。**

| :--- | :--- | :--- |

| 类型 | 操作数位置 | 数据访存 |
| :--- | :--- | :---: |
| RR 型（寄存器-寄存器） | 都存寄存器 | 0 |
| RS 型（寄存器-存储器） | 一个寄存器，一个内存 | 1 |
| SS 型（存储器-存储器） | 都在内存 | 2 |

RISC 采用 **Load-Store 架构**：运算指令仅 RR 型，访存单独用 LOAD/STORE。

#### 五、CISC vs RISC

| 维度 | CISC | RISC |
| :--- | :--- | :--- |

| 字长 | 变长 | 定长 |
| 寻址方式 | 多（>10） | 少（3-5） |
| 运算访存 | 可直接访存 | 仅 LOAD/STORE |
| 控制方式 | 微程序 | 硬布线 |
| 流水线 | 难 | 易 |

#### 六、程序控制类指令细分

| 类型 | 行为 | 保存返回地址？ |
| :--- | :--- | :---: |
| 无条件转移 `JMP` | PC ← 目标 | ❌ |
| 条件转移 `JZ`/`JNZ` | 条件满足则 PC ← 目标 | ❌ |
| 子程序调用 `CALL` | 压栈返回地址 → PC ← 目标 | ✅ |
| 子程序返回 `RET` | 弹栈 → PC | ❌ |
| 中断隐指令 | 硬件压栈断点 → 取中断向量 | ✅（硬件自动） |

### Q42 | 2026-05-19 | 特权指令 + 各指令的作用与存在意义

**问题**：指令分类中漏了特权指令。另外各类指令分别解决什么实际需求？转移、调用、返回这些怎么改变程序执行次序？

**回答**：

#### 一、特权指令（补充 Q41 遗漏的分类）

特权指令 = **只能在核心态（管态）执行的指令**，用户态执行会触发异常。

| 类型 | 典型操作 | 作用 |
| :--- | :--- | :--- |
| I/O 控制 | `IN`, `OUT`（I/O 独立编址时） | 用户程序不能绕过 OS 直接操作硬件 |
| PSW 修改 | 修改中断使能位、特权级位 | 控制 CPU 运行级别 |
| 存储管理 | 写页表基址寄存器、刷新 TLB | OS 管理虚拟内存，进程隔离 |
| 中断控制 | `CLI`(关中断)、`STI`(开中断) | 控制中断响应时机 |
| 系统控制 | `HLT`(停机)、模式切换 | CPU 全局状态 |
| 保护寄存器 | 修改越界检查的基址/限长寄存器 | 内存保护 |

> ⚠️ **访管指令（陷入指令）不是特权指令**——它故意在用户态执行，作用是主动陷入内核，让 CPU 切换到核心态去执行真正的特权操作。

#### 二、各类指令解决什么实际需求

| 程序中的需求 | 对应指令 | 机制 |
| :--- | :--- | :--- |
| 把数据从内存搬到寄存器 | `LOAD` | 内存 → 寄存器 |
| 把结果写回内存 | `STORE` | 寄存器 → 内存 |
| 寄存器间搬运 | `MOV` | 纯 CPU 内部 |
| 函数传参/局部变量 | `PUSH` / `POP` | 栈操作 |
| 算术运算 | `ADD`, `SUB`, `MUL`, `DIV` | ALU 运算 |
| 比较大小 | `CMP` | 做减法但不存结果，只置标志位 |
| 位掩码操作 | `AND`, `OR`, `XOR` | 按位逻辑 |
| 乘除 $2^n$ | `SHL`, `SHR`（逻辑移位） | 左移一位 = ×2 |
| if-else 分支 | `JZ` / `JNZ` / `JG` / `JL` | 根据标志位决定 PC 是否跳转 |
| while/for 循环 | `JMP`(跳回开头) + `JNZ`(条件满足跳出) | 条件转移 + 无条件转移组合 |
| 调用函数 | `CALL` | 压栈返回地址 → 跳转 |
| 函数返回 | `RET` | 弹栈 → PC |
| 响应键盘/时钟等外部事件 | 中断隐指令 + `IRET` | 硬件压栈断点 → 取向量 → 执行处理程序 → 返回 |
| OS 管理硬件资源 | 特权指令 | 只能在核心态执行 |
| 用户请求 OS 服务(读文件/分配内存) | 访管指令(`INT`/`SYSCALL`) | 主动陷入内核 |

#### 三、程序控制类改变执行次序的本质

程序默认**顺序执行**（PC 不断 +1）。这三类指令的核心都是**改写 PC**，区别在于"跳之前是否保存返回路径"：

```
JMP（无条件转移）    PC ← 目标地址
                    不保存任何东西，一去不回
                    用途：goto、循环的"跳回开头"

JZ/JNZ/...（条件转移） if (标志位满足) PC ← 目标地址
                    也不保存返回地址
                    用途：if-else 分叉、循环的条件判断

CALL（子程序调用）   SP ← SP-1; M[SP] ← (下条指令地址); PC ← 目标
                    ★ 和 JMP 的本质区别：CALL 保存了"回家路线"
                    用途：调用函数

RET（返回）          弹栈 → PC
                    ★ CALL 和 RET 必须成对使用
                    用途：从函数返回调用处继续执行
```

**一句话**：程序需要非顺序执行时，就靠这些指令改写 PC。JMP 是"一去不回"，CALL/RET 通过栈解决了"跳过去还得回来"的问题。

### Q43 | 2026-05-19 | 相对寻址中偏移量 A 的符号扩展

**问题**：相对寻址 EA = (PC) + A，其中 A 为补码表示的偏移量。运算时是否需要先把 A 扩充位宽？

**回答**：

**是的，必须先做符号扩展（sign-extend），再送入 ALU 相加。**

#### 一、为什么不能直接加

A 字段只有几个 bit（如 8-bit 偏移），PC 是 32/64-bit。位宽不等，ALU 无法直接运算。扩展位宽时，高位填什么决定了数值的正确性。

#### 二、数值示例

PC = `0x00001008`，A = -8（8-bit 补码 = `0xF8`）

| 扩展方式 | A 扩展结果 | EA 计算结果 | 正确？ |
| :--- | :--- | :--- | :---: |
| **符号扩展**（高位填符号位） | `0xFFFFFFF8` | `0x00001008 + 0xFFFFFFF8` = **`0x00001000`** | ✅ 往前 8 字节 |
| 零扩展（高位填 0） | `0x000000F8` | `0x00001008 + 0x000000F8` = `0x00001100` | ✗ 变成往后 248 字节 |

**因为 A 是补码（有符号数），必须用符号扩展才能保持数值不变。** 零扩展只适用于无符号数。

#### 三、硬件实现

指令译码后，硬件直接把 A 的最高位（符号位）复制到 ALU 输入的所有高位上，一个周期内完成，不需要额外时钟：

```
A 字段（8-bit）： [a7][a6][a5][a4][a3][a2][a1][a0]
                       ↓ 符号扩展至 32-bit
ALU 输入：    [a7][a7][a7]...[a7][a7][a6][a5][a4][a3][a2][a1][a0]
              ←────── 24 个 a7（符号位）复制 ──────→
```

#### 四、408 中的相关考点

不只是相对寻址——所有带**立即数偏移**的寻址（变址、基址、相对）中，偏移量字段都是补码，运算前都要符号扩展。做成大题时不要漏掉这一步，否则负偏移量方向的 EA 全部算错。
